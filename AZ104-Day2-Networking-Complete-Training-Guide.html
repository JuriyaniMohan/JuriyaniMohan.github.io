Module 1: Azure Virtual Networks (VNets)

Click to expand

What Is a VNet?

Analogy / Memory Tip A Virtual Network (VNet) is your own private network inside Azure. Think of it as your own private neighborhood in a massive city. Your resources (VMs, databases, etc.) live inside this neighborhood and can talk to each other, but they’re isolated from everyone else’s neighborhoods by default.
Analogy / Memory Tip ANALOGY: VNet = Your Private Neighborhood

Imagine Azure as a huge city. A VNet is your gated community within that city. Subnets are the different streets inside your community (Elm Street for web servers, Oak Avenue for databases). NSGs are the security guards at each street entrance checking who can enter and leave. The VNet address space (10.0.0.0/16) is like your community’s postal code range — all houses get addresses from this range.

Key VNet Facts

A VNet exists in a single Azure region (e.g., East US) and a single subscription
A VNet has one or more address spaces defined in CIDR notation (e.g., 10.0.0.0/16)
VNets are FREE — you don’t pay for VNets themselves
Resources in the SAME VNet can communicate by default (no extra config needed)
Resources in DIFFERENT VNets CANNOT communicate by default (you need peering or VPN)
A VNet is completely isolated from other VNets unless you explicitly connect them

  1. Go to portal.azure.com > search “Virtual networks” > + Create

Module 2: Network Security Groups (NSGs)

Click to expand

What Is an NSG?

A Network Security Group is a virtual firewall that filters network traffic to and from Azure resources. It contains security rules that allow or deny inbound and outbound traffic based on source, destination, port, and protocol.

Analogy / Memory Tip ANALOGY: NSG = Nightclub Bouncer

Think of an NSG as a bouncer at a nightclub. The bouncer has a list of rules (VIP list). Rule 1 (Priority 100): Allow anyone wearing a blue wristband (port 443). Rule 2 (Priority 200): Allow anyone with a VIP card (port 3389 from specific IP). Rule 3 (Priority 65000): Deny everyone else. The bouncer checks each person against the rules IN ORDER of priority (lowest number = checked first). First match wins — once a rule matches, the bouncer stops checking.

LAB: Create NSG Rules for a Three-Tier App
  1. Go to Network security groups > + Create
  2. Name: “NSG-WebSubnet”, Region: East US, RG: RG-Networking-Lab
  3. After creation, go to NSG > Inbound security rules > + Add
  4. Rule 1: Source=Internet, Dest Port=80,443, Protocol=TCP, Action=Allow, Priority=100, Name=Allow-HTTP-HTTPS
  5. Rule 2: Source=Any, Dest Port=3389, Protocol=TCP, Action=Deny, Priority=200, Name=Deny-RDP-From-Internet
  6. Go to NSG > Subnets > Associate > select Prod-VNet > WebSubnet
  7. Create another NSG: “NSG-DbSubnet”
  8. Rule: Source=10.0.2.0/24 (AppSubnet), Dest Port=1433, Protocol=TCP, Action=Allow, Priority=100, Name=Allow-SQL-From-App
  9. Associate NSG-DbSubnet with DbSubnet
  10. Test: Deploy a VM in WebSubnet — verify it can receive HTTP traffic but not RDP from internet

Q1: What is the priority range for NSG rules?
Show Answer ▾
A: 100 to 4096. Lower number = higher priority (evaluated first). Default rules use 65000-65500.
Q2: Can you delete default NSG rules?
Show Answer ▾
A: No. Default rules cannot be deleted but can be overridden by rules with lower priority numbers.
Q3: If both subnet NSG and NIC NSG exist, which is checked first for inbound?
Show Answer ▾
A: Subnet NSG is evaluated FIRST for inbound traffic, then NIC NSG. For outbound, it’s reversed.
Q4: What is a Service Tag?
Show Answer ▾
A: A predefined label representing a group of Azure service IPs (e.g., Internet, VirtualNetwork, Storage).
Q5: What is the benefit of ASGs over IP-based rules?
Show Answer ▾
A: ASGs let you group VMs logically. Add/remove VMs from the group without changing NSG rules.

Module 3C: Azure NAT Gateway — Deep Dive

Click to expand

What Is NAT Gateway?

Azure NAT Gateway is a fully managed, highly resilient Network Address Translation service. It provides outbound-only internet connectivity for VMs in a subnet using a static public IP, without requiring those VMs to have their own public IPs.

Analogy / Memory Tip ANALOGY: NAT Gateway = Your Office’s Internet Router

Imagine your office has 200 computers (VMs) all sharing one internet connection through a single router (NAT Gateway). Every computer has a private desk number (private IP like 10.0.1.4), but when any computer sends data to the internet, the router translates the desk number to the office’s public address (public IP like 52.186.77.23). From the outside, ALL 200 computers appear to come from ONE address. When replies come back, the router knows which desk to forward them to. But NOBODY from outside can randomly call a desk number — only responses to outgoing calls get through.

How NAT Gateway Works (Step by Step)

You create a NAT Gateway resource and attach a Standard Static Public IP to it
You associate the NAT Gateway with a subnet (e.g., WebSubnet)
Immediately, ALL VMs in that subnet use the NAT Gateway’s public IP for outbound internet traffic
The private IP (10.0.1.4) is translated (SNAT’d) to the NAT Gateway’s public IP (52.x.x.1)
Return traffic (responses) flows back through the NAT Gateway to the correct VM
UNSOLICITED inbound traffic from the internet is BLOCKED — only responses get through

SNAT Port Exhaustion — The Problem NAT Gateway Solves

SNAT port exhaustion is one of the most common production issues in Azure. Here’s what happens:

Every outbound connection from a VM requires a SNAT port (think of it as a temporary channel number)
A Load Balancer pre-allocates a FIXED number of ports per VM (e.g., 1,024 ports per VM when pool has 8-15 VMs)
If a VM makes too many simultaneous outbound connections (e.g., a web scraper calling thousands of APIs), it runs out of ports
Result: Connection failures, timeouts, application errors

NAT Gateway fixes this by: dynamically allocating SNAT ports on-demand. Instead of fixed allocation, all 64,512 ports per IP are shared across all VMs in the subnet. VMs that need more ports get more ports. VMs that are idle use fewer. No fixed limits per VM.

LAB: Deploy a NAT Gateway
  1. Go to portal.azure.com > search “NAT gateways” > + Create
  2. Resource group: RG-Networking-Lab
  3. Name: “nat-gw-prod”, Region: East US
  4. Availability zone: Zone 1 (or No Zone for non-zonal)
  5. Idle timeout: 4 minutes (default, leave as-is)
  6. Go to “Outbound IP” tab: Click “Create a new public IP address”, name it “nat-gw-pip”
  7. Go to “Subnet” tab: Select Prod-VNet > WebSubnet
  8. Click Review + create > Create
  9. VERIFY: SSH/RDP into a VM in WebSubnet and run: curl ifconfig.me
  10. The returned IP should be the NAT Gateway’s public IP (not the VM’s individual IP)
  11. VERIFY: Try the same from a VM in a DIFFERENT subnet (not attached to NAT GW) — it will show a different IP

Azure CLI: Create a NAT Gateway

# Create a public IP for the NAT Gateway az network public-ip create \ --resource-group RG-Networking-Lab \ --name nat-gw-pip \ --sku Standard \ --allocation-method Static # Create the NAT Gateway az network nat gateway create \ --resource-group RG-Networking-Lab \ --name nat-gw-prod \ --public-ip-addresses nat-gw-pip \ --idle-timeout 4 # Associate NAT Gateway with a subnet az network vnet subnet update \ --resource-group RG-Networking-Lab \ --vnet-name Prod-VNet \ --name WebSubnet \ --nat-gateway nat-gw-prod # Verify from a VM in WebSubnet # SSH into VM, then run: curl ifconfig.me # Should show the NAT Gateway's public IP

Module 3D: Service Endpoints & Private Endpoints

The Problem: Securing Access to Azure PaaS Services

When a VM accesses Azure services like Storage or SQL Database, by default the traffic goes over the public internet via the service’s public endpoint. This is a security concern — even though Azure encrypts the traffic, it still travels over the internet.

Service Endpoint vs Private Endpoint WITHOUT ENDPOINTS (default): VM (10.0.1.4) ──> Internet ──> Storage (public endpoint) Traffic goes via public internet path WITH SERVICE ENDPOINT: VM (10.0.1.4) ──> Azure Backbone ──> Storage (public endpoint) Traffic stays on Microsoft network, but storage still has public IP Storage firewall can restrict: “only allow from WebSubnet” WITH PRIVATE ENDPOINT (most secure): VM (10.0.1.4) ──> 10.0.5.4 (storage’s private IP in your VNet!) Storage gets a PRIVATE IP inside your VNet! No public endpoint needed. Completely private.

LAB: Configure a Service Endpoint for Azure Storage
  1. Go to Prod-VNet > Subnets > select WebSubnet
  2. Under “Service endpoints”, click “+ Add”
  3. Select “Microsoft.Storage” from the dropdown
  4. Click Save — this enables the service endpoint on the subnet
  5. Now go to your Storage Account > Networking
  6. Under “Firewalls and virtual networks”, select “Enabled from selected virtual networks and IP addresses”
  7. Click “+ Add existing virtual network” > select Prod-VNet > WebSubnet
  8. Click Save
  9. Now ONLY VMs in WebSubnet can access this storage account via Azure backbone
  10. Any other source (internet, other subnets without endpoint) is BLOCKED by the storage firewall
Exam Tip EXAM TIP: Service Endpoints are free but only work from within Azure VNets (not from on-premises). Private Endpoints cost money but work from everywhere (including on-prem via VPN/ExpressRoute) and give the service a private IP in your VNet. The exam loves asking when to use which. Key rule: if on-prem access is needed, use Private Endpoint.

What Is VNet Peering?

VNet Peering connects two Azure VNets so resources in each VNet can communicate with each other using private IP addresses. Traffic uses Microsoft’s backbone network (not the public internet) — ultra-fast, low latency.

A <──> B B <──> C Does NOT mean A <──> C You must explicitly create A <──> C peering!

Module 7: ExpressRoute

Click to expand

What Is ExpressRoute?

ExpressRoute is a PRIVATE, dedicated connection between your on-premises datacenter and Azure. Unlike VPN, traffic NEVER goes over the public internet. It’s faster, more reliable, and more secure.

VPN Gateway vs ExpressRoute VPN Gateway: ExpressRoute: ┌───────┐ Internet ┌─────┐ ┌───────┐ Private ┌─────┐ │On-Prem│──────────>│Azure│ │On-Prem│───────>│Azure│ └───────┘ (Encrypted)└─────┘ └───────┘ Link └─────┘ (No Internet) ┌───────────────┬───────────────┬───────────────┐ │ Feature │ VPN Gateway │ ExpressRoute │ ├───────────────┼───────────────┼───────────────┤ │ Uses Internet │ Yes │ No (private) │ │ Max Bandwidth │ 10 Gbps │ 100 Gbps │ │ Latency │ Variable │ Predictable │ │ Cost │ Lower │ Higher │ │ Setup Time │ ~45 min │ Days/Weeks │ │ Encryption │ IPsec (built-in)│ Not by default│ └───────────────┴───────────────┴───────────────┘
Exam Tip EXAM TIP: ExpressRoute does NOT encrypt traffic by default (it’s a private link, so Microsoft considers it already secure). If you need encryption over ExpressRoute, you must configure a VPN tunnel ON TOP of ExpressRoute. Both can coexist on the same VNet.
QUICK RECAP
Q1: Does ExpressRoute traffic go over the internet?
Show Answer ▾
A: No. It’s a private, dedicated connection through a connectivity provider.
Q2: Is ExpressRoute encrypted by default?
Show Answer ▾
A: No. You can add encryption by running a VPN tunnel over ExpressRoute.
Q3: When should you use ExpressRoute over VPN?
Show Answer ▾
A: When you need: high bandwidth (>10Gbps), low/predictable latency, compliance (data can’t traverse internet).
Q4: Can VPN Gateway and ExpressRoute coexist on the same VNet?
Show Answer ▾
A: Yes! They can both connect to the same VNet for redundancy. VPN acts as failover if ExpressRoute goes down.

What Is a Load Balancer?

A load balancer distributes incoming traffic across multiple backend servers (VMs) to ensure no single server gets overwhelmed. It’s essential for high availability.

Q1: At what OSI layer does Application Gateway operate?
Show Answer ▾

Q2: What is URL path-based routing?
Show Answer ▾
A: Routes traffic to different backends based on URL (e.g., /images/* → Image VMs, /api/* → API VMs).
Q3: What is SSL termination?
Show Answer ▾

LAB: Use IP Flow Verify to Troubleshoot NSG
  1. Scenario: A VM in WebSubnet cannot receive HTTP traffic. Let’s find out why.
  2. Go to Network Watcher (search in portal)
  3. Click “IP flow verify”
