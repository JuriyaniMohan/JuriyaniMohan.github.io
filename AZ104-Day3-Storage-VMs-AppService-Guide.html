HOW TO THINK ABOUT AZURE STORAGE

Imagine you're moving into a new house. You need different types of storage for different things:

📦 Blob Storage = Your attic — dump anything: photos, videos, backups, logs. Just throw boxes up there.
📁 Azure Files = A shared network drive — everyone in the office maps the same F: drive. Familiar folders and files.
📊 Table Storage = A giant spreadsheet — billions of rows of simple structured data (NoSQL).
📬 Queue Storage = A mailbox queue — apps drop messages in, other apps pick them up one by one.

The Storage Account is the HOUSE itself. You first build the house (choose location, security, how many copies), then use the rooms (blob, file, table, queue) inside it.

Module 1: Storage Accounts — The Foundation

Account types, performance tiers, and creation

What Is a Storage Account?

A Storage Account is the top-level container for all Azure Storage services. It provides a unique namespace (URL) for your data, like https://mystorageaccount.blob.core.windows.net. Every piece of data you store in Azure lives inside a storage account.

Module 2: Storage Redundancy — Protecting Your Data

LRS, ZRS, GRS, GZRS, RA-GRS, RA-GZRS explained
THINK OF REDUNDANCY LIKE PHOTOCOPIES

Imagine your data is a precious document. Redundancy = how many copies and WHERE you keep them:

LRS = 3 copies in the SAME building (same datacenter). Cheapest, but building burns → all copies gone.
ZRS = 3 copies across 3 DIFFERENT buildings in the same city (availability zones). One building burns → still safe.
GRS = 3 copies in Building A (primary) + 3 more copies in Building B in another city (secondary region). City floods → still safe.
GZRS = 3 copies across 3 buildings in City A + 3 copies in one building in City B. Best of both worlds.

⚠️ EXAM TIP — ARCHIVE TIER RESTRICTIONThe Archive access tier is NOT supported with ZRS, GZRS, or RA-GZRS redundancy. It only works with LRS, GRS, or RA-GRS. Any redundancy with a "Z" blocks Archive. Remember: "Z blocks Archive."
DECISION FRAMEWORK: Choosing Redundancy

Ask: "What am I protecting against?"

Server failure only (dev/test) → LRS (cheapest)
Datacenter failure (production in one region) → ZRS
Regional disaster (business-critical) → GRS or GZRS
Need to READ from secondary during normal operations → Add RA- prefix (RA-GRS, RA-GZRS)

Second question: "Does the exam mention synchronous replication?"
Synchronous = LRS or ZRS (within the same region)
Asynchronous = anything with G (GRS, GZRS) — the cross-region part is async

QUICK RECAP QUIZ
Q1: Which redundancy replicates synchronously AND protects against a datacenter failure?
Show Answer ▾
ZRS — 3 copies across 3 availability zones, all synchronous. LRS is also synchronous but only within one datacenter.
Q2: You need to read data from a secondary region WITHOUT triggering a failover. Which redundancy?
Show Answer ▾
RA-GRS or RA-GZRS — the "RA" (Read-Access) prefix means you can read from the secondary endpoint anytime (e.g., mystorageaccount-secondary.blob.core.windows.net).
Q3: Can you move a blob to the Archive tier in a ZRS storage account?
Show Answer ▾
No. Archive tier is NOT supported with ZRS, GZRS, or RA-GZRS. Only LRS, GRS, and RA-GRS support Archive. Remember: "Z blocks Archive."

THINK ABOUT TIERS LIKE A WAREHOUSE

Hot = Items on your desk — instant access, but desk space is expensive
Cool = Items in a nearby filing cabinet — takes a few seconds to get, cheaper to store
Cold = Items in the basement storage room — takes a walk to get, much cheaper rent
Archive = Items in an offsite warehouse across town — takes HOURS to retrieve, but storage is almost free

Key insight: Storage cost goes DOWN as you go colder. Access cost goes UP. So archive is perfect for data you rarely need but must keep (compliance, legal). Hot is for your active website images.

Lifecycle Management — Automating Tier Changes

Lifecycle policies automatically move or delete blobs based on age. This is critical for cost optimization in production.

📐 FLOW: Typical Lifecycle Policy Day 0: Blob created in HOT tier (active use) │ Day 30: ──► Auto-move to COOL tier (accessed less often) │ Day 90: ──► Auto-move to COLD tier (rarely accessed) │ Day 180: ──► Auto-move to ARCHIVE tier (compliance retention) │ Day 365: ──► Auto-DELETE blob (retention period over) This entire lifecycle runs AUTOMATICALLY — zero human intervention needed!

Soft Delete & Versioning

Soft Delete = When you delete a blob, it's not actually gone — it goes to a "recycle bin" for a configurable period (1-365 days). You can recover it during this period.

Blob Versioning = Every time a blob is modified, Azure saves the previous version. You can restore any historical version. Think of it like Git version history for your files.

Snapshots = A read-only copy of a blob at a specific point in time. Unlike versioning (automatic), snapshots are created manually.

⚠️ EXAM TIPSoft delete protects against accidental DELETION. Versioning protects against accidental OVERWRITE. They solve different problems. Enable BOTH in production. Soft delete can be enabled for blobs, containers, AND file shares (each separately).
QUICK RECAP QUIZ
Q1: Which blob types support access tiers (Hot/Cool/Archive)?
Show Answer ▾
Block blobs only. Append blobs and page blobs do NOT support access tiers.
Q2: A blob was moved to Cool tier 15 days ago. If you delete it now, will you pay an early deletion fee?
Show Answer ▾
Yes. Cool tier has a 30-day minimum retention. Deleting or moving before 30 days incurs an early deletion charge for the remaining days (15 days of charges).
Q3: How long does it take to retrieve data from the Archive tier?
Show Answer ▾
1–15 hours depending on retrieval priority (Standard = up to 15 hours, High priority = under 1 hour at extra cost). Archive data must be "rehydrated" before access.
Q4: What protects against accidental file overwrite?
Show Answer ▾
Blob Versioning. Soft delete protects against deletion, versioning protects against overwrite by keeping all previous versions.

Access keys, shared access signatures, identity-based access, encryption

The 3 Ways to Access Storage Data

MethodHow It WorksSecurity LevelUse Case
Access Keys2 master keys per account — full access to everything⚠️ Lowest — like giving someone your house master keyAdmin tools, legacy apps. Rotate regularly!
SAS TokensTime-limited, scoped tokens you generate from a key✅ Medium — limited time, limited permissionsTemporary access for external users/apps

THINK OF STORAGE KEYS LIKE HOTEL ACCESS

Access Key = The hotel master key. Opens EVERY room, gym, pool, restaurant. If someone steals it, they own the whole hotel. Never share it. You have 2 keys so you can rotate one while the other is active.

SAS Token = A temporary guest card. Valid from March 1–March 3, opens only Room 204 and the gym, read-only. If stolen, damage is limited (expires soon, limited scope).

Azure AD RBAC = The fingerprint scanner. Each person is identified individually. You can see who accessed what, revoke anyone's access instantly, and nobody shares keys.

SAS Token Types

SAS TypeCreated FromScopeBest For
Account SASAccount access keyOne or more services (blob, file, queue, table)Broad access to multiple services
Service SASAccount access keySingle service (e.g., blob only)Scoped to one service
User Delegation SASAzure AD credentialsBlob and Data Lake only✅ Most secure — no keys involved
⚠️ EXAM TIPUser Delegation SAS is the MOST SECURE type because it's created with Azure AD credentials (no access key involved). It only works for Blob storage. If a question asks about the most secure SAS type, the answer is User Delegation SAS.

Storage Encryption

SSE (Storage Service Encryption) — ALL data in Azure Storage is encrypted at rest by default using 256-bit AES encryption. You cannot disable this. You have two options for managing encryption keys:

Microsoft-managed keys (MMK) — Default. Microsoft handles everything. Zero effort.
Customer-managed keys (CMK) — You manage keys in Azure Key Vault. Required for compliance in some industries.
QUICK RECAP QUIZ
Q1: Which is the most secure SAS token type?
Show Answer ▾
User Delegation SAS — uses Azure AD credentials instead of account keys. No keys are exposed.
Q2: Is data encrypted at rest by default in Azure Storage?
Show Answer ▾
Yes. 256-bit AES encryption is always on and cannot be disabled. You only choose who manages the keys.
Q3: How many access keys does a storage account have? Why two?
Show Answer ▾
Two keys (key1, key2). Two keys allow rotation without downtime — switch apps to key2, regenerate key1, then switch back.

HOW TO THINK ABOUT AZURE VMs

A Virtual Machine is a "computer inside a computer." It has everything a physical computer has — CPU, RAM, disk, network card — but it runs as software on Azure's physical hardware.

Think of Azure VMs like renting an apartment:
VM Size = the apartment size (studio, 1BR, 3BR — determines CPU/RAM)
OS Disk = the building's foundation (where the OS lives — can't remove it)
Data Disk = extra closets/storage units you add on (for your app data)
NIC = your mailbox/internet connection (how you connect to the network)
Availability Set/Zone = which building you're in (affects whether you survive disasters)

Module 7: High Availability — Sets, Zones & Scale Sets

Availability sets, availability zones, VMSS auto-scaling
THINK ABOUT AVAILABILITY LIKE EGG BASKETS

No availability strategy = All eggs in ONE basket. Basket drops → all eggs break.
Availability Set = Eggs spread across multiple baskets on the SAME table (same datacenter, different racks). One rack loses power → some eggs safe.
Availability Zone = Eggs spread across baskets in DIFFERENT buildings (different datacenters in a region). Building burns → other buildings safe.
VMSS = A machine that automatically creates MORE baskets and fills them with eggs when demand is high, and removes baskets when demand is low.

Availability Sets

ConceptWhat It IsMax
Fault Domain (FD)Physical rack in the datacenter. VMs in different FDs are on different racks with separate power and network.3 FDs
Update Domain (UD)Logical group rebooted together during Azure maintenance. VMs in different UDs aren't rebooted simultaneously.20 UDs
📐 ARCHITECTURE: Availability Set (2 FD, 5 UD) Fault Domain 0 (Rack A) Fault Domain 1 (Rack B) ┌─────────────────┐ ┌─────────────────┐ │ UD0: [VM1] │ │ UD0: [VM2] │ │ UD1: [VM3] │ │ UD1: [VM4] │ │ UD2: [VM5] │ │ UD2: [VM6] │ └─────────────────┘ └─────────────────┘ If Rack A loses power: VM1, VM3, VM5 go down BUT VM2, VM4, VM6 on Rack B keep running! During Azure maintenance: Only 1 UD rebooted at a time UD0 reboots → VM1, VM2 down, rest keeps running Then UD1 → VM3, VM4 down, etc.

VM Scale Sets (VMSS)

A VMSS creates and manages a group of identical, auto-scaling VMs. You define a template (image, size, config) and VMSS automatically creates/deletes instances based on demand.

📐 FLOW: VMSS Auto-Scaling Morning (low traffic): Evening (peak traffic): ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ ┌───┐ │VM1│ │VM2│ (2 instances) │VM1│ │VM2│ │VM3│ │VM4│ │VM5│ (5 instances) └───┘ └───┘ └───┘ └───┘ └───┘ └───┘ └───┘ Rule: If avg CPU > 75% for 5 min → add 1 VM (scale OUT) Rule: If avg CPU < 25% for 5 min → remove 1 VM (scale IN) Min: 2 instances Max: 10 instances
⚠️ EXAM TIPScale OUT = add more VMs (horizontal). Scale UP = make VM bigger (vertical, requires reboot). VMSS does scale OUT/IN automatically. Scale UP/DOWN must be done manually and causes downtime. Availability Sets CANNOT be changed after VM creation — plan ahead!
QUICK RECAP QUIZ
Q1: What SLA do Availability Zones provide vs Availability Sets?
Show Answer ▾
Availability Zones = 99.99%. Availability Sets = 99.95%. Zones provide higher availability because VMs are in different datacenters.
Q2: What is the difference between Scale Out and Scale Up?
Show Answer ▾
Scale Out = add more identical VMs (horizontal, no downtime). Scale Up = make existing VM bigger/more powerful (vertical, requires reboot/downtime).
Q3: Can you add a VM to an Availability Set after the VM is created?
Show Answer ▾
No. Availability Set must be specified at VM creation time. You cannot change it later. You'd need to delete and recreate the VM.

Module 9: Deployment Slots & Custom Domains

Zero-downtime deployment, slot swaps, TLS/SSL, custom DNS

Deployment Slots — The Zero-Downtime Trick

Deployment slots let you deploy a new version of your app to a "staging" slot, test it, then SWAP it with production — instantly, with zero downtime.

📐 FLOW: Slot Swap for Zero-Downtime Deployment BEFORE SWAP: Production Slot: v1.0 (live to users at myapp.azurewebsites.net) Staging Slot: v2.0 (being tested at myapp-staging.azurewebsites.net) SWAP OPERATION: (takes seconds, zero downtime) Azure swaps the routing — staging becomes production and vice versa AFTER SWAP: Production Slot: v2.0 (now live — users see new version instantly!) Staging Slot: v1.0 (old version — instant rollback if v2.0 has bugs!) If v2.0 has issues? Just SWAP AGAIN to roll back to v1.0 instantly!

What Swaps and What Doesn't

Swapped (moves with slot)NOT Swapped (stays with slot)
App code and contentPublishing endpoints
App settings (unless marked "slot setting")Custom domain names
Connection strings (unless marked "slot setting")TLS/SSL certificates and bindings
Handler mappingsScale settings (auto-scale rules)
General settings (framework, websockets, etc.)IP restrictions
💡 SLOT SETTINGS EXPLAINEDWhen you mark an app setting or connection string as a "slot setting" (also called "sticky"), it STAYS with that slot during a swap. Example: Your staging slot connects to a test database. Mark the DB connection string as a "slot setting" so staging always points to the test DB, even after swap. Without this, your staging slot would start pointing to the production database after swap — bad!

Custom Domains & TLS/SSL

Custom Domain: Map your own domain (www.company.com) to the App Service using a CNAME record (subdomains) or A record (root domain) + TXT for verification
Free Managed Certificate: Azure provides free SSL certificates for custom domains (auto-renewed, Standard tier+)
App Service Managed Certificate: Free but limited — doesn't support wildcard or export
Bring Your Own Certificate: Upload a PFX certificate from a certificate authority

Backup & Restore

App Service can back up your app configuration, content, and linked databases. Requires Standard tier or higher and a storage account for the backup files.

🏢 Real-World Production Scenarios

SCENARIO 1: E-Commerce Company — Storage Architecture

Requirement: An e-commerce company stores product images (accessed frequently), monthly sales reports (accessed occasionally), and 7-year compliance data (rarely accessed).

Solution:

Create a GPv2 storage account with GRS redundancy (business-critical data)
Container "product-images" → Hot tier (accessed every page load)
Container "reports" → Cool tier (accessed monthly)
Container "compliance" → Archive tier (accessed once in 7 years)
Lifecycle Policy: Move reports from Hot→Cool after 30 days, Cool→Archive after 180 days
Enable soft delete (14 days) and blob versioning for accidental deletion protection
Security: Azure AD RBAC for employees, User Delegation SAS for external partners, Private Endpoint for VNet access
SCENARIO 2: SaaS Company — VM High Availability

Requirement: A SaaS company runs a customer-facing API that must have 99.99% uptime. Traffic varies from 100 req/s at night to 10,000 req/s during business hours.

Solution:

Deploy API VMs across 3 Availability Zones (99.99% SLA)
Use a VM Scale Set with auto-scaling: min 3 VMs, max 15 VMs
Auto-scale rules: Scale out when CPU > 70%, Scale in when CPU < 30%
Standard Load Balancer distributes traffic across all instances
Premium SSD managed disks for low-latency database queries
Azure Backup with daily snapshots, 30-day retention
SCENARIO 3: Startup — App Service with CI/CD

Requirement: A startup deploys their Node.js web app multiple times per day. They need zero-downtime deployments and instant rollback capability.

Solution:

App Service Plan: Standard S1 (supports deployment slots + auto-scale)
Create a "staging" deployment slot
GitHub Actions CI/CD deploys to staging slot automatically on merge to main
Team tests on staging URL (myapp-staging.azurewebsites.net)
When approved: Swap staging → production (zero downtime)
If bugs found: Swap again to rollback instantly
Mark database connection strings as "slot settings" so staging always uses test DB
Custom domain: www.startup.com with free managed SSL certificate
Auto-scale: 1-5 instances based on HTTP queue length
THE DECISION FRAMEWORK: VM vs App Service vs Container

When the exam asks "what should you use?", ask yourself:

Do you need full OS control? (install custom software, configure OS settings, specific OS version) → VM
Just need to run web code? (focus on code, not infrastructure) → App Service
Need to run containerized apps? → Azure Container Instances (simple) or AKS (orchestration)
Need max isolation for compliance? → App Service Environment (Isolated tier) or Dedicated Host VM

Cost rule of thumb: App Service < Container Instances < VMs < Dedicated Hosts

📝 Day 3 Comprehensive Practice Exam (15 Questions)

Test yourself — try answering before clicking "Show Answer"

Q1: You need a storage account that replicates synchronously and remains available if a single datacenter fails. Which redundancy and account type?
Show Answer ▾
ZRS + General-purpose v2. ZRS replicates synchronously across 3 availability zones. GPv2 is the only standard account type that supports ZRS.
Q2: A blob in Cool tier was created 10 days ago. You move it to Hot tier. Are there extra charges?
Show Answer ▾
Yes — early deletion fee. Cool tier has a 30-day minimum. Moving before 30 days incurs charges for the remaining 20 days.
Q3: You need to give a contractor read-only access to a specific blob container for 24 hours using the most secure method. What should you use?
Show Answer ▾
User Delegation SAS. It's the most secure SAS type (uses Azure AD credentials, no access key exposure), can be scoped to a container, and time-limited to 24 hours.
Q4: Your storage account uses ZRS. Can you set up a lifecycle policy to move blobs to the Archive tier?
Show Answer ▾
No. Archive tier is not supported with ZRS, GZRS, or RA-GZRS. You can run lifecycle management for tier changes to Cool/Cold, but not Archive. Only LRS/GRS/RA-GRS support Archive.
Q5: A VM was stopped using the "Shut down" button inside Windows. Is compute billing still active?
Show Answer ▾
Yes! Shutting down from inside the OS puts the VM in "Stopped" state — you still pay for compute. You must "Stop (Deallocate)" from the Azure portal or CLI to stop compute billing.
Q6: You need 99.99% SLA for your VMs. Should you use Availability Sets or Availability Zones?
Show Answer ▾
Availability Zones — they provide 99.99% SLA. Availability Sets provide only 99.95%. Zones spread VMs across different datacenters in the region.
Q7: Traffic to your web app increases 10x during Black Friday. You want it to automatically handle the load without manual intervention. What should you configure?
Show Answer ▾
VM Scale Set with auto-scaling rules (if using VMs) or App Service auto-scale (if using App Service, Standard tier+). Both scale OUT (add instances) automatically based on metrics like CPU or HTTP queue length.
Q8: Your App Service uses the Basic (B1) tier. A developer asks to create a deployment slot for staging. Can they?
Show Answer ▾
No. Deployment slots require Standard (S1) tier or higher. Basic tier does not support slots. You must upgrade the App Service Plan to Standard first.
Q9: You swap your staging slot to production. The staging slot had a connection string pointing to a test database. After the swap, production is now connecting to the test database. How do you prevent this?
Show Answer ▾
Mark the connection string as a "slot setting" (sticky). Sticky settings stay with their slot and don't move during swaps. The production connection string would stay pointing to the production database.
Q10: You need to copy 500 GB of data from an on-premises server to Azure Blob Storage as fast as possible via the internet. What tool should you use?
Show Answer ▾
AzCopy. It's a command-line tool optimized for high-speed bulk data transfer to Azure. For 500 GB over internet, AzCopy is the best tool. For 50+ TB, consider Azure Data Box (physical device).
Q11: What is the difference between a block blob, append blob, and page blob?
Show Answer ▾
Block blob = general files, most common. Append blob = optimized for append-only operations (logs). Page blob = random read/write, used for VM disks (VHD files). Only block blobs support access tiers.
Q12: You have a web application that requires full OS-level control, custom drivers, and a specific Windows Server version. Should you use App Service or VMs?
Show Answer ▾
VMs. App Service doesn't provide OS-level access. If you need to install custom drivers, configure OS settings, or use a specific OS version, you need a VM.
Q13: What happens to data on a VM's temporary disk when the VM is deallocated?
Show Answer ▾
Data is LOST. The temporary disk is local SSD on the physical host. It's cleared on deallocation, host maintenance, or VM move. Never store important data on it.
Q14: You deploy v2.0 via slot swap. It has a critical bug. What's the fastest way to rollback?
Show Answer ▾
Swap again. The old version (v1.0) is still sitting in the staging slot. Swapping back puts v1.0 into production instantly — zero downtime rollback.
Q15: A GPv1 storage account needs zone-redundant storage. What should you do first?
Show Answer ▾
Upgrade to GPv2 first. GPv1 does not support ZRS. Upgrade to GPv2 (no downtime, no data loss), then change redundancy to ZRS.
