What Is This Section About?

Click to expand

Imagine you are the security guard and office manager of a huge building (Azure). Your job is to:

Decide WHO can enter the building (Identity = Microsoft Entra ID)
Decide WHAT each person can do once inside (Access = RBAC)
Set RULES for what is allowed in the building (Governance = Policy, Locks, Tags)
Analogy / Memory Tip ANALOGY: Think of Azure Like a Company Building

Entra ID = The reception desk that checks ID cards and gives badges. RBAC = The keycard system that decides which doors each badge can open. Policy = The building rules (no smoking, wear safety gear in the lab). Locks = The padlock on the server room that even the CEO cannot remove without a special key. Tags = The labels on each room (Floor 3, Department: Finance, Cost Center: 4001).

What Is a Tenant?

Analogy / Memory Tip A tenant is your dedicated instance of Entra ID. When your organization signs up for Azure, a tenant is automatically created. Think of it as your private directory in the cloud.
Every tenant has a unique ID (GUID) and a default domain (e.g., yourcompany.onmicrosoft.com)
You can add custom domains (e.g., yourcompany.com) by verifying DNS records
A single tenant can have multiple Azure subscriptions attached to it
A subscription can only trust ONE tenant at a time
LAB: Explore Your Entra ID Tenant
  1. Go to portal.azure.com and sign in
  2. Search for “Microsoft Entra ID” in the search bar and click on it
  3. On the Overview page, note your Tenant ID and Primary Domain
  4. Click “Properties” in the left menu — review Tenant Name, Country, and Notification Language
  5. Click “Custom domain names” — you’ll see your default .onmicrosoft.com domain
  6. Note: To add a custom domain, you’d need to add a TXT or MX record to your DNS provider

Understanding User Types

Created and managed entirely in the cloud

  1. Go to Microsoft Entra ID > Users > All users
  2. Click “+ New user” > “Create new user”

  1. Go to Microsoft Entra ID > Users > Bulk operations > Bulk create

Deleting and Restoring Users

Click to expand

When you delete a user in Entra ID, the user goes into a “soft-deleted” state:

Soft-deleted users can be restored within 30 days
After 30 days, the user is permanently deleted and CANNOT be recovered
Soft-deleted users still consume a license until permanently deleted
To view soft-deleted users: Entra ID > Users > Deleted users
Exam Tip EXAM TIP: If a question says “a user was accidentally deleted 15 days ago” — the answer is you CAN restore them. If it says “45 days ago” — the user is permanently gone and must be recreated.

Membership Types

Groups can have three types of membership:

1. Assigned: You manually add and remove members. Simple and direct.

2. Dynamic User: Members are automatically added/removed based on user attributes (like department, job title, country). Requires Entra ID P1 or P2.

3. Dynamic Device: Same as dynamic user but for devices. Only available for Security groups.

Dynamic Group Membership Rules

This is a powerful feature and is heavily tested on the exam. Dynamic groups use expressions to auto-populate:

Dynamic Membership Rule Examples

# All users in the IT department

(user.department -eq "IT")

# All users with job title containing "Engineer"

(user.jobTitle -contains "Engineer")

# All users in US OR UK

(user.usageLocation -eq "US") -or (user.usageLocation -eq "UK")

# All users in IT department AND with Manager role

(user.department -eq "IT") -and (user.jobTitle -eq "Manager")

# All users who are NOT guests

(user.userType -eq "Member")

# All users with email ending in @company.com

(user.mail -match "@company.com$")

LAB: Create a Dynamic Security Group
  1. Go to Microsoft Entra ID > Groups > New group
  2. Group type: Security
  3. Group name: “Dynamic-IT-Department”
  4. Membership type: “Dynamic User”
  5. Click “Add dynamic query”
  6. In the rule builder: Property = department, Operator = Equals, Value = IT
  7. Click “Validate Rules” tab — select a user to test if they would be included
  8. Click “Save” > “Create”
  9. WAIT: Dynamic groups can take 5–15 minutes to populate. Check back after a few minutes.
  10. Verify: Go to the group > Members and confirm the correct users appear
Exam Tip EXAM TIP: Dynamic groups can take up to 24 hours to fully evaluate in large tenants. You CANNOT manually add or remove members from a dynamic group — membership is entirely controlled by the rule. If you need to add even one exception, you must modify the rule or use a separate assigned group.

PRODUCTION TIP: Nesting Groups

In real-world Azure, you often nest groups. For example: Create a dynamic group “All-Engineers” based on job title. Create a security group “Engineering-Resources-Access”. Add the “All-Engineers” group as a member of “Engineering-Resources-Access”. Assign RBAC roles to “Engineering-Resources-Access”. This way, when new engineers join, they automatically get the right access through the dynamic group membership chain.

What Is SSPR?

Click to expand

SSPR allows users to reset their own passwords without calling the helpdesk. This is one of the most asked-about features on the exam and one of the most useful in production.

How SSPR Works (Step by Step)

User goes to passwordreset.microsoftonline.com (or clicks “Forgot password” at login)
User enters their username (UPN)
User must pass a CAPTCHA (to prevent bots)
User verifies identity using one or more authentication methods
If verification passes, user can set a new password
If password writeback is enabled, the new password syncs back to on-premises AD

SSPR Configuration Options

Setting

Options

Details

SSPR Enabled

None / Selected / All

Selected lets you enable for specific groups first (pilot). All enables for entire tenant.

Authentication Methods Required

1 or 2

How many methods the user must complete. Microsoft recommends 2 for better security.

Available Methods

Mobile app notification, Mobile app code, Email, Mobile phone, Office phone, Security questions

You choose which methods are available. Security questions are NOT available for admins.

Number of Security Questions Required

3 to 5

Questions required to register AND questions required to reset (can be different numbers).

Registration

Require at registration / Days to re-confirm

Force users to register methods when they next sign in. Re-confirm every 180 days default.

Password Writeback

On / Off

Syncs new password back to on-premises AD. Requires Entra Connect + P1 license.

LAB: Enable and Test SSPR
  1. Go to Microsoft Entra ID > Password reset
  2. Under “Properties”: Set “Self-service password reset enabled” to “Selected”
  3. Select a group (e.g., create a test group with your test user)
  4. Go to “Authentication methods”: Set “Number of methods required to reset” to 1 (for testing). Enable “Email” and “Mobile phone”
  5. Go to “Registration”: Enable “Require users to register when signing in”
  6. Click “Save”
  7. Open an InPrivate/Incognito browser window
  8. Sign in as your test user at portal.azure.com
  9. The user will be prompted to register authentication methods (email, phone)
  10. After registering, sign out and go to passwordreset.microsoftonline.com
  11. Enter the test user’s email and complete the reset process
  12. Verify the password was successfully changed by signing in with the new password
Exam Tip EXAM TIP: Security questions are NOT available for administrator accounts — this is a security measure. Admins always need 2 methods. Also, SSPR requires Entra ID P1 minimum for the “Selected” option and P1 for password writeback.

What Is B2B Collaboration?

Click to expand

Azure AD B2B (Business-to-Business) lets you invite external users (partners, vendors, contractors) to access your Azure resources. They sign in with their own identity (their company’s account, Gmail, etc.) but appear as “Guest” users in your directory.

How B2B Invitation Works

You invite an external user by their email address
They receive an email invitation with a link
They click the link and sign in with their OWN identity provider
A Guest user object is created in YOUR Entra ID directory
You can assign them to groups, give RBAC roles, etc.

Guest User Default Permissions

By default, guest users have LIMITED permissions:

Can read their own profile
Cannot enumerate other users or groups (can’t browse the directory)
Cannot read directory information (limited view)
Can be granted additional permissions through RBAC

You can customize guest permissions at: Entra ID > External Identities > External collaboration settings:

Most restrictive: Guest users have limited access to directory objects
Default: Guests can see members but not roles
Most inclusive: Guest users have the same access as members (NOT recommended)
LAB: Invite an External Guest User
  1. Go to Microsoft Entra ID > Users > New user > Invite external user
  2. Enter the external email address (e.g., partner@theircompany.com)
  3. Add a personal message: “Welcome to our Azure environment”
  4. Click “Properties” tab and fill in: Display name, Job title, Department
  5. Click “Assignments” tab — add them to a security group like “External-Vendors”
  6. Click “Review + invite” > “Invite”
  7. The guest will receive an email. Once they accept, their status changes from “Pending” to “Accepted”
  8. Verify: Go to Users > filter by User Type = Guest to see all guest users

Understanding RBAC (The Core of Azure Security)

Click to expand

Role-Based Access Control (RBAC) is how Azure controls WHO can do WHAT with WHICH resources. It is built on three core concepts:

The Three Components of Every RBAC Assignment

Component

Also Called

What It Is

Example

Security Principal

WHO

The identity getting access

User: john@company.com, Group: IT-Admins, Service Principal, Managed Identity

Role Definition

WHAT

Collection of allowed actions

Reader (view only), Contributor (manage everything except access), Owner (full control)

Scope

WHERE

The level at which access applies

Management Group, Subscription, Resource Group, or Individual Resource

Analogy / Memory Tip ANALOGY: Hotel Keycard System

Security Principal = The hotel guest (WHO). Role Definition = The type of keycard (WHAT doors it opens — pool, gym, restaurant, room). Scope = Which floor or building the keycard works on (WHERE). Just like a hotel keycard, an RBAC assignment is the COMBINATION of a person + keycard type + building. Without all three, access doesn’t work.

The Four Fundamental Built-in Roles

Azure has 300+ built-in roles, but these four are the foundation:

Role

Actions (What they CAN do)

Cannot Do

Use Case

Owner

Everything — full control over resources

Nothing — has all permissions

Subscription administrators, team leads who need to delegate access

Contributor

Create, update, delete ANY resource

Cannot assign roles to others, cannot manage access

Developers, engineers who need to deploy resources but shouldn’t control access

Reader

View all resources and their configurations

Cannot modify, create, or delete anything

Auditors, finance teams, stakeholders who need visibility

User Access Administrator

Manage user access to Azure resources

Cannot create or modify resources themselves

Security teams who manage RBAC without needing resource control

Exam Tip EXAM TIP: Owner = Contributor + User Access Administrator. This is a very common exam question. Also: Contributor CANNOT assign roles. If a question asks about giving someone the ability to assign roles, the answer is NEVER Contributor.

Scope Hierarchy — How Inheritance Works

Click to expand

RBAC follows a strict hierarchy. Permissions assigned at a higher level FLOW DOWN to all child levels:

Management Group (Highest)

└── Subscription └── Resource Group └── Resource (Lowest)

Key Rules:

Permissions are INHERITED downward (a Reader role at the Subscription level gives Reader access to ALL resource groups and resources in that subscription)
RBAC is ADDITIVE — if you have Reader at Subscription + Contributor at Resource Group, you get Contributor at that Resource Group (permissions are a UNION, not intersection)
Deny assignments OVERRIDE allow (but deny assignments can only be created by Azure Blueprints, not manually)
You CANNOT restrict inherited permissions at a lower scope — you can only ADD more permissions
LAB: Assign RBAC Roles at Different Scopes
  1. PART A: Assign Reader Role at Subscription Level
  2. Go to Subscriptions > select your subscription > Access control (IAM)
  3. Click “+ Add” > “Add role assignment”
  4. Search for “Reader” role > select it > click Next
  5. Click “+ Select members” > search for your test user > select them > click Select
  6. Click “Review + assign” twice
  7. PART B: Assign Contributor Role at Resource Group Level
  8. Go to Resource groups > select a resource group > Access control (IAM)
  9. Add role assignment: “Contributor” to the same test user
  10. PART C: Verify Effective Access
  11. Go to any resource inside that resource group > Access control (IAM) > Check access
  12. Search for the test user and examine their effective roles
  13. You should see BOTH Reader (inherited from subscription) AND Contributor (from resource group)
  14. The effective permission is Contributor at this scope because RBAC is additive

Understanding Role Definitions (JSON Structure)

Every role (built-in or custom) is defined as a JSON structure. Understanding this structure is essential:

Example: Contributor Role Definition

{

"Name": "Contributor",

"Id": "b24988ac-6180-42a0-ab88-20f7382dd24c",

"Description": "Lets you manage everything except access",

"Actions": [

"*" // ALL actions allowed

],

"NotActions": [

"Microsoft.Authorization/*/Delete", // Cannot delete role assignments

"Microsoft.Authorization/*/Write", // Cannot create role assignments

"Microsoft.Authorization/elevateAccess/Action"

],

"DataActions": [], // No data-plane access specified

"NotDataActions": [],

"AssignableScopes": ["/"] // Assignable everywhere

}

The key fields are:

Actions: Management-plane operations allowed (e.g., Microsoft.Compute/virtualMachines/start/action)
NotActions: Operations explicitly excluded from Actions
DataActions: Data-plane operations allowed (e.g., Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read)
NotDataActions: Data-plane operations explicitly excluded
AssignableScopes: Where this role can be used/assigned

Custom Roles

When built-in roles don’t meet your needs, you can create custom roles. Custom roles require Entra ID P1 or P2 (or Pay-As-You-Go/Enterprise subscription).

LAB: Create a Custom Role via Azure CLI
  1. Create a JSON file called custom-role.json with this content:
  2. {
  3. "Name": "VM Operator",
  4. "Description": "Can start, stop, and restart VMs but not create or delete them",
  5. "Actions": [
  6. "Microsoft.Compute/virtualMachines/start/action",
  7. "Microsoft.Compute/virtualMachines/restart/action",
  8. "Microsoft.Compute/virtualMachines/deallocate/action",
  9. "Microsoft.Compute/virtualMachines/read",
  10. "Microsoft.Network/*/read",
  11. "Microsoft.Resources/subscriptions/resourceGroups/read"
  12. ],
  13. "NotActions": [],
  14. "AssignableScopes": ["/subscriptions/YOUR-SUBSCRIPTION-ID"]
  15. }
  16. Run: az role definition create --role-definition custom-role.json
  17. Verify: az role definition list --custom-role-only true
  18. Assign it: az role assignment create --assignee user@domain.com --role "VM Operator" --resource-group myRG
Exam Tip EXAM TIP: Custom roles can be scoped to Management Groups, Subscriptions, or Resource Groups — but NOT individual resources. You can have a maximum of 5000 custom roles per tenant. Custom roles are defined in JSON and MUST include AssignableScopes.

What Is a Subscription?

Click to expand

A subscription is a logical container that serves as BOTH a billing boundary and an access control boundary. Every Azure resource must belong to exactly one subscription.

Key Facts About Subscriptions

A subscription is linked to exactly ONE Entra ID tenant (trust relationship)
A tenant can have MULTIPLE subscriptions
A subscription is the default scope for billing — all resources in a subscription are billed to that subscription’s payment method
RBAC assigned at the subscription level is inherited by ALL resource groups and resources within it
Subscriptions have limits/quotas (e.g., max 980 resource groups, max vCPU cores per region)

CRITICAL PRODUCTION FACT: Moving Subscriptions Between Tenants

When you transfer a subscription to a different Entra ID tenant, ALL RBAC role assignments are PERMANENTLY DELETED. All managed identities are disabled. All key vault access policies are removed. This is one of the most impactful operations in Azure and is a favorite exam question. Always plan for re-assignment of all permissions after a tenant transfer.

What Are Management Groups?

Click to expand

Management groups are containers ABOVE subscriptions that allow you to organize subscriptions into a hierarchy and apply governance (RBAC and Policy) at scale.

Analogy / Memory Tip Think of it this way:

Root Management Group (auto-created, cannot be deleted)

├── Production Management Group │ ├── Prod Subscription 1 │ └── Prod Subscription 2 ├── Development Management Group │ └── Dev Subscription └── Testing Management Group └── Test Subscription

Key Rules

Maximum depth: 6 levels (not counting the root)
Maximum 10,000 management groups per tenant
Each management group can have multiple children but only ONE parent
All subscriptions and management groups roll up to the root management group
The root management group CANNOT be moved or deleted
By default, only Global Administrator (after elevating access) can manage the root management group
LAB: Create a Management Group Hierarchy
  1. Go to portal.azure.com > search for “Management groups”
  2. If this is your first time, click “Start using management groups”
  3. Click “+ Add management group”
  4. Management group ID: “mg-production” (this cannot be changed later!)
  5. Display name: “Production”
  6. Click Save
  7. Create another: ID = “mg-development”, Name = “Development”
  8. Now move a subscription: Click on “Production” > “+ Add subscription” > select your subscription
  9. Apply a policy: Click on “Production” > “Policies” > Assign the “Allowed locations” policy
  10. This policy will now apply to ALL subscriptions under the Production management group
Exam Tip EXAM TIP: The Management Group ID is PERMANENT and cannot be changed after creation. The display name CAN be changed. This is a common trick question. Also, by default the root management group ID equals the Entra ID tenant ID.

What Is Azure Policy?

Click to expand

Azure Policy is a service that lets you create, assign, and manage rules (policies) that your Azure resources must follow. Unlike RBAC (which controls WHO), Policy controls WHAT CAN EXIST regardless of who is creating it.

Analogy / Memory Tip ANALOGY: City Building Codes

Imagine Azure Policy as the building codes for a city. RBAC decides who is allowed to build (licensed contractors). Policy decides what kind of buildings are allowed (no more than 10 stories, must have fire exits, must use approved materials). Even if you’re the most powerful contractor in town, you STILL have to follow building codes. Similarly, even an Owner in Azure must follow Policy rules.

Policy Concepts

Concept

What It Is

Example

Policy Definition

A single rule written in JSON

Require a tag on every resource group

Policy Initiative (Set)

A GROUP of related policy definitions bundled together

A “Compliance” initiative that includes: require tags + allowed locations + require encryption

Policy Assignment

Applying a policy/initiative to a specific SCOPE

Assign “Allowed Locations” policy to the Production subscription

Policy Parameters

Variables that make a policy reusable

The “Allowed Locations” policy has a parameter for which locations to allow

Compliance

Whether existing resources follow the policy

85% of resources are compliant, 15% need remediation

Policy Effects (MUST MEMORIZE)

Every policy definition has an “effect” that determines what happens when a resource doesn’t comply:

Effect

What Happens

When to Use

Deny

BLOCKS creation or modification of non-compliant resources

When you want to PREVENT something (e.g., block VMs in unapproved regions)

Audit

ALLOWS the resource but flags it as non-compliant in compliance reports

When you want visibility without blocking (discovery phase)

AuditIfNotExists

Checks if a related resource exists and audits if it doesn’t

Check if diagnostic settings are enabled on resources

Append

ADDS properties to a resource during creation/update

Auto-add a tag to resources that don’t have one

Modify

ADDS, UPDATES, or REMOVES properties/tags on existing resources

Enforce specific tag values or add managed identity to VMs

DeployIfNotExists (DINE)

Deploys a related resource if it doesn’t exist

Auto-deploy diagnostic settings when a VM is created

Disabled

Policy exists but is not enforced

Temporarily disable a policy without deleting the assignment

Exam Tip EXAM TIP: Policy evaluation order: Disabled > Append/Modify > Deny > Audit. This means: if a policy has Deny effect, the resource is blocked BEFORE Audit policies even evaluate. Also: DeployIfNotExists and Modify require a MANAGED IDENTITY for remediation (because they need to create/modify resources).
LAB: Create and Assign an Azure Policy
  1. PART A: Assign a Built-in Policy (Allowed Locations)
  2. Go to Policy service in the portal (search for “Policy”)
  3. Click “Assignments” > “Assign policy”
  4. Scope: Select your subscription (or a specific resource group to limit impact)
  5. Policy definition: Search for “Allowed locations” and select it
  6. Click “Parameters” tab: Select “East US” and “West US” as allowed locations
  7. Click “Review + create” > “Create”
  8. PART B: Test the Policy
  9. Try to create a resource (like a resource group) in “UK South”
  10. You should get a DENY error saying the location is not allowed by policy
  11. Now create the same resource in “East US” — it should succeed
  12. PART C: Check Compliance
  13. Go to Policy > Compliance
  14. You’ll see overall compliance state and which resources are non-compliant
  15. Non-compliant resources created BEFORE the policy was assigned will show as non-compliant but won’t be deleted (policies are NOT retroactive for Deny)
LAB: Create a Custom Policy (Require Tag on Resource Groups)
  1. Go to Policy > Definitions > “+ Policy definition”
  2. Definition location: Select your subscription
  3. Name: “Require CostCenter Tag on Resource Groups”
  4. Category: Create new > “Custom-Governance”
  5. In the policy rule, paste this JSON structure (conceptually):
  6. Rule: IF resourceType equals Microsoft.Resources/subscriptions/resourceGroups AND tag CostCenter does not exist THEN effect = Deny
  7. Click Save
  8. Now assign this policy to your subscription (same process as Part A above)
  9. Test: Try creating a resource group WITHOUT the CostCenter tag — it should be denied
  10. Test: Create a resource group WITH tag CostCenter=IT001 — it should succeed

PRODUCTION TIP: Policy Adoption Strategy

In real-world production environments, NEVER start with Deny. Follow this rollout: Phase 1 — Audit: Assign policies with Audit effect to understand current compliance state. Phase 2 — Remediate: Fix existing non-compliant resources. Phase 3 — Deny: Change the effect to Deny once you’re confident everything is compliant. This prevents accidentally blocking critical production deployments.

What Are Resource Locks?

Click to expand

Resource locks prevent accidental deletion or modification of critical Azure resources. Even users with Owner permissions cannot bypass a lock — they must first REMOVE the lock, then perform the action.

Two Types of Locks

Lock Type

Can Read?

Can Modify?

Can Delete?

Use Case

ReadOnly (CanNotModify)

Yes

No

No

Production databases, critical configs that should never change

Delete (CanNotDelete)

Yes

Yes

No

Production VMs that can be scaled/updated but never accidentally deleted

Important Lock Behaviors

Locks are INHERITED: A lock on a resource group applies to ALL resources inside it
Locks override RBAC: Even an Owner CANNOT delete a resource that has a Delete lock without removing the lock first
ReadOnly lock on a Storage Account blocks listing access keys (because listing keys is a POST operation, not GET)
ReadOnly lock on a resource group prevents creating NEW resources inside it (because create is a write operation)
Locks do NOT prevent data-plane operations (e.g., a Delete lock on a storage account doesn’t prevent someone from deleting blobs inside it)
LAB: Apply and Test Resource Locks
  1. Create a test resource group: “RG-LockTest”
  2. Create a storage account inside it
  3. Go to RG-LockTest > Locks > + Add
  4. Lock name: “prevent-deletion”, Lock type: Delete
  5. Click OK
  6. Now try to delete the resource group — you should get an error about the lock
  7. Now try to delete the storage account inside the RG — this should also fail (lock is inherited)
  8. Try modifying the storage account (e.g., change access tier) — this should succeed (Delete lock allows modifications)
  9. Now change the lock to ReadOnly and try modifying the storage account — it should fail
  10. To delete: First remove the lock (Locks > select lock > Delete), then delete the resource
Exam Tip EXAM TIP: The ReadOnly lock on a Storage Account blocking key listing is one of the MOST tested gotchas. Remember: Listing keys = POST action = blocked by ReadOnly. Also: Locks are about management-plane operations, NOT data-plane. A Delete lock on a SQL database prevents deleting the database but NOT deleting data inside it.

What Are Tags?

Click to expand

Tags are name-value pairs (metadata) you attach to Azure resources for organization, cost tracking, and automation. They are NOT security boundaries — they are organizational labels.

Key Tag Facts

Format: Key = Value (e.g., Environment = Production, CostCenter = IT001, Owner = john@company.com)
Maximum: 50 tags per resource, resource group, or subscription
Tag names are case-INSENSITIVE, tag values are case-SENSITIVE
Tags are NOT inherited from resource group to resources by default
Use Azure Policy to enforce tag inheritance
Tags appear in billing reports for cost allocation

LAB: Apply Tags and Enforce with Policy
  1. PART A: Manually Apply Tags
  2. Go to any resource > Tags
  3. Add: Name = Environment, Value = Production
  4. Add: Name = CostCenter, Value = IT001
  5. Click Save
  6. PART B: Apply Tags at Resource Group Level
  7. Go to your resource group > Tags
  8. Add: Name = Department, Value = Engineering
  9. Note: This tag does NOT automatically appear on resources inside the RG!
  10. PART C: Enforce Tag Inheritance with Policy
  11. Go to Policy > Assignments > Assign policy
  12. Search for “Inherit a tag from the resource group” and select it

  16. New resources in the RG will now automatically get the Department tag
Exam Tip EXAM TIP: Tags are NOT inherited by default — this is one of the top 5 most tested facts in AZ-104. You MUST use Azure Policy to enforce inheritance. The specific built-in policies are: “Inherit a tag from the resource group” and “Inherit a tag from the subscription.”

Scenario 1: New Company Onboarding

You are tasked with setting up Azure identity and governance for a new company with 200 employees across 3 departments (Engineering, Marketing, Finance) with Dev/Test and Production environments.

Scenario 2: External Vendor Access

Practice Questions

Click to expand

Q1: Your company requires that all virtual machines must be deployed only in the East US and West US regions. No user, regardless of their role, should be able to create VMs in other regions. What should you use?

A) RBAC custom role B) Azure Policy with Deny effect C) Resource Lock D) Management Group

Answer: B — Azure Policy with Deny effect enforces what resources CAN EXIST regardless of who creates them.

Q2: A user has the Reader role at the Subscription level and the Contributor role at a Resource Group level. What is their effective access at the Resource Group level?

A) Reader only B) Contributor only C) Reader + Contributor (both apply) D) No access

Answer: C — RBAC is additive. The user has the union of both roles at the RG level, which effectively gives them Contributor permissions.

Q3: You need to automatically add all users in the Sales department to a security group. The group membership should update without manual intervention. What type of group should you create?

A) Assigned security group B) Dynamic user security group C) Microsoft 365 group D) Distribution group

Answer: B — A dynamic user security group with rule (user.department -eq "Sales") will auto-update membership. Requires Entra ID P1.

Q4: You applied a ReadOnly lock on a storage account. A developer reports they cannot list the storage account access keys. Why?

A) They don’t have the right RBAC role B) ReadOnly lock blocks POST operations and listing keys is a POST action C) The lock is broken D) ReadOnly locks only block delete operations

Answer: B — Listing storage keys is a POST action, and ReadOnly locks block all write/POST operations. This is a well-known gotcha.

Q5: You created a budget of $500/month for your subscription. What happens when the spending reaches $500?

A) All resources are automatically stopped B) New deployments are blocked C) Nothing happens to resources — only alert notifications are sent D) The subscription is suspended

Answer: C — Budgets only send alerts. They do NOT stop, suspend, or block any resources.

Q6: You need to give a contractor the ability to manage virtual machines but NOT assign roles to other users. Which built-in role should you assign?

A) Owner B) Contributor C) User Access Administrator D) Virtual Machine Administrator Login

Answer: B — Contributor can manage all resources but cannot assign roles. Owner can do both.

Q7: You applied the tag Department=IT to a resource group. Do the resources inside the resource group automatically get this tag?

A) Yes, tags are always inherited B) No, tags are never inherited C) No, but you can use Azure Policy to enforce inheritance D) Yes, but only for new resources

Answer: C — Tags are NOT inherited by default. Use the built-in policy “Inherit a tag from the resource group” to enforce this.

Q8: Your organization transfers a subscription to a new Entra ID tenant. What happens to the existing RBAC role assignments?

A) They are transferred with the subscription B) They are permanently deleted C) They are temporarily disabled D) They remain but become inactive

Answer: B — ALL RBAC role assignments are permanently deleted when a subscription is transferred to a different tenant.
