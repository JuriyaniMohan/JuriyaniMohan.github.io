Chapter 01

What is Azure Backup & Why It Exists

Azure Backup is a fully managed, cloud-native backup service that replaces traditional on-premises backup infrastructure (tape drives, backup servers, SAN snapshots) with a simple, scalable, pay-as-you-go solution. Instead of managing your own backup servers, storage, and rotation schedules, Azure handles everything — you just define policies and Azure does the rest.

Think of it this way: in the old world, backing up meant buying expensive backup software (Veritas, Commvault), dedicated backup servers, tape libraries, and hiring someone to manage tape rotation. Azure Backup eliminates all of that.

Problems Azure Backup Solves

Data Loss: Accidental deletion, ransomware, corruption — backup gives you a time machine to roll back.

Compliance Requirements: Many regulations (HIPAA, GDPR, MAS in Singapore) mandate data retention for years.

Disaster Recovery: If an entire region goes down, your backups in another region let you restore.

Operational Errors: A developer runs DROP TABLE users; in production. Backup saves the day.

Infrastructure Complexity: No backup servers to manage, patch, or monitor.

Key Benefits

Zero-infrastructure: No backup servers needed. Fully PaaS.

Application-consistent: Uses VSS (Windows) or pre/post scripts (Linux) to ensure clean backups.

Unlimited scale: No limits on backup data size. Storage grows automatically.

Encryption at rest and in transit: AES-256 encryption always.

Geo-redundant storage: Backups replicated to paired region (GRS/RA-GRS).

Soft delete: Deleted backups retained for 14 extra days — ransomware protection.

Azure Backup = "Backup as a Service" — Mnemonic SECURE: Scalable, Encrypted, Compliance-ready, Unlimited storage, Resilient (geo-redundant), Effortless (no infra to manage).
Chapter 02

Azure Backup Service for VMs

Fig 1 — VM backup is a two-phase process: fast local snapshot, then vault transfer for long-term storage.

Common Issues with Azure VM Backup

VM Agent not running: The Azure VM Agent must be healthy. If it crashes or is missing (custom images), backups fail silently.

Extension failure: The backup extension may fail if NSG rules block outbound traffic, or antivirus software interferes.

Disk limits: Maximum 32 disks per VM. NFS/network drives are NOT backed up — only attached Azure disks.

Linux consistency: Without pre/post scripts, Linux backups are only crash-consistent, not application-consistent. MySQL/PostgreSQL need custom scripts to freeze I/O.

Locked resource groups: Azure creates a restore point collection in a managed RG. A lock on that RG breaks backup cleanup and eventually stops backups.

Snapshot tier cost: Snapshots for instant restore (1-5 days) are charged separately. This often-overlooked cost can be significant.

Large disk first backup: A 32 TB disk takes hours for the initial full backup. Plan for this.

"Snap then Ship" — Phase 1 = Snap (local snapshot, fast restore). Phase 2 = Ship (to vault, long-term). Restore from snapshot tier = minutes. Restore from vault = hours.
Chapter 03

Backup Policies

A backup policy defines WHEN backups happen and HOW LONG they're kept. Every backup item must be associated with exactly one policy.

Components of a Backup Policy

Schedule (Frequency): Hourly (every 4/6/8/12 hrs — Enhanced), daily, or weekly.

Retention layers: Daily (e.g., 30 days) → Weekly (e.g., 12 weeks) → Monthly (e.g., 12 months) → Yearly (e.g., 10 years). Each layer keeps one representative backup point.

Snapshot retention: How many days to keep the local snapshot for instant restore. Standard: 1-5 days. Enhanced: 1-30 days. More days = faster restore, higher cost.

Tiering policy: When to move older recovery points to Archive tier for ~99% cost savings (minimum 180-day commitment).

Standard Policy

DEFAULT 1 BACKUP/DAY

One backup per day. Snapshot 1-5 days. Full retention layers. Good for most workloads with RPO of 24 hours.

Enhanced Policy

HOURLY UP TO 6/DAY ZONE-PIN

Multiple backups per day (every 4-12 hrs). Snapshot up to 30 days. Supports Trusted Launch VMs, Ultra SSD, zone-pinned restore. RPO as low as 4 hours.

"Standard = Simple, Enhanced = Enterprise" — Exam keyword: "multiple backups per day" or "hourly backup" or "RPO < 24 hours" → Always Enhanced Policy.
Chapter 04

Vaults — Types & Differences

A vault is the central storage and management entity for backups. Think of it as a secure safe-deposit box in the cloud. Azure has two vault types serving different workloads.

Fig 2 — RSV is the veteran (VMs, on-prem, ASR). Backup Vault is the modern option (PaaS, disks, blobs, AKS).
⚠️ EXAM TRAP — VAULT STORAGE REDUNDANCY
You can only set the storage redundancy (LRS/GRS/ZRS) before the first backup item is registered. Once any backup is configured, you CANNOT change redundancy. Plan before you start.
"RSV = VMs & Veterans, BV = Blobs & New Blood" — If it involves a VM or existed before 2021 → RSV. If it's a newer PaaS service (managed disks, blobs, PostgreSQL, AKS) → Backup Vault.
Chapter 05

RTO & RPO — The Two Sacred Numbers

Fig 3 — RPO looks backward (data loss). RTO looks forward (downtime).

RPO — Recovery Point Objective

"How much data can you afford to lose?" Measured in time. RPO = 4h means you accept losing the last 4 hours of data. This dictates backup frequency. RPO = 0 requires synchronous replication (not backup).

RTO — Recovery Time Objective

"How long can your business be down?" Maximum acceptable downtime. RTO = 2h means the system must be back within 2 hours. RTO = 0 requires active-active architecture with auto failover.

Chapter 06

Business Continuity Center (BCC)

The Azure Business Continuity Center is the unified management portal for all backup and DR operations across your entire Azure estate. It replaced the fragmented experience of checking individual vaults, giving you a single pane of glass across all subscriptions.

What BCC Shows You

Overview: Total protected items, vault count, backup health, ASR health — across ALL subscriptions at once.

Security posture: Resources lacking backup, soft delete status, MUA status, immutable vault status. A security "score" for your backup estate.

Protection coverage: % of VMs, SQL DBs, file shares, disks that are backed up vs. unprotected. Gaps highlighted with recommended actions.

Backup jobs: Centralized view of all running, completed, and failed jobs across every vault.

Compliance: Azure Policy compliance for backup — are all VMs covered? BCC shows violations.

ASR dashboard: Replication health, failover readiness, test failover status.

Vault management: Create vaults, configure policies, manage registrations — all from one place.

💡 BCC vs INDIVIDUAL VAULT VIEWS
BCC doesn't replace individual vault blades — it aggregates them. BCC = executive dashboard (monitoring, governance). Individual vault = engineer's workbench (configuration, troubleshooting).
"BCC = Boss's Command Center" — The control tower that sees all backup planes across all runways (vaults). For the exam, know it exists and what it shows.
Chapter 07

Azure Site Recovery (ASR) — Deep Dive

Azure Site Recovery is NOT backup — it's disaster recovery. Backup creates point-in-time copies. ASR creates a live, near-real-time replica of your infrastructure in another region so you can failover in minutes if the primary region goes down.

Backup protects against "oops I deleted it." ASR protects against "the whole region is gone."

What ASR Does

Continuous replication: Replicates VM disks asynchronously to target region. Every write is captured.

Crash-consistent snapshots: Every few minutes — disk state as if power was pulled.

App-consistent snapshots: Every 1-4 hours — flushes memory and in-flight I/O.

Automated failover: Recovery plans failover dozens of VMs with scripted ordering (DB → App → Web).

Test failover: Spin up replicas in isolated network without affecting production. Do this quarterly.

Failback: After primary recovers, replicate back and switch traffic home.

When to Use ASR

Region-level disasters: Entire Azure region down → failover to paired region.

Compliance mandates: Regulations requiring tested DR plan with < 1h RTO.

Mission-critical workloads: ERP, banking, healthcare that cannot tolerate hours of downtime.

Migration: Replicate on-prem (VMware/Hyper-V/physical) to Azure — migration tool.

Azure-to-Azure DR: Most common — replicate between Azure regions.

ASR Limitations & Complications

RPO ≈ 15-30 minutes (not zero): Asynchronous replication means some in-transit writes are lost during real failover.

IP address changes: Failover VMs get new IPs. Hardcoded IPs break. Always use DNS + Traffic Manager/Front Door.

VM type restrictions: Some VM types (Gen2, Ultra Disks, ephemeral OS disks) may have restrictions. Check the support matrix.

Network not replicated: You must pre-configure VNets, NSGs, public IPs, LBs in target region. ASR only replicates disk data.

Cost: ~$25/month per protected instance + replicated storage + DR compute when running.

No shared disk support: VMs using shared disks (clusters) are not supported.

Capacity risk: During real regional disaster, target region may lack capacity. Use Capacity Reservations.

Recovery plan complexity: Multi-tier apps need carefully ordered plans with automation scripts. Time-consuming to design and test.

DNS propagation: Traffic Manager/DNS updates add minutes to effective RTO.

✅ ASR BENEFITS
Near-zero RTO (minutes) • RPO ~15 min • Automated recovery plans • Test failover without production impact • Supports Azure-to-Azure, VMware-to-Azure, Hyper-V-to-Azure, Physical-to-Azure • BCC monitoring • Azure Automation runbook integration.
"Backup = Time Machine (go back), ASR = Mirror Machine (live copy)" — You need BOTH. Backup protects data. ASR protects infrastructure.
🔧 HOW TO DO PROPER SITE RECOVERY — STEP BY STEP
1. Pre-requisites: Ensure target region VNets, subnets, NSGs exist. Reserve capacity if mission-critical. Configure Azure Traffic Manager or Front Door for DNS failover.

2. Enable replication: RSV → Site Recovery → Enable replication → Select source VMs → Choose target region, VNet, subnet, storage → Configure replication policy (crash/app-consistent frequency).

3. Customize target settings: Map source NICs to target subnets. Configure target VM sizes (can be different). Set up target availability sets/zones. Assign target public IPs and LBs.

4. Create recovery plans: Group VMs by tier (Group 1: DB, Group 2: App, Group 3: Web). Add pre/post scripts (Azure Automation runbooks) for each group — e.g., pre-script to stop app before DB failover, post-script to update connection strings.

5. Test failover (quarterly!): Recovery plan → Test failover → Select recovery point → Choose isolated test network → Verify all VMs start and apps work → Clean up test VMs.

6. Document and drill: Document the procedure. Time each step. Compare against RTO target. Train the ops team. Repeat quarterly.

Chapter 09

Same-Region DR — When You Can't Leave

In Singapore, data sovereignty laws may prevent replicating to another country/region. Here's how to achieve DR within a single Azure region:

Option 1: Availability Zones + Zone-to-Zone ASR

BEST OPTION 99.99% SLA

Southeast Asia (Singapore) has 3 Availability Zones — physically separate data centers with independent power, cooling, networking, connected by low-latency fiber (< 2ms).

Zone-to-Zone ASR: Replicate VMs from Zone 1 to Zone 3 within the same region. If Zone 1 goes down, failover to Zone 3 — still in Singapore, still compliant.

Option 2: Zone-Redundant Architecture

Deploy across all 3 zones with a load balancer natively. No failover needed — if one zone fails, others absorb. Requires zone-redundant VMSS, Standard LB, ZRS storage, zone-redundant SQL.

Option 3: ZRS Vault + Backup

If ASR isn't feasible, use Azure Backup with ZRS vault. Backups spread across 3 zones. Slower recovery (hours vs minutes) but data survives zone failure.

Option 4: Paired Region with Legal Agreement

Negotiate with legal/compliance to allow replication to Singapore ↔ Hong Kong (Azure's paired regions) with contractual controls. Gives true geographic diversity while remaining in APAC.

"Can't Leave? Go Zonal!" — Data sovereignty → Availability Zones. Zones = different buildings, same city. Regions = different cities.

Chapter 11

How to Backup VMs, Storage & Data

Backing Up Azure VMs

  1. Create RSV in same region as VM. Set storage redundancy (LRS/GRS/ZRS) BEFORE first backup item.
  2. Define Backup Policy — schedule, retention layers, snapshot retention, tiering rules.
  3. Enable Backup — VM → Operations → Backup → Select vault → Select policy → Enable. Extension auto-installs.
  4. Monitor — First backup is full, subsequent are incremental. Monitor in Backup Center/BCC.
  5. Restore — Options: Create new VM, replace existing disks, restore individual disks, or file-level recovery (mount as drive).

Backing Up Azure Blobs

BACKUP VAULT

Operational: Continuous point-in-time restore (any second, last 1-365 days). Same storage account only. Cheapest.

Vaulted: Discrete recovery points in Backup Vault. Supports cross-region restore with GRS. Better for compliance.

Backing Up Managed Disks

BACKUP VAULT

Incremental snapshots (first full, then changes only). Stored in your subscription. Define frequency and retention via policy. Supports cross-region copy. Useful for disks not attached to VMs.

Backing Up SQL / SAP HANA in Azure VMs

RSV STREAM-BASED

Auto-discovers SQL instances in registered VMs. Uses SQL's native backup stream but sends output to vault. Supports full, differential, and log backups. Transaction log backups every 15 minutes = RPO of 15 minutes for SQL databases. SAP HANA uses certified Backint interface.

Backup location cheat sheet: VM → RSV. Disk → Backup Vault. Blob → Backup Vault. Azure Files → RSV. SQL in VM → RSV. PostgreSQL → Backup Vault. AKS → Backup Vault. On-prem → RSV (via MARS/MABS/DPM).
★ Chapter 12 — KEY SECTION

MARS, MABS & DPM — Complete Breakdown

These three agents/products handle on-premises and hybrid backup to Azure. Understanding their differences is critical for the AZ-104 exam and hybrid architecture design. They overlap — but each has a distinct purpose.

AGENT-BASED · LIGHTWEIGHT · WINDOWS ONLY

MARS — Microsoft Azure Recovery Services Agent

What it is: A lightweight agent installed directly on a Windows machine (physical or VM, on-prem or Azure). Backs up files, folders, and System State directly to RSV. No intermediate server needed.

What it CAN backup: Files & folders on Windows Server/client machines. Windows System State (registry, boot files, COM+, AD if DC).

What it CANNOT backup:

  • ❌ Full machine/bare-metal (no full VM restore from scratch)
  • ❌ Application-aware (no SQL, Exchange, SharePoint — no VSS writer integration)
  • ❌ Linux (Windows only)
  • ❌ Azure VM disks (use native VM backup)
  • ❌ Network shares or NAS (only local volumes)

How it works: Install → Register with RSV (vault credentials + passphrase) → Schedule backup & retention → Agent compresses + encrypts → Sends to vault over HTTPS.

Key limits: Max 3 backups/day. Max 54 recovery points. Passphrase is YOUR responsibility — lose it and Microsoft cannot recover your data. Uses ~6% CPU per core during backup.

"MARS = My files And Recovery of System state" — Files + folders + system state only. No apps, no Linux, no bare-metal. Think: smart robocopy to the cloud.
DEDICATED SERVER · APPLICATION-AWARE · FREE

MABS — Microsoft Azure Backup Server

What it is: A full backup server product (free with Azure subscription). Install on a dedicated Windows Server. Acts as centralized backup server protecting multiple machines and apps, then tiers data to Azure.

What it CAN backup (everything MARS does, plus):

  • ✅ Full machine/bare-metal recovery (BMR)
  • ✅ Hyper-V VMs and VMware VMs
  • ✅ SQL Server databases (application-consistent via VSS)
  • ✅ Exchange Server databases
  • ✅ SharePoint farms
  • ✅ Windows client machines
  • ✅ Linux machines (file-level)

What it CANNOT do:

  • ❌ Tape backup (removed in MABS v3+)
  • ❌ Oracle database backup

Architecture: Disk-to-Disk-to-Cloud (D2D2C). MABS stores backups on local disk first (fast restore), then tiers to RSV for long-term. Needs a protection agent on each protected server. MABS requires its own SQL instance (Express auto-installed or bring your own).

Licensing: Free with Azure subscription. No System Center license needed.

"MABS = Mini Application Backup Server" — Free mini-DPM. Key differentiator from MARS: application-aware (SQL, Exchange) + bare-metal + Linux. Key differentiator from DPM: no tape, no Oracle, no System Center license.
SYSTEM CENTER · ENTERPRISE · TAPE + ORACLE

DPM — Data Protection Manager (System Center)

What it is: Enterprise-grade backup product, part of System Center suite. Everything MABS does plus tape and Oracle. Integrates with SCOM, SCCM, SCVMM.

What it adds over MABS:

  • ✅ Tape backup (D2D2T — Disk to Disk to Tape) for air-gapped compliance
  • ✅ Oracle databases
  • ✅ DPM-to-DPM chaining (replication across data centers)
  • ✅ System Center integration (SCOM monitoring, SCCM deployment)

Licensing: Requires System Center license ($$). This is the key cost difference from MABS.

When DPM over MABS: Tape for compliance (air-gapped storage), Oracle databases, existing System Center investment, multi-site DPM-to-DPM replication.

"DPM = Daddy of Protection Management" — The full workshop. Exam triggers: "tape" → DPM. "System Center" → DPM. "No additional license" → MABS. "Oracle" → DPM.

Real-World Usage Scenarios

Where MARS is Used

Small offices: 5 Windows file servers need documents backed up to Azure. Install MARS on each, schedule, done.

Individual machines: Critical files from developer workstations.

Domain Controller System State: AD recovery from DC system state backup.

Azure VM file-level: Specific folders inside an Azure VM (not whole VM).

Where MABS is Used

SMBs going cloud-first: 20 servers, SQL databases, Hyper-V VMs — centralized backup without System Center cost.

Hybrid environments: Local disk for fast restore + Azure vault for long-term.

SQL/Exchange protection: Application-consistent backups without DPM licensing cost.

VMware/Hyper-V VMs: Hypervisor-level VM backup.

Where DPM is Used

Enterprise data centers: 500+ servers with tape libraries and System Center.

Air-gapped compliance: Financial services, government mandating offline tape copies.

Oracle databases: The only Microsoft backup tool supporting Oracle.

Multi-site DR: DPM-to-DPM chaining across data centers → then to Azure.

⚠️ EXAM TRAPS FOR MARS/MABS/DPM
Trap 1: "Backup SQL on-premises to Azure, no additional license cost" → MABS (DPM needs System Center license).

Trap 2: "File-level backup of Windows server with minimal infrastructure" → MARS (no dedicated server needed).

Trap 3: "Backup to tape for regulatory compliance" → DPM (MABS removed tape support).

Trap 4: "Can MARS backup Linux?" → No. MARS is Windows only. Linux files on-prem → MABS.

Trap 5: "MABS stores data locally before sending to Azure" → True. D2D2C. MARS sends directly to cloud.
The Ultimate Video Game Memory Trick:

🟠 Level 1 — MARS (Beginner): Files only. No server. Direct to cloud. Windows only. Free.
🟢 Level 2 — MABS (Intermediate): + Apps + VMs + BMR + Linux. Needs server. Cloud-first. Free.
🟣 Level 3 — DPM (Boss Level): + Tape + Oracle + Multi-site. Needs System Center $$. Enterprise.

Each level includes everything from the previous level plus more. MARS ⊂ MABS ⊂ DPM.
Chapter 13

Architect's Decision Framework

  1. What's your RPO? RPO 24h = daily backup. RPO 4h = Enhanced policy. RPO ~0 = ASR or sync replication.
  2. What's your RTO? RTO 24h = vault restore. RTO 4h = snapshot + automation. RTO minutes = ASR auto failover.
  3. Where does the workload run? Azure VM → native backup. On-prem files → MARS. On-prem apps → MABS/DPM. PaaS → Backup Vault.
  4. Data sovereignty? Must stay in-country → LRS/ZRS + zone-to-zone ASR. Can cross-border → GRS + cross-region ASR.
  5. Retention requirement? 30 days → standard. 7 years → yearly retention + Archive tier. 10+ years → immutable vaults.
  6. Budget? Tight → backup + LRS. Medium → backup GRS + ASR for critical VMs. Full → ASR all workloads + capacity reservations.
  7. TEST YOUR RECOVERY! Schedule quarterly test restores and ASR test failovers. Automate with Azure DevOps. Time the recovery. Compare against RTO/RPO.
🏁 ARCHITECT'S FINAL RULES
Rule #1: A backup that hasn't been tested is not a backup — it's a hope. Test monthly. Document the procedure. Time the recovery.

Rule #2: Enable Soft Delete + MUA + Immutable Vaults. If ransomware compromises your admin account, these are your last defense.

Rule #3: Azure Backup is backup. ASR is DR. You need BOTH. Backup = "oops I deleted it." ASR = "the region is gone." Different problems, complementary solutions.
Master Summary — "VAULT MARS":
