Containers & Azure Container Apps

From an Architect's Lens — AZ-104 Day 4, Part 1
Compute Domain • 20-25% Exam Weight

🐳 What Are Containers?

The Problem They Solve

Imagine you're a developer at a bank. Your app runs perfectly on your laptop, but when the ops team deploys it to production, it crashes — different OS version, different Python library, missing dependency. This is the classic "it works on my machine" problem. Containers solve this by packaging your application code, its runtime, libraries, and configuration into a single, portable unit that runs identically everywhere.

What Exactly Is a Container?

A container is a lightweight, isolated execution environment that shares the host operating system's kernel. Unlike a VM that runs a full guest OS, a container only includes the application and its dependencies. Think of it this way:

🏗️ Architect's Analogy
A VM is like renting an entire apartment — you get your own kitchen, bathroom, plumbing, electricity. A Container is like renting a desk in a co-working space — you bring your laptop and setup, but share the building's infrastructure. Much cheaper, faster to set up, and easier to move.

Container Image vs Running Container

A container image is a read-only template — like a class in OOP. A running container is an instance of that image — like an object created from that class. Images are built from a Dockerfile and stored in a container registry (like Azure Container Registry, Docker Hub).

Dockerfile → docker build → Container Image → Push to ACR → Run on ACI/ACA/AKS

Core Concepts to Lock In

  • Ephemeral by nature — containers can be destroyed and recreated instantly. Never store critical data inside a container filesystem.
  • Immutable — you don't patch a container. You build a new image and redeploy.
  • Stateless by default — if your app needs persistent data, you mount external volumes (Azure Files, managed disks).
  • Portable — same image runs in dev, staging, production, any cloud.
  • Microsecond startup — containers start in seconds vs minutes for VMs.
📝 Exam Tip
The AZ-104 expects you to know WHEN to use containers vs VMs — not how to write Dockerfiles. Focus on use-case decisions, not Docker internals.

🧠 Memory Mnemonic: "CLIPS"

Containers are: Consistent (same everywhere) • Lightweight (no OS overhead) • Immutable (replace, don't patch) • Portable (any cloud) • Stateless (use external storage)

⚡ VM vs Containers — The Architect's Decision Framework

Why This Matters

As an architect, you'll get asked "should we containerize this?" on every project. The answer isn't always "yes." Understanding the trade-offs is what separates an administrator from an architect.

CriteriaVirtual MachinesContainers
IsolationFull hardware-level isolation via hypervisor. Each VM runs its own OS kernel.Process-level isolation. Shares host OS kernel. Lighter but less isolated.
Startup TimeMinutes (boot entire OS)Seconds or sub-second
SizeGBs (includes full OS)MBs (just app + dependencies)
Density~10-20 VMs per host~100-1000 containers per host
StateNaturally stateful (data on disk persists)Ephemeral by default — need external volumes for persistence
PatchingPatch in place (apt update, Windows Update)Never patch — rebuild image and redeploy
OS SupportAny OS (Windows, Linux, custom)Linux containers most common; Windows containers supported but heavier
LicensingNeed OS licenses (Windows Server, RHEL)No guest OS license needed for Linux containers
Best ForLegacy apps, Windows-only workloads, apps needing kernel-level access, databasesMicroservices, APIs, batch jobs, CI/CD pipelines, stateless web apps

When to Choose VMs — The Non-Negotiables

  • Legacy applications that can't be refactored — monolithic .NET Framework apps, SAP systems
  • Specific OS or kernel requirements — custom kernel modules, GPU passthrough configurations
  • Compliance requirements mandating full isolation — some financial regulators require hypervisor-level separation
  • Stateful workloads — SQL Server, Oracle DB, Active Directory Domain Controllers
  • Windows-heavy shops — Windows containers exist but are limited and larger (~3-4 GB base image)

When to Choose Containers

  • Microservices architectures — each service in its own container, independently deployable
  • CI/CD pipelines — build once, test once, deploy everywhere
  • High-density workloads — run hundreds of instances on same hardware
  • Rapid scaling — add/remove instances in seconds, not minutes
  • Dev/test environments — spin up identical environments instantly
  • Event-driven processing — process a queue message, scale to zero when done
📝 Exam Tip
The exam will present scenarios and ask you to choose between VM and container. Key signals: "minimize infrastructure management" → containers. "Legacy Windows app that can't be modified" → VM. "Scale rapidly to handle bursts" → containers. "Run SQL Server with persistent storage" → VM.
🏗️ Architect's Real-World Insight
In production at scale (10 years AWS/Azure experience speaking), I've found the sweet spot is often both. Databases and legacy systems on VMs, application microservices in containers. Don't force-fit everything into containers — it's not a religious decision, it's an engineering one.

🧠 Memory Mnemonic: "VM = VISA, Container = CASH"

VM (VISA): Verbose, Isolated, Stateful, Any-OS
Container (CASH): Compact, Agile, Stateless, High-density

📦 Azure Container Instances (ACI)

What Is ACI?

Azure Container Instances is the simplest, fastest way to run a container in Azure. No VM provisioning, no cluster management, no orchestration overhead. You give Azure an image, specify CPU and memory, and it runs. Think of it as "serverless containers" at the most fundamental level.

The Problem ACI Solves

Before ACI, running a single container in Azure meant: (1) create a VM, (2) install Docker, (3) pull your image, (4) run the container, (5) manage the VM's OS patches, networking, etc. ACI eliminates all of that. You go from image → running container in seconds.

Key Features & Characteristics

  • Per-second billing — you pay only for the CPU and memory allocated, billed from when image pull starts until container stops
  • Fast startup — containers start in seconds, no VM boot time
  • Hyper-V isolation — each container group gets its own Hyper-V isolated kernel (stronger than typical container isolation)
  • Supports Linux AND Windows containers — but Windows containers have limitations (see below)
  • Configurable CPU/Memory — you specify the exact vCPU and GiB you need
  • Persistent storage via Azure Files — mount an Azure File Share for data that needs to survive container restarts
  • VNet integration — deploy into an Azure Virtual Network for private communication
  • Restart policies — Always, OnFailure, Never
  • No built-in autoscaling — if you need 5 instances, you create 5 separate container instances
  • No built-in load balancing — each instance gets its own IP

When to Use ACI — Use Cases

  • Batch processing jobs — run a data transformation, then stop and pay nothing
  • CI/CD build agents — spin up a build container, run tests, destroy
  • Quick prototyping — test a container image without setting up infrastructure
  • AKS burst overflow — AKS can use ACI as "virtual nodes" to handle overflow traffic
  • Scheduled tasks — run a report generator every night via Logic Apps + ACI
  • Sidecar containers — deploy logging/monitoring agents alongside your app in a container group

Resource Configuration

Each container in ACI has two resource settings:

  • Resource Request — the guaranteed minimum CPU/memory allocated
  • Resource Limit — the maximum CPU/memory the container can use
⚠️ Critical Exam Point
If you do NOT specify a resource limit, the container's maximum resource usage equals its resource request. You cannot dynamically change resource limits on a running container — you must delete and recreate the container group.

Networking Options

OptionDescriptionUse Case
PublicContainer gets a public IP and FQDNInternet-facing APIs, demo apps
PrivateDeploy into a VNet subnet (delegated)Internal microservices, backend processing
NoneNo network interfaceBackground jobs with no inbound traffic

CLI Quick Reference

# Create a simple public container instance az container create \ --resource-group myRG \ --name mycontainer \ --image mcr.microsoft.com/azuredocs/aci-helloworld:latest \ --cpu 1 --memory 1.5 \ --ports 80 \ --dns-name-label myapp-demo \ --restart-policy Always # View running container logs az container logs --resource-group myRG --name mycontainer # Attach to a running container's console az container attach --resource-group myRG --name mycontainer # Deploy into a VNet (private) az container create \ --resource-group myRG \ --name private-container \ --image myacr.azurecr.io/myapp:v1 \ --vnet myVNet --subnet aci-subnet \ --cpu 2 --memory 4
📝 Exam Tip
ACI persistent storage ONLY supports Azure File Shares — not Blob Storage, not Table Storage, not managed disks. This is a frequently tested point.

🧠 Memory Mnemonic: ACI = "A Container Instantly"

Simple. Fast. No cluster. Per-second billing. File Shares for persistence. No autoscale — you manage instance count yourself.

🔗 Azure Container Groups

What Is a Container Group?

A container group is a collection of containers that get scheduled on the same host machine. They share the same lifecycle, local network, and storage volumes. Think of it as a Kubernetes "Pod" — but in ACI.

Why Container Groups Exist

Sometimes you need containers that work together closely — like your main app container plus a logging sidecar, or a web server plus a data sync container. Deploying them in a container group ensures they:

  • Share the same network namespace — they can communicate via localhost
  • Share the same lifecycle — they start and stop together
  • Share mounted volumes — both can read/write the same Azure File Share
  • Are co-located — same host, minimal latency between them

Critical Rules for Container Groups

RuleDetails
Multi-container groups: Linux ONLYWindows containers only support single-container groups. If exam asks "which can be in a container group?" — look for Linux OS.
Resource allocation is at group levelTotal CPU/memory is the SUM of all containers in the group. Individual containers get their configured request/limit within that pool.
Network: shared IP, unique portsAll containers share one IP. Each container must use different ports. They talk to each other via localhost.
Lifecycle: all or nothingYou can't restart a single container — the entire group restarts. Can't add/remove containers from a running group.
Deployment methodsARM templates, YAML files, or Azure CLI. YAML is recommended for multi-container groups.

Sidecar Pattern — The Key Architecture Pattern

The most common container group pattern is the sidecar. Your main application container runs alongside helper containers that provide cross-cutting concerns:

  • Logging sidecar — collects and ships logs to a central system
  • Monitoring sidecar — exports metrics to Azure Monitor
  • Proxy sidecar — handles SSL termination or authentication
  • Data sync sidecar — periodically pulls config from a remote source

YAML Deployment Example

# container-group.yaml apiVersion: 2021-09-01 name: myContainerGroup location: eastus properties: containers: - name: webapp properties: image: nginx:latest ports: - port: 80 resources: requests: cpu: 1.0 memoryInGb: 1.5 volumeMounts: - name: shared-data mountPath: /var/log/nginx - name: log-shipper properties: image: fluentd:latest resources: requests: cpu: 0.5 memoryInGb: 0.5 volumeMounts: - name: shared-data mountPath: /fluentd/log volumes: - name: shared-data azureFile: shareName: myshare storageAccountName: mystorageacct storageAccountKey: "xxxxx" ipAddress: type: Public ports: - protocol: TCP port: 80 osType: Linux # Deploy: az container create --resource-group myRG --file container-group.yaml
📝 Exam Tip — Frequently Tested
Q: "Which containers can be deployed to a container group?" → Only Linux containers support multi-container groups. Windows containers = single container only per group.

Q: "A container group has Container A (request: 2 CPU, limit: 4 CPU) and Container B (request: 1 CPU, limit: 2 CPU). What is the total CPU for the group?" → The group total is the SUM of individual requests (3 CPU). Limits define how much each container can burst within the group's allocation.

🧠 Memory Mnemonic: Container Group = "Pod in ACI"

S.L.I.N. — Shared lifecycle, Localhost networking, IP is shared, No Windows multi-container. Remember: Groups = Pods, Sidecars = Helpers.

🚀 Azure Container Apps (ACA)

What Is ACA?

Azure Container Apps is a fully managed, serverless container platform built on top of Kubernetes (but you never touch K8s). It's designed for microservices and event-driven workloads. Microsoft manages the infrastructure, scaling, networking, and service discovery — you just deploy your containers.

The Problem ACA Solves

AKS gives you full Kubernetes power but requires a team to manage clusters, node pools, upgrades, and networking. ACI is too simple — no autoscaling, no service discovery, no traffic splitting. ACA sits in the sweet spot: Kubernetes capabilities without Kubernetes complexity.

🏗️ Architect's Perspective
Think of ACA as "managed Kubernetes without the PhD." In my 10 years, most teams don't need full K8s — they need auto-scaling, revisions, traffic splitting, and event triggers. ACA gives you that at 20% of the operational overhead.

Key Features

  • Scale to zero — no traffic = no running instances = no cost (Consumption plan)
  • KEDA-based autoscaling — scale based on HTTP traffic, queue length, CPU, memory, custom metrics
  • Revisions — deploy new versions as "revisions." Split traffic between revisions (canary, blue-green)
  • Dapr integration — built-in service-to-service invocation, pub/sub, state management
  • Managed identity — authenticate to Azure services without credentials
  • Built-in ingress — HTTPS endpoints with custom domains, no need for separate load balancer
  • Container Apps Environment — a secure boundary for a group of container apps (like a namespace)
  • Jobs — run on-demand, scheduled (cron), or event-driven tasks
  • Linux only — does not support Windows containers

Scaling in ACA

Event Source (HTTP, Queue, Timer) → KEDA Detects → Scale Up Replicas → Traffic Served → Event Stops → Scale to Zero

Traffic Splitting — Blue/Green & Canary

# Split traffic: 80% to current, 20% to new revision az containerapp ingress traffic set \ --name myapp \ --resource-group myRG \ --revision-weight myapp--rev1=80 myapp--rev2=20

📝 Exam Tip
ACA supports Linux containers only. If a question mentions a Windows container needing autoscaling and event-driven triggers, ACA is NOT the answer — you'd need AKS with Windows node pools or App Service for Containers. Also: ACA supports "scale to zero" for HTTP — AKS does NOT natively (requires KEDA add-on).
☁️ AWS Comparison
ACA ≈ AWS App Runner (for simple cases) or ECS Fargate with auto-scaling + event bridge. The traffic splitting/revision concept is similar to AWS CodeDeploy canary deployments.

🧠 Memory Mnemonic: ACA = "Auto-Contained Apps"

S.E.R.V.E. — Scale to zero, Event-driven (KEDA), Revisions & traffic split, VNet integration, Environment-scoped. Think: "ACA Serves microservices."

🗄️ Azure Container Registry (ACR)

What Is ACR?

Azure Container Registry is a managed, private Docker registry service based on the open-source Docker Registry 2.0. You use it to store and manage your container images, Helm charts, and OCI artifacts. Every container service in Azure (ACI, ACA, AKS, App Service) can pull images from ACR.

Why Not Just Use Docker Hub?

  • Security — ACR is private by default. Docker Hub free tier images are public.
  • Geo-replication — replicate images close to your deployment regions for faster pulls
  • Network integration — ACR can be accessed via Private Endpoints (no public internet)
  • Azure AD authentication — RBAC, managed identity, service principals — no shared credentials
  • Image scanning — integrated vulnerability scanning with Microsoft Defender
  • ACR Tasks — build container images in Azure without a local Docker daemon

Key CLI Commands

# Create a registry az acr create --resource-group myRG --name myACR --sku Standard # Login to ACR az acr login --name myACR # Tag and push an image docker tag myapp:v1 myacr.azurecr.io/myapp:v1 docker push myacr.azurecr.io/myapp:v1 # Build image in Azure (no local Docker needed!) az acr build --registry myACR --image myapp:v1 . # List images in the registry az acr repository list --name myACR
📝 Exam Tip
To push an image to ACR, you must first TAG it with the registry's login server name. The correct order is: (1) Authenticate → (2) Tag → (3) Push. The admin account is disabled by default and should NOT be used in production — use managed identity or service principal instead.

🧠 Memory Mnemonic: ACR SKUs = "B.S.P."

Basic (dev), Standard (prod single-region), Premium (geo-replication + private link). Remember: Geo-replication and Private Link are PREMIUM only.

🏗️ Architect's Rule of Thumb
If you don't know Kubernetes and don't want to learn it → ACA or App Service.
If you know Kubernetes and need full control → AKS.
If you just need to run one container quickly → ACI.
If the exam says "minimize management overhead" → ACA (for containers) or App Service (for web).

🧠 Memory Mnemonic: "I Am King" → ACI, ACA, AKS

Instant = ACI (just run it) → Auto = ACA (auto-scales, auto-manages) → King = AKS (king of control, full Kubernetes). As complexity grows, move right.

🎯 Containers Knowledge Check

📋 Rapid-Fire Quiz — Test Yourself

Q1: Your company needs to run a nightly data processing job that takes 15 minutes. The container should start, process, and stop. Minimal infrastructure management is required. Which service?
Azure Container Instances (ACI) — perfect for short-lived, on-demand tasks with per-second billing and no cluster overhead. Use restart policy "Never" or "OnFailure."
Q2: A development team wants to deploy 10 microservices that need to auto-scale based on queue depth and communicate with each other via service discovery. They don't want to manage Kubernetes. Which service?
Azure Container Apps (ACA) — KEDA-based scaling on queue depth, built-in service discovery, Dapr for service-to-service communication, no K8s management required.
Q3: You have a container group with two containers: Container A (request 2 CPU, limit 3 CPU) and Container B (request 1 CPU, no limit set). What is Container B's maximum CPU usage?
1 CPU — when no resource limit is specified, the maximum equals the resource request. Container B can use at most 1 CPU.
Q4: You need to deploy a multi-container group (app + sidecar). One container runs Windows Server Core, the other runs Linux Alpine. Can they be in the same container group?
No — a container group can only have ONE OS type. You cannot mix Windows and Linux in the same group. Additionally, multi-container groups only support Linux containers.
Q5: Your ACI container needs persistent storage for log files. Which Azure storage service is supported?
Azure Files (File Share) only. ACI does not support Blob Storage, Table Storage, or managed disks for volume mounts.
Q6: You need to push a container image to ACR. You've already authenticated. What must you do BEFORE running docker push?
Tag the image with the ACR login server name. Example: docker tag myapp:v1 myacr.azurecr.io/myapp:v1. Without this tag, Docker doesn't know which registry to push to.
Q7: Your team needs geo-replication of container images and private endpoint access to the registry. Which ACR SKU is required?
Premium — geo-replication and Private Link are only available in the Premium SKU.
Q8: An ACA app needs to deploy a new version and gradually shift 20% of traffic to it before full rollout. What feature enables this?
Revisions with traffic splitting. Deploy the new version as a new revision, then use ingress traffic rules to split 80/20 between revisions (canary deployment pattern).
Q9: You want to run a Windows container with private networking in ACI. What should you check first?
Historically, private networking was Linux-only in ACI. This is a frequently tested exam point. While recent updates have added Windows support for private networking, always verify current documentation. In the exam, if private networking is "unavailable" and OS is Windows, changing OS to Linux is typically the expected answer.
Q10: Your AKS cluster is at capacity during peak hours, but you don't want to permanently add more nodes. What Azure-native solution can handle the burst?
AKS Virtual Nodes (powered by ACI) — allows AKS to burst overflow pods to ACI, providing elastic scaling without permanently provisioning extra nodes. Requires Azure CNI networking.
