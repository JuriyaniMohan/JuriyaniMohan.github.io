📊 Azure Monitor — The Central Nervous System

What Is Azure Monitor?

Azure Monitor is the unified monitoring platform for all of Azure. It collects, analyzes, and acts on telemetry from your cloud and on-premises environments. It's not a single tool — it's a comprehensive suite that ingests both metrics and logs from every layer of your stack: infrastructure, platform, application, and network.

The Problem It Solves

Without centralized monitoring, you'd have: separate dashboards for VMs, separate alerts for storage, separate logs for apps, and no way to correlate "why did CPU spike at the same time as the storage queue backed up?" Azure Monitor unifies all of this into one platform with one query language (KQL) and one alerting pipeline.

🏗️ Architect's Analogy
Think of Azure Monitor as the central nervous system of your cloud environment. Just as your brain receives signals from every part of your body (pain, temperature, pressure), Azure Monitor receives telemetry from every Azure resource. It processes these signals, identifies anomalies, and triggers responses (alerts = reflexes, dashboards = consciousness).

What Azure Monitor Does — The 5 Pillars

  • Collect — Gathers metrics and logs from Azure resources, applications, OS, custom sources
  • Analyze — Uses Log Analytics (KQL) for deep analysis and Metrics Explorer for real-time visualization
  • Visualize — Dashboards, Workbooks, Power BI, Grafana integration
  • Alert — Proactive notification when conditions are met (metric thresholds, log patterns)
  • Act — Trigger automated responses via Action Groups (email, SMS, webhook, Logic Apps, Functions)

🧠 Memory Mnemonic: "CAVAA" — What Azure Monitor Does

Collect → Analyze → Visualize → Alert → Act. Think: "CAVAA — the monitoring JAVA" (Collection powers everything).

Monitor Components Overview

  • Azure Monitor Agent (AMA) — the current-generation agent that replaces the legacy Log Analytics Agent (MMA/OMS). Collects guest OS data using Data Collection Rules.
  • Data Collection Rules (DCR) — define WHAT data to collect, HOW to transform it, and WHERE to send it. Each VM can have multiple DCRs.
  • Log Analytics Workspace — the central repository where logs land. Queryable with KQL.
  • Metrics Explorer — real-time visualization of numerical metrics (CPU, memory, requests/sec).
  • Alerts — rules that evaluate conditions and fire notifications via Action Groups.
  • Workbooks — interactive, customizable reports combining metrics, logs, and text.
  • Insights — curated monitoring experiences (VM Insights, Container Insights, Network Insights).
⚠️ Critical: AMA vs Legacy Agents
The Azure Monitor Agent (AMA) is the current standard. The Log Analytics Agent (MMA) was deprecated in August 2024. For the AZ-104 exam, always choose AMA when given the option. AMA uses DCRs; the legacy agent used workspace-level configuration.
📝 Exam Tip
Know the dependency chain: VM → needs AMA installed → AMA needs a DCR → DCR sends data to → Log Analytics Workspace → Alert Rule queries the workspace → triggers Action Group. The exam loves testing these connections.

🧠 Memory Mnemonic: "AMA → DCR → LAW → ALERT → AG"

Agent → Data Collection Rule → Log Analytics Workspace → Alert Rule → Action Group. Data flows left to right, always.

📈 Metrics vs Logs — The Two Data Types

What Are Metrics?

Metrics are numerical values collected at regular intervals that describe some aspect of a resource at a point in time. They're lightweight, near real-time, and stored in a time-series database. Think: "how much CPU is being used right now?"

What Are Logs?

Logs are rich, structured text/JSON records that capture detailed information about events, errors, traces, and activities. They're stored in Log Analytics and queried with KQL. Think: "why did the app crash at 3:42 PM?"

💡 The Golden Rule
Metrics tell you WHAT happened (measurement). Logs tell you WHY it happened (context). Use metrics for dashboards and threshold alerts. Use logs for root cause analysis and forensics.

How Events Occur in Azure Monitor

An "event" in monitoring terms is any discrete occurrence that Azure captures:

  • Platform events — Azure automatically emits these: a VM starting/stopping, a storage account key rotated, a deployment succeeding/failing
  • Activity Log events — every control-plane operation (create, update, delete of resources) is recorded here
  • Diagnostic events — resource-level events you opt into: request logs from App Service, query metrics from SQL Database
  • Application events — your code emits custom events via Application Insights SDK: user login, payment processed, error caught
  • Security events — sign-in failures, suspicious IP access, policy violations

Alert Severity Levels

Sev 0 — Critical
Production down, data loss imminent. Page the on-call immediately.
Sev 1 — Error
Service degraded, users impacted. Needs attention within 1 hour.
Sev 2 — Warning
Potential issue detected. May become critical if not addressed.
Sev 3 — Informational
Notable event, no action needed now. Useful for trending.
Sev 4 — Verbose
Debug-level information. Used during troubleshooting only.
📝 Exam Tip
Severity levels range from 0 (Critical/most severe) to 4 (Verbose/least severe). This is COUNTER-INTUITIVE — lower number = higher severity. The exam may test this in scenario questions about alert prioritization.

🧠 Memory Mnemonic: Metrics = "M for Measurement", Logs = "L for Logic"

Metrics answer "how much/many?" → numerical, fast, cheap. Logs answer "what happened and why?" → detailed, rich, queryable. Severity: "0 is Oh-No!" (most critical) down to "4 is For-details" (verbose).

🔍 KQL — Kusto Query Language

What Is KQL?

KQL (Kusto Query Language) is a read-only query language designed for exploring large volumes of structured, semi-structured, and unstructured data in Azure Monitor Logs. Think of it as SQL for logs — but optimized for time-series analysis, text searching, and aggregation at massive scale.

Where KQL Is Used

  • Azure Monitor — Log Analytics — primary use, querying log data
  • Application Insights — querying app telemetry
  • Microsoft Sentinel — security analytics and threat hunting
  • Azure Data Explorer — big data analytics
  • Azure Resource Graph — querying Azure resource metadata at scale
  • Microsoft Defender for Cloud — security posture queries

Is KQL Available Across Cloud Providers?

KQL is a Microsoft-proprietary language. It's NOT available in AWS or GCP natively. However:

CloudLog Query LanguageComparison
AzureKQL (Kusto Query Language)Most powerful for log analytics. Pipe-based syntax similar to PowerShell.
AWSCloudWatch Logs InsightsSimpler syntax, less powerful. No pipe operator. Good for basic queries.
GCPCloud Logging Query LanguageSimple filter-based syntax. Can also use BigQuery SQL for exported logs.
🏗️ Architect's Take
KQL is one of Azure's genuine competitive advantages. Once you learn it, you can query logs, investigate security incidents, analyze app performance, and audit resource changes — all with the same syntax. In AWS, you'd need different tools for each of these.

KQL Fundamentals — The Structure

Every KQL query follows a pipe-based flow: Source → Filter → Transform → Aggregate → Visualize

// Basic structure: Table | filter | project | sort // 1. Find all failed requests in the last 24 hours requests | where timestamp > ago(24h) | where success == false | project timestamp, name, resultCode, duration | order by duration desc // 2. Average CPU by VM over last 1 hour Perf | where ObjectName == "Processor" | where CounterName == "% Processor Time" | where TimeGenerated > ago(1h) | summarize AvgCPU = avg(CounterValue) by Computer | order by AvgCPU desc // 3. Count events by severity in Activity Log AzureActivity | where TimeGenerated > ago(7d) | summarize Count = count() by Level | order by Count desc // 4. Find top 5 error messages AppExceptions | where TimeGenerated > ago(24h) | summarize Count = count() by problemId | top 5 by Count

Activity Log Queries — Scoping

The Activity Log captures control-plane operations — everything done to your Azure resources (create, delete, update, RBAC changes). When querying it, scoping is critical because:

  • Without scope, you query ALL subscriptions you have access to — massive data volume, slow queries, confusing results
  • Scope to subscription — see all operations in a specific subscription
  • Scope to resource group — narrower, focused on a specific workload
  • Scope to resource — see only operations on a specific VM, storage account, etc.
// Query Activity Log scoped to a specific resource group AzureActivity | where ResourceGroup == "myResourceGroup" | where ActivityStatusValue == "Failed" | where TimeGenerated > ago(24h) | project TimeGenerated, OperationNameValue, Caller, ActivityStatusValue | order by TimeGenerated desc

Log Query Best Practices

  • Always filter time FIRST — where TimeGenerated > ago(24h) should be your first filter to minimize scanned data
  • Use project early — select only the columns you need to reduce data transfer
  • Avoid wildcards on large tables — search * scans everything, extremely expensive
  • Use summarize for aggregation — don't pull raw records when you need counts/averages
  • Test queries before using in alerts — run them in Log Analytics first to verify results
  • Scope your queries — always scope to the narrowest resource/group needed
📝 Exam Tip
The AZ-104 does NOT require you to write complex KQL. But you MUST be able to: (1) read a basic KQL query and understand what it does, (2) identify the correct table name for a given scenario (e.g., AzureActivity for control-plane, Perf for VM metrics, requests for app telemetry), (3) understand the pipe (|) operator chains filters sequentially.

🧠 Memory Mnemonic: KQL = "K-ueue of Queries in a Line"

Data flows through a pipeline: Table → where (filter) → summarize (aggregate) → project (select columns) → order by (sort). Each pipe (|) refines the data further. Think of it as an assembly line for data.

🔔 Alert Rules & Action Groups

How Alerting Works — The Flow

Data Source → Alert Rule (condition) → Condition Met? → Fire Alert → Action Group (notify/act)

Types of Alert Rules

TypeWhat It MonitorsExample
Metric AlertNumeric metric crosses a threshold"Alert when CPU > 90% for 5 minutes"
Log Search AlertKQL query returns results matching criteria"Alert when error count > 10 in last 15 min"
Activity Log AlertSpecific control-plane operation occurs"Alert when someone deletes an NSG"
Prometheus AlertKubernetes/AKS metrics via Prometheus"Alert when pod restart count > 3"
Resource Health AlertAzure platform health events"Alert when my VM becomes unavailable"

What Are Action Groups?

An Action Group is a reusable collection of notification and automation actions that get triggered when an alert fires. You create an action group once and attach it to multiple alert rules.

Notification Types

  • Email — send to up to 1,000 email addresses
  • SMS — text message to phone numbers
  • Push notification — Azure mobile app
  • Voice call — phone call to a number

Action Types (Automation)

  • Webhook — POST request to any HTTP endpoint (Slack, PagerDuty, custom API)
  • Azure Function — trigger serverless code to auto-remediate
  • Logic App — trigger a workflow (create ticket in ServiceNow, restart VM)
  • Automation Runbook — execute a PowerShell/Python script
  • ITSM Connector — create incidents in ITSM tools
  • Event Hub — stream alert data to external systems

Alert Processing Rules

Alert Processing Rules (APRs) modify alert behavior after the alert is generated. They do NOT change the condition — they change the response.

  • Suppression — silence all alerts for a resource during maintenance windows ("Don't wake me up Sunday 2-4 AM during backup")
  • Add Action Group — attach additional notification channels to existing alerts
  • Remove Action Group — remove notification for specific time periods
📝 Exam Tip — Frequently Tested
Action Groups can be REUSED across multiple alert rules. This is a key design principle — don't create a separate AG for every alert. Also: Alert Processing Rules are used to SUPPRESS alerts during maintenance, not to change alert conditions.
🏗️ Architect's Best Practice
Design action groups by severity and team: AG-Critical-OnCall (SMS + voice + PagerDuty), AG-Warning-Team (email + Teams), AG-Info-Log (Event Hub for analytics). Don't send SMS for every info-level alert — you'll create alert fatigue and people will ignore real emergencies.

🧠 Memory Mnemonic: Action Groups = "WHEN-WHO-HOW"

WHEN = Alert Rule defines the condition. WHO = Action Group defines who gets notified. HOW = Notification/Action type defines the channel. Alert Processing Rules = "EXCEPT during maintenance."

🗃️ Log Analytics Workspaces

What Is a Log Analytics Workspace?

A Log Analytics Workspace (LAW) is a unique environment for Azure Monitor log data. It's essentially a massive, queryable data lake for all your operational telemetry. Every log that enters Azure Monitor eventually lands in a LAW where it can be queried with KQL.

Why Not Just One Giant Workspace?

While you CAN put everything in one workspace, architects design workspace strategies based on:

  • Data sovereignty — workspace region determines where data is stored. Singapore data stays in Singapore LAW.
  • Access control — RBAC is applied at the workspace level. Dev team shouldn't see prod security logs.
  • Retention requirements — different data types may need different retention periods (30 days for dev, 2 years for compliance).
  • Cost management — each workspace has its own billing. Separate workspaces make cost attribution clearer.
  • Query performance — extremely large workspaces can have slower queries.

Common Workspace Architectures

PatternDescriptionWhen to Use
CentralizedOne workspace for all resourcesSmall orgs, < 50 resources, single team, simple RBAC
DecentralizedOne workspace per team/subscriptionLarge orgs with strict team boundaries, different retention needs
Hybrid (Recommended)Centralized ops workspace + separate security workspaceEnterprise: ops team queries operational data, security team has isolated SOC workspace

Workspace Key Settings

  • Retention — 30 days free, configurable up to 730 days (2 years). Beyond that, archive to storage.
  • Daily Cap — limit data ingestion to prevent cost spikes (use carefully — you'll lose visibility)
  • Pricing Tier — Pay-as-you-go or Commitment Tiers (100 GB/day+) for discounts
  • Access Control Mode — Workspace-context (RBAC on entire workspace) vs Resource-context (RBAC per resource)
📝 Exam Tip
A common exam scenario: "Your organization has resources in East US and West Europe. Compliance requires that log data stays in the same region as the resource. What should you do?" → Create a separate Log Analytics Workspace in each region.

🧠 Memory Mnemonic: LAW = "Logs Always Welcome"

The Log Analytics Workspace is where ALL logs go. Design by: R.A.C.E. — Region (data sovereignty), Access (RBAC boundaries), Compliance (retention), Efficiency (cost/performance).

🏗️ Architecting a Monitoring Solution — The Process

Step-by-Step Framework

Here's the process I follow with every client engagement when designing monitoring from scratch:

Step 1: Define What Matters (SLOs & KPIs)

Before configuring anything, define: What does "healthy" look like? What are the Service Level Objectives?

  • API response time < 200ms at P95
  • Availability > 99.9% measured monthly
  • Error rate < 0.1% of total requests
  • Database query time < 50ms average

Step 2: Design Workspace Strategy

  • How many workspaces? (Follow R.A.C.E. framework above)
  • What retention for each workspace?
  • Which pricing tier? (Commitment tier if > 100 GB/day)

Step 3: Configure Data Collection

  • Deploy AMA to all VMs via Azure Policy (automated, at-scale)
  • Create DCRs for: performance counters, event logs, syslog
  • Enable diagnostic settings on all Azure resources (storage, SQL, App Service)
  • Integrate Application Insights into application code

Step 4: Build Alert Rules by Severity

  • Sev 0: System down → metric alerts (availability = 0) → AG: SMS + Voice + PagerDuty
  • Sev 1: Degraded performance → metric alerts (CPU > 90%) → AG: Email + Teams
  • Sev 2: Warning signs → log search alerts (error spike) → AG: Email
  • Sev 3-4: Informational → log search alerts → AG: Event Hub (for analytics)

Step 5: Create Dashboards & Workbooks

  • Executive dashboard — high-level health, SLO compliance
  • Ops dashboard — real-time metrics, active alerts, recent deployments
  • Investigation workbook — drill-down KQL queries for incident response

Step 6: Set Up Alert Processing Rules

  • Suppress alerts during known maintenance windows
  • Route after-hours alerts to on-call rotation via webhook

Step 7: Continuous Improvement

  • Review alert noise monthly — suppress or tune noisy alerts
  • Track Mean Time to Detect (MTTD) and Mean Time to Resolve (MTTR)
  • Add new data sources as new services are deployed
🏗️ The Monitoring Anti-Patterns I've Seen in 10 Years
1. Alert fatigue — 500 emails/day means everyone ignores alerts. Fix: tune thresholds, use severity properly.
2. No baseline — alerting on 80% CPU when your app normally runs at 75%. Fix: observe for 2 weeks before setting thresholds.
3. Missing correlation — separate dashboards for app, infra, network with no cross-reference. Fix: centralized workspace + workbooks.
4. Monitoring without action — alerts fire but nobody has a runbook. Fix: every Sev 0/1 alert must have a documented response procedure.

🛡️ Data Protection in Azure

What Data Protection Covers

Data protection in Azure encompasses ensuring your data is: encrypted at rest and in transit, backed up for disaster recovery, compliant with regulatory requirements, and protected from accidental or malicious deletion. Day 4 focuses on the monitoring and operational aspects of data protection.

Azure Data Protection Key Services

ServiceWhat It ProtectsKey Feature
Azure BackupVMs, SQL, Files, Blobs, DisksPolicy-based backup with vaulted & snapshot tiers
Azure Site RecoveryVMs, physical serversReplication to secondary region for DR
Soft DeleteBlobs, containers, backup dataRecoverable deletion (14-365 day retention)
Immutable StorageBlob dataWORM compliance — data cannot be modified or deleted
Resource LocksAny Azure resourcePrevent accidental deletion (CanNotDelete) or modification (ReadOnly)
Azure Key VaultKeys, secrets, certificatesCentralized secret management, HSM-backed keys
EncryptionAll Azure storageSSE with Microsoft-managed or customer-managed keys (CMK)

Data Protection Monitoring with Azure Monitor

Data protection isn't just about configuring backups — it's about monitoring that protection is working:

  • Backup Reports — configure diagnostic settings on Recovery Services Vault → send to Log Analytics → build dashboards showing backup success/failure rates
  • Activity Log Alerts — alert when someone removes a resource lock or disables soft delete
  • Key Vault monitoring — enable diagnostic logging to detect unauthorized access to secrets/keys
  • Azure Policy — enforce that all VMs must have backup enabled, all storage must have soft delete, all resources must have locks

Monitoring + Data Protection Integration

Azure Backup → Diagnostic Settings → Log Analytics → Alert Rule (backup failed) → Action Group (email ops)
// KQL: Find all failed backup jobs in the last 7 days AddonAzureBackupJobs | where TimeGenerated > ago(7d) | where JobStatus == "Failed" | project TimeGenerated, BackupItemUniqueId, JobOperation, JobStatus, JobFailureCode | order by TimeGenerated desc
📝 Exam Tip
The exam may ask: "How do you get notified when a VM backup fails?" → Answer: Configure diagnostic settings on the Recovery Services Vault to send data to a Log Analytics Workspace, then create a log search alert rule with a KQL query filtering for failed jobs, linked to an action group.
💡 Defense in Depth for Data
Layer your protection: Encryption (always on) → Backup (recovery from data loss) → Soft Delete (recovery from accidental deletion) → Immutable Storage (regulatory compliance) → Resource Locks (prevent accidental changes) → Azure Policy (enforce all of the above organization-wide).

🧠 Memory Mnemonic: Data Protection = "EBSIRL"

Encryption → Backup → Soft Delete → Immutable → Resource Locks → Log & Alert. Remember: "Every Backup Should Include Real Logging."

🎯 Monitor & Data Protection Knowledge Check

📋 Rapid-Fire Quiz

Q1: What are the two primary data types in Azure Monitor?
Metrics (numerical time-series data) and Logs (rich structured text/JSON records). Metrics = WHAT happened. Logs = WHY it happened.
Q2: A VM needs to send performance counters to Log Analytics. What must be installed on the VM, and what configuration is required?
Install the Azure Monitor Agent (AMA) and create a Data Collection Rule (DCR) that specifies which counters to collect and which Log Analytics Workspace to send them to.
Q3: What is the severity level for the most critical alerts? What number?
Severity 0 (Sev 0) is the most critical. Counter-intuitive: lower number = higher severity. Sev 4 is the least severe (verbose/informational).
Q4: Your organization has resources in US East and EU West. Compliance requires log data to stay in the same region as the resource. How should you design your workspace strategy?
Create separate Log Analytics Workspaces in each region (one in East US, one in West Europe). The workspace region determines where data is stored. Use cross-workspace queries if you need a unified view.
Q5: What is KQL and where is it used? Is it available in AWS?
Kusto Query Language — a read-only query language for Azure Monitor Logs, Application Insights, Sentinel, and Azure Data Explorer. It is Microsoft-proprietary and NOT available in AWS (which uses CloudWatch Logs Insights) or GCP (which uses Cloud Logging Query Language).
Q6: What is the difference between an Action Group and an Alert Processing Rule?
Action Group = defines WHO gets notified and HOW (email, SMS, webhook, automation). Alert Processing Rule = modifies alert behavior AFTER firing (suppress during maintenance, add/remove action groups). Action Groups define the response; APRs modify when/whether the response happens.
Q7: You want to be notified when a VM backup fails. Walk through the full configuration path.
1. Enable Diagnostic Settings on the Recovery Services Vault → send to Log Analytics Workspace. 2. Create a Log Search Alert Rule with a KQL query filtering AddonAzureBackupJobs where JobStatus == "Failed". 3. Attach an Action Group with email/SMS notification. 4. Set appropriate severity (Sev 1 or Sev 2).
Q8: When querying the Activity Log, why is scoping important?
Without scoping, the query runs across ALL subscriptions you have access to — resulting in massive data volumes, slow performance, and irrelevant results. Always scope to the narrowest level needed: subscription → resource group → individual resource.
Q9: What's the default log retention in a Log Analytics Workspace, and what's the maximum?
Default: 30 days (free). Maximum interactive retention: 730 days (2 years). Beyond that, you can archive data to cheaper storage.
Q10: A KQL query starts with: Perf | where ObjectName == "Processor" | where CounterName == "% Processor Time" | summarize avg(CounterValue) by Computer. What does this return?
It queries the Perf table, filters for CPU processor time metrics, then calculates the average CPU usage per computer (VM). The result is a table with two columns: Computer name and AvgCPU value.
