🏛️ DNS Hierarchy — The Complete Tree

The DNS system is organized as an inverted tree, with the root at the top. Every domain name on the internet is part of this single, global tree. The hierarchy has distinct levels, each managed by different entities.

. (Root) ┌───────────┼───────────┐ .com .org .net .io .gov .edu ... ┌──────┼──────┐ google amazon github ┌────┼────┐ www mail maps drive cloud ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ Level 0 — ROOT │ 13 root server clusters (a.root-servers.net → m.root-servers.net) │ Managed by ICANN, IANA, and various orgs │ Knows where ALL TLDs live Level 1 — TLD │ .com, .org, .net (generic TLDs — gTLDs) │ .uk, .sg, .jp (country code TLDs — ccTLDs) │ .gov, .edu, .mil (sponsored TLDs — sTLDs) │ .app, .dev, .cloud (new gTLDs) │ Managed by registries (Verisign for .com/.net) Level 2 — SLD │ The domain you register: google.com, github.com (Second Level) │ Managed by domain owner / registrant │ Your authoritative name servers live here Level 3+ — Subdomains │ www, mail, api, blog, dev, staging, etc. │ Created by domain owner as needed │ Can be further delegated (sub.sub.domain.com)
Think of it like a corporate org chart. The CEO (Root) oversees VPs (TLDs), who manage Directors (domains), who manage Managers (subdomains). When an employee (resolver) needs to find someone, they start at the top and get directed down the chain until they find the right person.

🌍 Root Name Servers — The Foundation

There are 13 root server identities (named a.root-servers.net through m.root-servers.net), but thanks to Anycast routing, there are actually 1,700+ physical servers distributed globally. The root servers don't know the IP for www.google.com — they only know where to find the TLD servers (like the .com servers).

Why Only 13?

The original DNS protocol used UDP with a 512-byte packet size limit. Fitting all root server addresses (with IPv4) into a single UDP response meant a maximum of 13 entries. Today, with EDNS0 (Extended DNS), larger packets are possible, but the 13-identity convention remains.

📁 TLD Servers — The Categories

Top-Level Domain (TLD) servers manage the top-level zones. When the root server tells the resolver "for .com, go to the .com TLD server," the TLD server then points to the authoritative name server for the specific domain.

Types of TLDs

gTLD (Generic)
.com, .org, .net, .info, .biz — open to anyone
New gTLD
.app, .dev, .cloud, .io, .xyz, .tech — introduced since 2012
ccTLD (Country)
.us, .uk, .sg, .jp, .de, .in — tied to countries/territories
sTLD (Sponsored)
.gov, .edu, .mil, .museum — restricted to qualifying organizations
Infrastructure
.arpa — used for reverse DNS and other infrastructure (managed by IANA)

Key point: The TLD server for .com doesn't know the IP of www.google.com. It only knows which name servers are authoritative for google.com (i.e., ns1.google.com, ns2.google.com, etc.).

✅ Authoritative Name Servers (ANS)

The Authoritative Name Server is the final stop in the DNS resolution chain. It holds the actual DNS records (A, AAAA, MX, CNAME, etc.) for a domain and gives the definitive answer. There is no guessing or caching involved — this is the source of truth.

Authoritative Server Properties

Definitive
It owns the zone file and provides the canonical answer
Non-recursive
It does NOT chase other servers — it answers only for its own zones
Two types
Primary (Master) — holds the read-write zone file. Secondary (Slave) — holds a read-only copy, updated via zone transfers.
AA flag
Sets the "Authoritative Answer" flag in DNS responses (visible in dig output as aa)
Examples
Cloudflare DNS, AWS Route 53, Google Cloud DNS, self-hosted BIND/PowerDNS
authoritative-check.sh
# Check if you're getting an authoritative answer $ dig @ns1.google.com google.com ;; flags: qr aa rd; QUERY: 1, ANSWER: 1 ;; ↑ "aa" flag = this IS an authoritative answer # Compare with a recursive resolver response: $ dig @8.8.8.8 google.com ;; flags: qr rd ra; QUERY: 1, ANSWER: 1 ;; ↑ NO "aa" flag = this is a cached/recursive answer

🔄 What is a Resolver?

A Recursive Resolver (also called a recursive DNS server or just "resolver") is the workhorse of DNS. It sits between your device and the authoritative servers, doing all the heavy lifting of chasing down the answer through the hierarchy.

How a Resolver Works

The Resolution Process

When your computer asks its resolver "What is the IP for www.example.com?", the resolver:

  1. Checks its own cache — if it has a recent, unexpired answer, returns it immediately
  2. If not cached, queries a Root Server: "Where is .com?" → Gets TLD server addresses
  3. Queries the .com TLD Server: "Where is example.com?" → Gets authoritative NS addresses
  4. Queries the Authoritative Name Server: "What is www.example.com?" → Gets the A record
  5. Caches the result (respecting TTL) and returns it to your device

The key point: your device sends one query and expects a final answer. The resolver handles the entire iterative process behind the scenes.

Types of Resolvers

Stub Resolver
The basic resolver built into your OS. It does NOT do recursion — it just forwards the query to a configured recursive resolver. (Found in /etc/resolv.conf on Linux)
Recursive Resolver
The full resolver that does the actual work. Your ISP runs one, and public ones include 8.8.8.8 (Google), 1.1.1.1 (Cloudflare), 9.9.9.9 (Quad9)
Local Resolver
A resolver running on your machine or local network (e.g., systemd-resolved, dnsmasq, Pi-hole, Unbound)

📤 What is a Forwarder?

A DNS Forwarder is a DNS server that doesn't resolve queries itself — instead, it forwards queries to another DNS server (usually a recursive resolver) and waits for the answer. It acts as a middleman/proxy.

Forwarder Behavior

Receives query
Client sends DNS query to the forwarder
Checks cache
If the answer is in its local cache, returns it immediately
Forwards if miss
If not cached, forwards the entire query to an upstream resolver (like 8.8.8.8)
Does NOT iterate
Unlike a resolver, it does NOT query root → TLD → auth. It just passes the buck.
Caches response
Stores the answer for future queries with the same name

Why Use a Forwarder?

Centralized caching: One forwarder caches DNS for all devices on the network, reducing external queries.

Policy control: You can log, filter, or modify DNS queries at the forwarder level (like Pi-hole blocking ads).

Reduced bandwidth: Internal clients make local queries; only cache misses go to the internet.

Conditional forwarding: Forward queries for internal.company.com to the internal DNS, but forward everything else to 8.8.8.8.

forwarder-config-example.conf
# BIND9 named.conf — Forwarder configuration options { directory "/var/named"; // Only forward, never try to resolve iteratively forward only; // Upstream recursive resolvers to forward to forwarders { 8.8.8.8; // Google Public DNS 8.8.4.4; // Google Public DNS (secondary) 1.1.1.1; // Cloudflare DNS }; }; # ─── "forward only" vs "forward first" ───────────────── # forward only → NEVER attempt recursion, fail if forwarders fail # forward first → Try forwarders first, then fall back to recursion

🗄️ Cache-Only DNS vs Full DNS Server

This is a frequently asked question, and the distinction is important for network architecture decisions.

Cache-Only DNS Server

  • Does NOT host any zone files
  • Does NOT have authoritative data for any domain
  • Only resolves and caches queries from clients
  • Acts as a recursive resolver OR a forwarder
  • Its sole purpose: speed up DNS by caching results locally
  • If restarted, the cache is empty — starts fresh
  • Example: A caching Unbound server on your LAN
  • Lightweight — minimal configuration needed

Full DNS Server (Authoritative)

  • Hosts zone files for one or more domains
  • IS the authoritative source for those domains
  • Answers queries with definitive, non-cached data
  • Can also do caching (if configured as recursive too)
  • Requires zone file maintenance, serial updates, transfers
  • Survives restarts — zone data is persistent on disk
  • Example: BIND hosting your company's DNS records
  • More complex — needs security hardening, monitoring
comparison-configs.conf
═══ CACHE-ONLY DNS Server (Unbound) ═══ # /etc/unbound/unbound.conf server: interface: 0.0.0.0 access-control: 192.168.1.0/24 allow do-not-query-localhost: yes # No zone files! Just resolves and caches. forward-zone: name: "." forward-addr: 8.8.8.8 forward-addr: 1.1.1.1 ═══ FULL (Authoritative) DNS Server (BIND) ═══ # /etc/named.conf zone "example.com" { type master; file "/var/named/example.com.zone"; allow-transfer { 192.168.1.5; }; // secondary server }; zone "1.168.192.in-addr.arpa" { type master; file "/var/named/192.168.1.rev"; // reverse zone };

Key Difference Summary

A cache-only server is like a librarian who doesn't own any books — they just remember recent answers and know which library to call. A full DNS server is like a librarian who actually owns and maintains the books (zone files) and is the definitive source.

⚠️ Important Distinction

A DNS server can be both authoritative and caching. For example, BIND can host zones for mycompany.com (authoritative) while also recursively resolving queries for google.com (caching). However, security best practice is to separate these roles — run your authoritative and recursive servers on different machines to reduce attack surface.

📂 Zones, Zone Files & Zone Transfers

A zone is a portion of the DNS namespace that is managed by a specific organization or administrator. It contains all the DNS records for a domain and potentially its subdomains.

Zone vs Domain

A domain is a name (like example.com). A zone is the actual administrative boundary — the set of records managed by one authority. If dev.example.com is delegated to a separate NS, then example.com and dev.example.com are two different zones, even though they're part of the same domain.

Zone Transfers

Zone Transfer Types AXFR (Full Zone Transfer) → Transfers the ENTIRE zone from primary to secondary → Used for initial sync or when incremental isn't available → Uses TCP port 53 IXFR (Incremental Zone Transfer) → Transfers only CHANGES since a given serial number → Much more efficient for large zones → Secondary says: "I have serial 2024031501, what's new?" 🔒 DNS Security

Traditional DNS is unencrypted and unauthenticated — queries travel in plaintext over UDP. This makes it vulnerable to several attacks:

DNS Attack Vectors

DNS Spoofing
Attacker injects fake DNS responses, redirecting users to malicious sites
Cache Poisoning
Corrupting a resolver's cache so it serves wrong IPs for domains
DNS Hijacking
Changing DNS settings on a device or router to point to a rogue server
DNS Tunneling
Encoding data inside DNS queries to bypass firewalls (data exfiltration)
DDoS via DNS
DNS amplification attacks using open resolvers to flood targets

Security Solutions

DNSSEC
Adds cryptographic signatures to DNS records. Resolvers can verify that the response hasn't been tampered with. Doesn't encrypt — just authenticates.
DoH (DNS over HTTPS)
Encrypts DNS queries inside HTTPS (port 443). Used by browsers (Firefox, Chrome). Harder to filter/monitor.
DoT (DNS over TLS)
Encrypts DNS queries using TLS (port 853). Easier for network admins to manage than DoH since it uses a dedicated port.
DoQ (DNS over QUIC)
Newest protocol. Uses QUIC transport for faster, encrypted DNS queries.

🧪 dig Practice — Tracing the Hierarchy

Let's use dig to actually SEE the DNS hierarchy in action. The +trace flag is your best friend here.

dig-trace-walkthrough.sh
# ─── TRACE the full resolution path ──────────────────── $ dig +trace www.google.com # This shows EVERY step: # 1. Query root servers → get .com NS records # 2. Query .com TLD servers → get google.com NS records # 3. Query google.com auth NS → get www.google.com A record # ─── Step-by-step manual trace ───────────────────────── # Step 1: Ask root server about .com $ dig @a.root-servers.net com NS # Returns: a.gtld-servers.net, b.gtld-servers.net, etc. # Step 2: Ask .com TLD server about google.com $ dig @a.gtld-servers.net google.com NS # Returns: ns1.google.com, ns2.google.com, etc. # Step 3: Ask Google's authoritative NS for the final answer $ dig @ns1.google.com www.google.com A # Returns: 142.250.x.x (the actual IP!) # ─── Other useful traces ─────────────────────────────── # Trace SOA record $ dig +trace +multiline google.com SOA # Check if DNSSEC is enabled $ dig +dnssec google.com # Compare response times between DNS providers $ dig @8.8.8.8 google.com | grep "Query time" $ dig @1.1.1.1 google.com | grep "Query time" $ dig @9.9.9.9 google.com | grep "Query time" # Find who is authoritative for a zone $ dig +short NS google.com # Find the SOA (who manages this zone) $ dig +short SOA google.com # Reverse DNS lookup $ dig -x 8.8.8.8 +short # Output: dns.google.
