VPC — Virtual Private Cloud

Your own isolated network inside AWS

Definition What is a VPC?

A Virtual Private Cloud (VPC) is a logically isolated virtual network within the AWS cloud. It's your own private section of the AWS infrastructure where you define the IP address range, create subnets, configure route tables, and set up security rules. Think of it as renting an entire floor of a building — you control the rooms, hallways, locks, and who enters.

Every VPC is defined by a CIDR block (Classless Inter-Domain Routing), for example 10.0.0.0/16, which gives you 65,536 IP addresses. AWS reserves 5 IPs per subnet from this range. The VPC spans an entire AWS Region but you carve it into subnets across Availability Zones.

What Does a VPC Do?

Network Isolation: Every resource you launch (EC2, RDS, Lambda, etc.) lives inside a VPC. Without a VPC, all AWS customers' resources would share the same flat network — a security nightmare. The VPC creates a boundary: traffic inside stays inside, traffic from outside must pass through controlled entry points.

IP Address Management: You define the CIDR block (e.g., 10.0.0.0/16), then subdivide it into subnets. This mirrors how on-premises networks use private IP ranges.

Traffic Control: Route tables decide where packets go. Security groups and NACLs filter what's allowed in and out. Internet Gateways and NAT Gateways control internet access.

Hybrid Connectivity: VPCs can connect to your on-premises data center via VPN or AWS Direct Connect, making hybrid cloud architectures possible.

What Problems Does VPC Solve?

1. Multi-tenant security: Without VPCs, all AWS customers' resources would be on the same network. VPC provides hard isolation — Customer A can never see Customer B's traffic.

2. Regulatory compliance: Industries like healthcare (HIPAA) and finance (PCI-DSS) require network segmentation. VPC provides this natively.

3. IP conflict avoidance: You choose your own CIDR range. If connecting to on-prem, you pick a range that doesn't overlap with your corporate network.

4. Blast radius containment: If one application is compromised, VPC boundaries prevent lateral movement to other applications in different VPCs.

⚠️ Common Issues

  • CIDR overlap: If your VPC uses 10.0.0.0/16 and your office also uses 10.0.0.0/16, VPN/peering won't work. Plan ranges early.
  • CIDR too small: Choosing /24 (256 IPs) initially feels fine, then you run out. VPCs can add secondary CIDRs but it's messy.
  • Default VPC confusion: AWS creates a default VPC per region. Production workloads on the default VPC lack proper segmentation.
  • Peering limitations: VPC peering is not transitive. If VPC-A peers with VPC-B, and VPC-B peers with VPC-C, VPC-A cannot reach VPC-C through VPC-B. Use Transit Gateway instead.
  • ENI/IP exhaustion: Each Lambda, ECS task, or EKS pod consumes an IP. At scale, you can run out of IPs in your subnet.
🏠 Daily Life Analogy

A VPC is like a gated residential community. The entire community has a boundary wall (the CIDR range). Inside, there are streets (subnets), houses (EC2 instances), a main gate (Internet Gateway), a back service gate (NAT Gateway), and security guards (Security Groups / NACLs). Visitors can only enter through the gate after being checked. Residents can go out freely.

🐧 Linux Analogy

A VPC is like creating a network namespace in Linux (ip netns add myvpc). Each namespace has its own routing table, interfaces, and firewall rules — completely isolated from the host's main network stack. Just as you'd use veth pairs to connect namespaces, AWS uses ENIs to connect resources to VPC subnets.

🪟 Windows Analogy

Think of a VPC like a Hyper-V Virtual Switch set to "Private" mode. VMs connected to that switch can talk to each other but are invisible to the outside network. You then add a NAT virtual switch to selectively give some VMs internet access, which is exactly how public vs private subnets work.

Deep Theory & Internals

CIDR Blocks: When you create a VPC with 10.0.0.0/16, the "/16" means the first 16 bits are the network portion. That leaves 16 bits for hosts = 2^16 = 65,536 addresses. Common choices:

# CIDR Examples 10.0.0.0/16 → 65,536 IPs (large VPC) 10.0.0.0/20 → 4,096 IPs (medium VPC) 10.0.0.0/24 → 256 IPs (small VPC, often too small) 10.0.0.0/28 → 16 IPs (minimum subnet size in AWS) # AWS reserves 5 IPs per subnet: 10.0.1.0 → Network address 10.0.1.1 → VPC router 10.0.1.2 → DNS server 10.0.1.3 → Future use 10.0.1.255 → Broadcast (not supported but reserved)

VPC Flow Logs: You can enable flow logs to capture IP traffic metadata (src IP, dst IP, port, protocol, action: ACCEPT/REJECT). These go to CloudWatch Logs, S3, or Kinesis Firehose. Essential for debugging "why can't my EC2 reach the database?" problems.

DNS in VPC: AWS provides a DNS server at the VPC base +2 address (e.g., 10.0.0.2). This resolves both public DNS names and private hosted zone records. You can enable enableDnsHostnames and enableDnsSupport on the VPC for private DNS resolution.

VPC Peering vs Transit Gateway: Peering is a 1-to-1 connection between two VPCs. Transit Gateway is a hub — connect 100+ VPCs and on-prem networks through a single hub. At scale, Transit Gateway is cheaper and simpler than managing hundreds of peering connections.

# AWS CLI: Create a VPC aws ec2 create-vpc \ --cidr-block 10.0.0.0/16 \ --tag-specifications 'ResourceType=vpc,Tags=[{Key=Name,Value=prod-vpc}]' # Enable DNS hostnames aws ec2 modify-vpc-attribute \ --vpc-id vpc-abc123 \ --enable-dns-hostnames '{"Value": true}'

🧠 Quick Check: What is the maximum CIDR block size for an AWS VPC?

The largest VPC CIDR is /16 (65,536 IPs). While AWS supports secondary CIDRs, a single primary block maxes at /16.

🧠 How many IPs does AWS reserve per subnet?

AWS reserves 5 IPs: network address, VPC router, DNS, future use, and broadcast.

Subnets — Public & Private

Carving your VPC into functional zones

Definition What is a Subnet?

A subnet (subnetwork) is a range of IP addresses within your VPC. Each subnet resides in exactly one Availability Zone and cannot span AZs. Subnets are where you actually place your AWS resources — EC2, RDS, Lambda (in VPC mode), etc.

Public Subnet: A subnet whose route table has a route to an Internet Gateway (IGW). Resources here can receive a public IP and be directly accessible from the internet.

Private Subnet: A subnet with no route to an IGW. Resources here cannot be reached from the internet. They may have outbound internet access via a NAT Gateway, but no inbound from outside.

What Subnets Do

Segment your network: Just like VLANs in traditional networking, subnets let you separate workloads. Web servers go in public subnets; databases, caches, and internal services go in private subnets.

Enable high availability: By placing subnets across multiple AZs, you survive data center failures. An Application Load Balancer requires subnets in at least 2 AZs.

Control routing per zone: Each subnet has its own route table association. Public subnets route to IGW; private subnets route to NAT GW or nowhere.

IP allocation: AWS assigns private IPs from the subnet's CIDR to resources launched in that subnet. Public subnets can auto-assign public IPs.

Problems Solved by Subnets

1. Security by architecture: Databases in private subnets are unreachable from the internet by design — no misconfiguration of a firewall rule can expose them because there's no route.

2. Compliance zoning: PCI-DSS requires the cardholder data environment (CDE) to be in its own network segment. Private subnets provide this.

3. Failure domain isolation: If AZ-1a goes down, resources in AZ-1b subnets continue serving traffic.

4. Cost optimization: NAT Gateway charges per GB. By having some subnets route through NAT and others not, you control costs.

⚠️ Common Issues

  • Insufficient IPs: A /24 subnet only gives 251 usable IPs. EKS pods, Lambda functions, and ECS tasks each consume an IP. You hit limits fast.
  • "My EC2 can't reach the internet": 90% of the time, the subnet's route table is missing the 0.0.0.0/0 route to IGW (public) or NAT GW (private).
  • Forgetting multi-AZ: Putting all subnets in one AZ means a single AZ outage takes down everything.
  • Public subnet without auto-assign public IP: The subnet routes to IGW but instances don't get public IPs. Traffic flows out but nothing can respond back.
  • Subnet group confusion: RDS requires a DB subnet group with subnets in at least 2 AZs even for single-AZ deployments.
🏠 Daily Life

Public subnet = the reception area of an office building. Anyone can walk in from the street. Private subnet = the server room in the basement. No door leads to the street — you can only reach it through internal hallways. The basement can call out (via NAT) for deliveries, but nobody from outside can walk in directly.

🐧 Linux

Subnets are like VLANs on a Linux bridge. You create br0 (the VPC), then assign tagged interfaces: br0.10 (public VLAN 10) and br0.20 (private VLAN 20). Each VLAN has its own IP range and iptables rules. The public VLAN has MASQUERADE (NAT) for outbound + port forwarding for inbound. The private VLAN only has MASQUERADE for outbound.

🪟 Windows

Think of it as different network profiles in Windows Firewall: the "Public" profile (stricter rules for untrusted networks) and the "Private/Domain" profile (more open for internal trusted networks). Each subnet is like assigning a NIC to a different profile with its own set of firewall rules and routing.

Deep Theory: Subnet Sizing & Design

The Golden Rule: Always plan for 2x the IPs you think you need. EKS, ECS, and Lambda VPC functions consume IPs aggressively.

# Recommended multi-AZ layout for a /16 VPC VPC: 10.0.0.0/16 (65,536 IPs) # Public subnets (small — only load balancers and bastion hosts) Public-1a: 10.0.0.0/24 (251 usable) Public-1b: 10.0.1.0/24 (251 usable) Public-1c: 10.0.2.0/24 (251 usable) # Private subnets (large — app servers, containers, lambdas) Private-1a: 10.0.16.0/20 (4,091 usable) Private-1b: 10.0.32.0/20 (4,091 usable) Private-1c: 10.0.48.0/20 (4,091 usable) # Data subnets (medium — RDS, ElastiCache) Data-1a: 10.0.64.0/22 (1,019 usable) Data-1b: 10.0.68.0/22 (1,019 usable) Data-1c: 10.0.72.0/22 (1,019 usable)

What makes a subnet "public"? It's not a magic flag — it's purely determined by the route table. If the associated route table has 0.0.0.0/0 → igw-xxx, the subnet is public. Remove that route, and it becomes private instantly.

# Create subnets via AWS CLI aws ec2 create-subnet \ --vpc-id vpc-abc123 \ --cidr-block 10.0.1.0/24 \ --availability-zone us-east-1a \ --tag-specifications 'ResourceType=subnet,Tags=[{Key=Name,Value=public-1a}]' # Enable auto-assign public IP for public subnet aws ec2 modify-subnet-attribute \ --subnet-id subnet-xyz789 \ --map-public-ip-on-launch

🧠 What makes a subnet "public"?

A subnet is public solely because its route table contains a 0.0.0.0/0 route pointing to an IGW.

Route Tables

The GPS of your VPC — directing every packet

Definition What is a Route Table?

A Route Table is a set of rules (called routes) that determine where network traffic from your subnet is directed. Every subnet MUST be associated with exactly one route table. If you don't explicitly associate one, AWS uses the VPC's Main Route Table (a default that's created with the VPC).

Each route has two components: a Destination (a CIDR range like 0.0.0.0/0) and a Target (where to send matching traffic, like an IGW, NAT GW, VPC peering connection, or "local").

What Route Tables Do

Packet routing decisions: When an EC2 instance sends a packet, the VPC router looks at the route table associated with that instance's subnet. It finds the most specific matching route (longest prefix match) and forwards the packet to that target.

Traffic segregation: Different subnets can have different route tables. Public subnets route to IGW, private subnets route to NAT GW, isolated subnets have only the local route.

Hybrid cloud routing: Routes can point to a Virtual Private Gateway (VPN), Transit Gateway, or VPC peering connection to reach other networks.

Problems Solved

1. Controlled internet access: Without a 0.0.0.0/0 route, a subnet simply cannot reach the internet — defense in depth by architecture, not just firewall rules.

2. Multi-network routing: A single VPC can route to the internet (via IGW), to on-prem (via VPN), to another VPC (via peering), and to AWS services (via VPC endpoints) — all managed through route tables.

3. Traffic inspection: You can route traffic through a network appliance (like a firewall EC2) by pointing routes to that instance's ENI, enabling deep packet inspection.

⚠️ Common Issues

  • Missing default route: Forgetting to add 0.0.0.0/0 to a public subnet's route table. Everything in that subnet silently fails to reach the internet.
  • Main route table trap: New subnets auto-associate with the Main route table. If someone adds an IGW route to the Main RT, all new subnets become public by default — a security risk.
  • Route propagation overlap: VPN route propagation can add routes that conflict with existing static routes, causing unpredictable routing.
  • Asymmetric routing: Traffic goes out via NAT GW but response comes back via a different path, causing drops.
🏠 Daily Life

A route table is like the directory sign in a hospital. "Radiology → Floor 2 Left", "Emergency → Ground Floor Right", "Everything else → Main Reception." Each floor (subnet) can have a different directory sign. Without it, patients (packets) wander aimlessly and never reach their destination.

🐧 Linux

This is the Linux ip route table. ip route show gives you the same structure: default via 10.0.1.1 dev eth0 (= 0.0.0.0/0 → IGW), 10.0.0.0/16 dev eth0 scope link (= local route). You can even have multiple routing tables with ip rule — policy-based routing, just like multiple route tables in AWS.

🪟 Windows

Run route print in cmd — you'll see the same structure: network destination, netmask, gateway, interface. AWS route tables are the cloud equivalent of what Windows manages in its IPv4 Route Table, but per-subnet instead of per-machine.

Deep Theory

Longest Prefix Match: If you have routes for both 10.0.0.0/16 and 10.0.1.0/24, a packet destined for 10.0.1.50 matches both — but the /24 route wins because it's more specific. This is how you can override general routes for specific subnets.

Local route: Every route table automatically has a "local" route matching the VPC CIDR. This enables all subnets in the VPC to communicate. You cannot delete this route.

Route priority: AWS routes follow this priority: local routes > static routes > propagated routes. Static routes always beat BGP-propagated routes from VPN.

# Create a custom route table aws ec2 create-route-table --vpc-id vpc-abc123 # Add a route to IGW (makes subnet public) aws ec2 create-route \ --route-table-id rtb-xyz789 \ --destination-cidr-block 0.0.0.0/0 \ --gateway-id igw-123abc # Associate with a subnet aws ec2 associate-route-table \ --route-table-id rtb-xyz789 \ --subnet-id subnet-abc456

🧠 If a route table has routes for both 10.0.0.0/16 and 10.0.1.0/24, which wins for 10.0.1.50?

Longest prefix match wins. /24 is more specific than /16, so it takes priority.

Internet Gateway & NAT Gateway

The doors between your VPC and the world

IGW Internet Gateway

An Internet Gateway (IGW) is a horizontally scaled, redundant, highly available VPC component that enables communication between your VPC and the internet. It performs two functions: it acts as a target in route tables for internet-routable traffic, and it performs Network Address Translation (NAT) for instances with public IPv4 addresses.

There is no bandwidth constraint on an IGW. It's fully managed, HA by default, and costs nothing (you pay for data transfer, not the gateway itself).

NAT GW NAT Gateway

A NAT Gateway enables instances in private subnets to initiate outbound connections to the internet (e.g., download patches, call APIs) while preventing the internet from initiating inbound connections to those instances.

The NAT Gateway lives in a public subnet, has an Elastic IP, and translates private source IPs to its own public IP for outbound traffic. It costs ~$0.045/hour + $0.045/GB processed.

What They Do

IGW performs 1:1 NAT: When an EC2 with private IP 10.0.1.10 and public IP 54.1.2.3 sends a packet, the IGW translates 10.0.1.10 → 54.1.2.3 in the source. On response, it translates 54.1.2.3 → 10.0.1.10 in the destination. The instance never "sees" its public IP — check ifconfig and you'll only see the private IP.

NAT GW performs many:1 NAT: Multiple private instances (10.0.2.20, 10.0.2.21, 10.0.2.22) all appear as the NAT GW's single Elastic IP (54.x.x.x) to the outside world. The NAT GW tracks connection state to route responses back to the correct private instance.

Problems Solved

IGW solves: How do users on the internet reach my web server? How does my web server respond? The IGW provides the bridge between public internet and VPC.

NAT GW solves: My database server needs to download security patches from the internet, but I don't want anyone from the internet to reach it. NAT GW provides outbound-only internet access for private resources.

Both solve: The fundamental tension between "I need internet connectivity" and "I need security isolation." IGW for resources that MUST be publicly reachable; NAT GW for resources that need outbound access but must remain private.

⚠️ Common Issues

  • NAT GW cost surprise: At $0.045/GB, a server downloading 1TB/month through NAT costs $45 in processing fees alone. Consider VPC endpoints for S3/DynamoDB access to bypass NAT.
  • NAT GW single AZ: A NAT GW lives in one AZ. If that AZ goes down, all private subnets routing through it lose internet access. Best practice: one NAT GW per AZ.
  • Port exhaustion: NAT GW supports 55,000 simultaneous connections per destination. High-throughput applications can hit this limit, causing dropped connections.
  • IGW without public IP: An instance in a public subnet (route to IGW exists) but without a public IP or Elastic IP can't reach the internet — the IGW has nothing to NAT to.

✅ Cost Optimization Tip

Use VPC Gateway Endpoints (free!) for S3 and DynamoDB traffic. This bypasses NAT GW entirely, saving both the $0.045/GB processing fee and the data transfer cost. For other AWS services, use Interface Endpoints (PrivateLink).

🏠 Daily Life

IGW = the front door of your house. It has your house number (public IP) so mail carriers (internet traffic) can find it. Traffic flows both ways.
NAT GW = a P.O. Box service. Your private address stays hidden. You can send letters out (the P.O. Box number appears as the return address), and replies come back to the P.O. Box, which forwards them to your real address. But nobody can send you unsolicited mail because they don't know your real address.

🐧 Linux

IGW = a Linux box acting as a router with IP forwarding enabled (echo 1 > /proc/sys/net/ipv4/ip_forward) and a public IP on eth0.
NAT GW = the same box but with iptables MASQUERADE: iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE. This rewrites private source IPs to the box's public IP for outbound traffic, exactly what NAT GW does.

Security Groups vs NACLs

Two layers of firewall — instance-level vs subnet-level

SG Security Group

A Security Group acts as a virtual firewall at the instance level (technically, at the ENI level). It controls inbound and outbound traffic. Security Groups are stateful — if you allow inbound traffic on port 80, the response traffic is automatically allowed out, regardless of outbound rules.

Key characteristic: Security Groups are allow-only. You can only write rules that allow traffic. There are no deny rules. Anything not explicitly allowed is implicitly denied.

NACL Network Access Control List

A NACL acts as a firewall at the subnet level. It evaluates traffic entering or leaving the subnet boundary. NACLs are stateless — you must explicitly allow both inbound AND outbound traffic. If you allow inbound port 80, you must also allow outbound ephemeral ports (1024-65535) for the response.

Key characteristic: NACLs support both ALLOW and DENY rules, evaluated in order of rule number (lowest first). First match wins.

Problems Solved

Security Groups solve: "Which specific ports should this instance accept traffic on, and from whom?" — per-instance granular control. The killer feature is SG-to-SG referencing: instead of allowing IP 10.0.1.10, you allow "sg-webservers" — so any instance in that group can communicate, regardless of IP changes.

NACLs solve: "I need to block a specific malicious IP address" or "I need an explicit deny rule." Since SGs are allow-only, NACLs provide the deny capability. They also provide a subnet-wide safety net — even if someone misconfigures a Security Group, the NACL can catch it.

Together they solve: Defense in depth. Two independent firewall layers that an attacker must bypass both of.

⚠️ Common Issues

  • NACL ephemeral port trap: You allow inbound :80 but forget to allow outbound :1024-65535 (ephemeral ports). Since NACLs are stateless, responses get blocked. This is the #1 NACL mistake.
  • SG rule limit: Default 60 inbound + 60 outbound rules per SG, max 5 SGs per ENI. At scale, you hit limits. Use prefix lists or SG references to consolidate.
  • Circular SG references: SG-A references SG-B, SG-B references SG-A. This works but can create debugging nightmares.
  • Default NACL is permissive: The default NACL allows all traffic. People assume they have protection but they don't. Custom NACLs default to deny-all.
  • "Why can't I connect?" debugging: When both SG and NACL block traffic, VPC Flow Logs show REJECT but don't tell you which layer rejected it. Check both.
🏠 Daily Life

NACL = the security gate at the entrance of your apartment building. The guard checks IDs against a list. Everyone entering or leaving must show ID separately (stateless).
Security Group = the lock on your apartment door. If you let someone in (allowed inbound), you know they're allowed to leave too (stateful). But you can only add people to the "allowed" list — you can't write "block apartment 3B" on your own door.

🐧 Linux

Security Group = iptables with connection tracking (-m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT). Once a connection is established, return traffic is automatically allowed.
NACL = iptables WITHOUT conntrack — raw rules applied to every packet independently. You need explicit rules for both request and response traffic, and rules are matched in order (like iptables chain processing).

🪟 Windows

Security Group = Windows Firewall with Advanced Security per-application rules (stateful by default). NACL = a hardware firewall appliance sitting in front of your network switch — inspects every packet independently, both directions, no state memory.

Deep Theory: SG Chaining

SG-to-SG referencing is the most powerful and underused feature. Instead of maintaining IP-based rules, you reference other security groups:

# Web tier SG: allow internet on 80/443 sg-web: Inbound: TCP :80 from 0.0.0.0/0 Inbound: TCP :443 from 0.0.0.0/0 # App tier SG: allow traffic ONLY from web tier sg-app: Inbound: TCP :8080 from sg-web ← not an IP, a security group! # DB tier SG: allow traffic ONLY from app tier sg-db: Inbound: TCP :3306 from sg-app # Result: Internet → Web → App → DB (no skipping layers)

This means if you add 10 new web servers to sg-web, they instantly get access to the app tier — no rule changes needed. If you remove a server from sg-web, it instantly loses access.

🧠 You allow inbound HTTP (:80) in a NACL but forget outbound rules. What happens?

NACLs are stateless. Without an outbound rule for ephemeral ports (1024-65535), response traffic is silently dropped.

EC2 — Deep Dive

Far beyond "it's a virtual machine in the cloud"

Definition What is EC2?

Elastic Compute Cloud (EC2) provides resizable compute capacity as virtual machines (called instances) on AWS's physical servers. But calling EC2 "just a VM" is like calling an F1 car "just a vehicle." EC2 is a deep ecosystem:

Instance types (200+): Optimized for compute (C-series), memory (R-series), storage (I/D-series), GPU/ML (P/G-series), general purpose (M/T-series).

Purchasing models: On-Demand (pay per second), Reserved (1-3 year commitment, up to 72% off), Spot (up to 90% off, but can be terminated with 2 min notice), Savings Plans, Dedicated Hosts.

Key components per instance: AMI (OS image), instance type, key pair (SSH), Security Group, subnet placement, EBS volumes, IAM role, user data script, metadata service.

What EC2 Does (Beyond Basic)

Instance Store vs EBS: Instance store is physically attached NVMe — blazing fast but EPHEMERAL (data lost on stop/terminate). EBS is network-attached — persistent, snapshottable, but limited by network throughput. Know the tradeoff.

Placement Groups: Cluster (same rack, lowest latency, for HPC), Spread (across hardware, for HA), Partition (for large distributed systems like Hadoop/Kafka).

Instance Metadata Service (IMDS): Every EC2 can query http://169.254.169.254/latest/meta-data/ to discover its own ID, public IP, IAM role credentials, etc. IMDSv2 requires a PUT to get a session token first (more secure).

User Data: A bash script (or cloud-init config) that runs on first boot. Used to install packages, pull code, configure services. Runs as root.

Elastic Network Interface (ENI): A virtual NIC. Each instance has a primary ENI (eth0) but can have additional ENIs in different subnets — useful for multi-homed instances, management networks, or failover.

Problems Solved

1. Capacity on demand: Need 100 servers for Black Friday? Launch them. Need 5 on Tuesday? Terminate the rest. No hardware procurement cycles.

2. Right-sizing: Start with t3.micro (free tier), realize you need more CPU, resize to c5.2xlarge in minutes. Try doing that with physical servers.

3. Global deployment: Launch instances in 30+ regions worldwide. Your users in Tokyo get a server in Tokyo, not Virginia.

4. Spot for batch processing: Run ML training, video encoding, or data analysis at 90% discount. If the instance is reclaimed, checkpoint and resume on another.

⚠️ Common Issues (Deep)

  • Instance type obsolescence: Running m4.large in 2024? m7i.large is cheaper AND faster. AWS doesn't auto-upgrade you — you must track new instance families.
  • EBS throughput bottleneck: gp2 volumes burst IOPS then throttle. Symptoms: high latency, application slowness that "comes and goes." Switch to gp3 with provisioned IOPS.
  • IMDSv1 security risk: IMDSv1 allows simple GET requests. An SSRF vulnerability in your app can leak IAM credentials. Always enforce IMDSv2 (requires session token).
  • Spot termination handling: Your app must handle the 2-minute termination notice. Check http://169.254.169.254/latest/meta-data/spot/termination-time and gracefully shut down.
  • "I lost my key pair": You can't SSH in. Solution: stop instance, detach root volume, attach to another instance, add your public key to ~/.ssh/authorized_keys, reattach, start.
  • T-series CPU credit exhaustion: T3/T3a are burstable. If you consistently use >20% CPU, you burn through credits and get throttled to baseline. Use M-series for sustained workloads.
🏠 Daily Life

On-Demand = staying at a hotel. Pay per night, leave whenever you want. Expensive but flexible.
Reserved = signing a 1-year apartment lease. Cheaper per month because you committed.
Spot = booking a last-minute Airbnb. Amazing price, but the host can cancel with 2 minutes' notice if someone pays full price.
Dedicated Host = buying the entire building. You control every floor. Needed for licensing requirements (Oracle, Windows Server).

🐧 Linux

EC2 is a KVM/QEMU virtual machine on steroids. AWS uses a custom hypervisor called Nitro (based on KVM). The Nitro System offloads networking, storage, and security to dedicated hardware cards — your vCPU does only your workload, not hypervisor overhead. lscpu on a Nitro instance shows the bare CPU without hypervisor tax.

🪟 Windows

IAM — Identity & Access Management

Who can do what, on which resources, under what conditions

Definition What is IAM?

IAM (Identity and Access Management) is the global AWS service that controls authentication (who are you?) and authorization (what can you do?). It's the backbone of every single AWS API call — every request to AWS must include valid IAM credentials and pass policy evaluation.

IAM has four core entities:

Users: Represent individual people or applications. Have permanent long-term credentials (access keys, passwords).

Groups: Collections of users. Attach policies to groups, not individual users — much easier to manage.

Roles: Identities that can be assumed temporarily. No permanent credentials. Used by EC2 instances, Lambda functions, cross-account access, and federated users.

Policies: JSON documents that define permissions. Attached to users, groups, or roles.

What IAM Does

Authentication: Verifies identity. For console: username + password + optional MFA. For API/CLI: Access Key ID + Secret Access Key. For roles: STS (Security Token Service) issues temporary credentials.

Authorization: Evaluates policies to determine if the authenticated identity is allowed to perform the requested action. The evaluation logic: start with implicit deny → check all applicable policies → if any explicit deny exists, deny → if any allow exists, allow → otherwise deny.

Federation: IAM integrates with external identity providers (Active Directory, Okta, Google) via SAML 2.0 or OIDC. Users authenticate with their corporate credentials and receive temporary AWS credentials.

Cross-account access: Account A creates a role, Account B's users assume that role. No need to create IAM users in every account.

Problems Solved

1. Principle of least privilege: Without IAM, everyone has root access. IAM lets you give a developer EC2 access but not the ability to delete the production database.

2. No hardcoded credentials: IAM Roles for EC2 = no access keys in code or environment variables. The instance automatically gets temporary credentials rotated every hour via the instance metadata service.

3. Audit trail: Every IAM API call is logged in CloudTrail. "Who deleted the S3 bucket at 3am?" → CloudTrail shows the IAM user, the IP address, and the exact API call.

4. Multi-account governance: With AWS Organizations + Service Control Policies (SCPs), you can set guardrails across 100+ accounts: "No account can launch instances outside us-east-1" — enforced at the organization level, unoverridable by account admins.

⚠️ Common Issues

  • Overly permissive policies: Using "Action": "*", "Resource": "*" (admin access) for everything. One compromised credential = entire account compromised.
  • Long-lived access keys: Access keys that haven't been rotated in months/years. Keys get leaked in git repos, Slack messages, Stack Overflow posts.
  • IAM policy limit confusion: Managed policy max size is 6,144 characters. Inline policy max 2,048. At scale, you hit these limits and must refactor.
  • Confused deputy problem: A service acting on behalf of one customer accidentally accesses another customer's resources. Solved with aws:SourceArn and aws:SourceAccount conditions.
  • Root account without MFA: The root account bypasses all IAM policies. Without MFA, a leaked root password = total account takeover.
🏠 Daily Life

IAM User = a named employee badge. Your name, your photo, always yours.
IAM Group = department badge access. Everyone in "Engineering" can access the lab.
IAM Role = a visitor badge. It's not assigned to anyone permanently. You "assume" it when needed, and it expires. An EC2 instance is like a contractor who wears a visitor badge — it gets temporary access that auto-renews.
Policy = the list of doors each badge can open.

🐧 Linux

IAM Users = Linux users in /etc/passwd. IAM Groups = Linux groups in /etc/group. IAM Policies = a combination of file permissions (rwx), ACLs (setfacl), and sudoers rules. IAM Roles = sudo -u serviceuser — you temporarily become another identity with different permissions. STS temporary credentials = Kerberos tickets that expire.

🪟 Windows

IAM = Active Directory (AD). Users, groups, Group Policy Objects (GPOs = IAM Policies). IAM Roles = "Run As" different accounts or gMSA (group Managed Service Accounts) for services. Cross-account roles = AD forest trusts between domains.

Deep Theory: Policy Evaluation Logic

# The IAM evaluation flow (simplified): 1. Start with IMPLICIT DENY (default) 2. Evaluate all applicable policies: - Identity-based policies (attached to user/group/role) - Resource-based policies (on the S3 bucket, SQS queue, etc.) - Permission boundaries (max permissions ceiling) - Session policies (for assumed roles) - SCPs (organization-wide guardrails) 3. If ANY policy has an EXPLICIT DENY → DENIED (game over) 4. If ANY policy has an ALLOW → ALLOWED 5. Otherwise → DENIED (implicit deny) # Critical insight: DENY always beats ALLOW

Policy Examples

# Allow reading from a specific S3 bucket only from a specific VPC { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Action": ["s3:GetObject"], "Resource": "arn:aws:s3:::prod-data/*", "Condition": { "StringEquals": { "aws:SourceVpc": "vpc-abc123" } } }] } # Deny everything except in us-east-1 (SCP) { "Version": "2012-10-17", "Statement": [{ "Effect": "Deny", "Action": "*", "Resource": "*", "Condition": { "StringNotEquals": { "aws:RequestedRegion": "us-east-1" } } }] }

🧠 If a policy allows s3:* and another policy explicitly denies s3:DeleteBucket, what happens when you try to delete?

Explicit Deny ALWAYS wins over Allow in IAM policy evaluation. This is a fundamental AWS security principle.

🧠 How does an EC2 instance get AWS credentials without access keys?

IAM Roles attached via Instance Profiles provide temporary credentials via the Instance Metadata Service, auto-rotated by AWS.
