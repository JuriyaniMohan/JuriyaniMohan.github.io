🔐 What is IAM?

IAM (Identity and Access Management) is a global AWS service that lets you control WHO can access WHAT in your AWS account. It is the foundation of all AWS security.

Scope
Global — not tied to any Region
Cost
Always FREE — no charge for IAM
Root Account
Created when you set up AWS — has FULL access. Never use for daily tasks!
Default Access
New IAM users have ZERO permissions (implicit deny)
⚠️
Root Account Warning: The root account should ONLY be used for: initial account setup, creating first IAM admin user, and changing account settings. Enable MFA on root immediately. Never create access keys for root.

🧱 IAM Building Blocks — The Big Picture

👤 IAM Users

An IAM user represents a person or application that needs to interact with AWS.

Console Access
Username + password (+ optional MFA)
Programmatic Access
Access Key ID + Secret Access Key
Default Permissions
NONE — must be explicitly granted
Limit
5,000 IAM users per account (hard limit)
🚫
Never embed access keys in code! Use IAM Roles for EC2/Lambda instead. Access keys in code is a top security anti-pattern. If keys are leaked, rotate them immediately.

👥 IAM Groups

Groups are collections of IAM users. Policies attached to the group apply to all members.

  • A user can belong to up to 10 groups
  • Groups cannot be nested (no groups within groups)
  • Groups are not identities — you can't reference a group in a resource policy's Principal
  • There is no default "All Users" group — you must create one manually if needed
💡
Best Practice: Always assign permissions through Groups, not directly to Users. This makes management scalable — when Alice changes teams, just move her to a different group.

🎭 IAM Roles

Roles are IAM identities with temporary credentials. They are assumed by trusted entities (users, services, accounts).

When to Use Roles (Critical for Exam!)

🖥️
EC2 Instance Role
Give EC2 instances permissions to access S3, DynamoDB, etc. without embedding access keys.
⚡
Lambda Execution Role
Every Lambda function needs a role to access other AWS services. Called the "execution role."
🔄
Cross-Account Access
User in Account A assumes a role in Account B to access resources there. No need to create users in both accounts.
🌐
Federation (SSO)
External users (SAML 2.0, OIDC, Active Directory) assume roles to get temporary AWS access.

How Role Assumption Works

🎯
Exam Tip: When the question says "an EC2 instance needs to access S3" — the answer is ALWAYS IAM Role (Instance Profile), never access keys.

📜 IAM Policies — Deep Dive

Policies are JSON documents that define permissions. They are the core of IAM — every access decision goes through policy evaluation.

Policy Structure (VERY Important for Exam)

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowS3Read", // Optional identifier
      "Effect": "Allow", // Allow or Deny
      "Action": [ // What actions are allowed
        "s3:GetObject",
        "s3:ListBucket"
      ],
      "Resource": [ // Which resources
        "arn:aws:s3:::my-bucket",
        "arn:aws:s3:::my-bucket/*"
      ],
      "Condition": { // Optional conditions
        "IpAddress": {
          "aws:SourceIp": "203.0.113.0/24"
        }
      }
    }
  ]
}

Policy Evaluation Logic — The Golden Rule

Types of Policies

TypeAttached ToKey Points
AWS ManagedUsers, Groups, RolesCreated by AWS. Examples: AmazonS3FullAccess, AdministratorAccess. Can't edit.
Customer ManagedUsers, Groups, RolesCreated by you. Reusable, versioned (up to 5 versions). Best practice for custom needs.
InlineSingle User, Group, or RoleEmbedded in the identity. Deleted when identity is deleted. Use for strict 1:1 mapping.
Resource-basedResources (S3, SQS, etc.)Attached to the resource, not the identity. Has a Principal field specifying WHO.
Permissions BoundaryUsers, RolesSets the MAXIMUM permissions. Even if a policy allows more, the boundary limits it.
SCP (Service Control Policy)AWS Organizations (OUs, accounts)Limits what services/actions an entire account can use. Doesn't grant — only restricts.

🧩 ARN Format (Amazon Resource Name)

Every AWS resource has a unique ARN. Understanding the format is essential for writing policies.

// General format:
arn:partition:service:region:account-id:resource-type/resource-id

// Examples:
arn:aws:s3:::my-bucket // S3 bucket (no region/account for S3)
arn:aws:s3:::my-bucket/* // All objects IN the bucket
arn:aws:ec2:us-east-1:123456789012:instance/i-abc123 // Specific EC2 instance
arn:aws:iam::123456789012:user/alice // IAM user (global, no region)
arn:aws:lambda:ap-southeast-1:123456789012:function:myFunc // Lambda function
⚠️
Common Exam Trap: arn:aws:s3:::my-bucket refers to the bucket itself. arn:aws:s3:::my-bucket/* refers to the objects inside. You often need BOTH in a policy!

🔀 Identity-based vs Resource-based Policies

FeatureIdentity-basedResource-based
Attached toUsers, Groups, RolesResources (S3, SQS, Lambda, KMS)
Has Principal field?NO (identity IS the principal)YES — specifies who can access
Cross-accountNeeds role assumptionCan directly grant cross-account access
ExampleIAM policy on a userS3 bucket policy, SQS queue policy
🎯
Exam Tip: For cross-account S3 access, you can use either: (1) Role assumption, OR (2) S3 bucket policy with the other account's ARN as Principal. Resource-based policies don't require the user to give up their original permissions.

🌐 Identity Federation

Federation allows external users (corporate AD, Google, Facebook) to access AWS without creating IAM users.

Federation TypeProtocolUse Case
SAML 2.0SAMLEnterprise SSO (Active Directory, Okta, Azure AD)
Web Identity (OIDC)OpenID ConnectMobile apps (Login with Google/Facebook/Amazon)
AWS SSO / IAM Identity CenterSAML + SCIMCentralized access to multiple AWS accounts (recommended)
Custom Identity BrokerCustomLegacy apps that can't use SAML/OIDC directly
💡
Exam Favorite: "Company uses Active Directory and needs SSO to AWS" → AWS IAM Identity Center (formerly AWS SSO) is the recommended answer. SAML 2.0 federation is the older approach. Amazon Cognito is for mobile/web app users.

🏢 AWS Organizations & SCPs

AWS Organizations lets you manage multiple AWS accounts centrally. Service Control Policies (SCPs) set guardrails.

Management Account
The master account that creates the organization. SCPs do NOT apply to it.
OUs (Organizational Units)
Logical groupings of accounts (e.g., Dev, Staging, Prod)
SCPs
Define maximum permissions for accounts/OUs. They don't grant — only restrict.
Consolidated Billing
Single bill for all accounts. Volume discounts apply across all accounts.
⚠️
Key Exam Point: SCPs affect all users and roles in member accounts — including the root user of those accounts! But SCPs never affect the management account itself. SCPs don't grant permissions — they only set boundaries.

🔐 Multi-Factor Authentication (MFA)

MFA adds a second layer of security beyond passwords. AWS strongly recommends MFA for all users, especially root.

MFA Device Options

DeviceTypeDetails
Virtual MFASoftwareGoogle Authenticator, Authy, Microsoft Authenticator. Free, most common.
U2F Security KeyHardwareYubiKey by Yubico. Physical USB key. Supports multiple root & IAM users.
Hardware MFAHardwareGemalto token. Key fob or display card. Must be purchased.
✅
Best Practice: Enable MFA on the root account FIRST. Then enable MFA on all IAM users. You can enforce MFA via IAM policies using the condition key aws:MultiFactorAuthPresent.

🔑 Password Policy

You can configure account-wide password requirements:

  • Minimum password length
  • Require uppercase, lowercase, numbers, special characters
  • Allow/prevent password reuse (remember last N passwords)
  • Password expiration (force rotation every N days)
  • Allow users to change their own password

📊 IAM Credentials Report & Access Advisor

Credentials Report
Account-level. Lists ALL users and status of their credentials (password, access keys, MFA). CSV download. Great for auditing.
Access Advisor
User-level. Shows which services a user accessed and when. Use to identify and remove unused permissions (least privilege).
🎯
Exam Tip: "Audit all IAM users' credentials" → Credentials Report. "Find unused permissions for a specific user" → Access Advisor. Know the difference!

✅ IAM Best Practices Checklist

These are heavily tested on the exam and are real-world critical:

Create an IAM admin user immediately. Lock root credentials, enable MFA, and store securely. Only use root for tasks that require it (like changing account billing settings).

Grant only the permissions required to perform a task — nothing more. Start with zero permissions and add as needed. Use IAM Access Advisor to identify and remove unused permissions.

Never attach policies directly to users. Create groups (Admins, Developers, ReadOnly) and assign users to groups. When someone changes roles, just move them to a different group.

EC2, Lambda, ECS — all should use IAM Roles, never hardcoded access keys. Roles provide temporary credentials that rotate automatically.

Enable MFA on root first, then all IAM users. Use conditional policies to enforce MFA for sensitive operations.

Set password rotation policies. Rotate access keys regularly. Use IAM Credentials Report to audit key age.

AWS maintains these policies and updates them. Use customer managed policies for custom requirements. Avoid inline policies except for strict 1:1 relationships.

When you want to allow developers to create roles but limit what permissions those roles can have, use permissions boundaries. The boundary sets the maximum.

🧠 Permissions Boundaries

A permissions boundary is an advanced feature that sets the maximum permissions an IAM entity can have.

🆔 IAM Identity Center (AWS SSO)

The recommended way to manage access for a multi-account organization.

  • Single sign-on to multiple AWS accounts and business applications
  • Integrates with Active Directory, Okta, Azure AD (SAML 2.0)
  • Built-in identity store or connect external IdP
  • Permission Sets = collections of policies assigned to users/groups per account
  • Centralized access management via AWS Organizations
🎯
Exam Tip: Any question about "centralized access management across multiple AWS accounts" → IAM Identity Center. It replaced the old AWS SSO naming.
