Day 4 - IAM Roles and Security

Think like an AWS security architect

Day 4 takes IAM from basic concepts into real design decisions. This is where you learn how access is delegated, how one account trusts another, how companies connect existing identity systems to AWS, and how security controls fit around IAM.

If Day 3 taught you the building blocks, Day 4 teaches you how those blocks are used in real architecture.

Main Idea

Role-based access

Roles are how AWS safely gives temporary permission to services, users, and even other accounts.

Main Idea

Trust and delegation

A role is useful only when the right entity is trusted to assume it.

Main Idea

Enterprise identity

Large organizations usually connect existing identity systems to AWS instead of creating separate IAM users for everyone.

IAM Roles

Why roles are such a big deal

Roles are one of the most important AWS security concepts because they reduce long-term credential exposure and enable temporary, delegated access.

  • A role is not tied to one person forever. It can be assumed when needed.
  • Roles usually produce temporary credentials. That is safer than leaving permanent secrets everywhere.
  • AWS services commonly use roles. EC2, Lambda, and others should usually assume roles instead of storing access keys.
  • People can also assume roles. This is useful for temporary admin access or cross-account work.
Strong trainer memory line: Role = delegated access for a limited time.
Role Use Cases

When roles are the right answer

EC2 to AWS

An instance needs S3 or DynamoDB access. Attach a role to the instance.

Lambda to AWS

A function needs CloudWatch logging, SQS access, or DynamoDB access. Use an execution role.

User temporary elevation

A user assumes a more privileged role only when needed instead of always having admin rights.

Cross-account access

One AWS account assumes a role in another account to perform a task safely.

Trust Policies

Every role has two sides

SideWhat it answersSimple meaning
Trust policyWho can assume this role?The entry rule
Permissions policyWhat can this role do once assumed?The action rule
Easy way to say it: trust decides who gets in, permissions decide what happens after they get in.
Exam Trap

What people misunderstand

  • A role does not magically run by itself. Something trusted must assume it.
  • A role can trust one entity but still do nothing useful if its permissions are weak.
  • A role can have strong permissions but still be safe if trust is tightly limited.
Trainer warning: many IAM mistakes come from understanding permissions but forgetting trust.
Cross-Account Access

How account A safely works in account B

Create a role in account B that trusts account A.
Attach permissions to that role inside account B.
A user or service in account A assumes the role.
AWS issues temporary credentials for the role session.
The caller acts inside account B using the permissions of that role.
This is one of the cleanest ways to share access between AWS accounts without sharing passwords or long-term keys.
When It Appears

Real cross-account scenarios

  • A security account needs to audit many workload accounts.
  • A central DevOps account deploys infrastructure into multiple application accounts.
  • One account needs limited access to another account's S3, KMS, or operational resources.
Architecture takeaway: cross-account roles support separation of duties and better multi-account governance.
Federation

Identity that starts outside AWS

Federation means AWS trusts an external identity provider. Instead of creating separate AWS users for everyone, people authenticate with an existing identity system and then receive AWS access.

  • Good for companies that already manage employee identities centrally.
  • Reduces the need to create large numbers of IAM users.
  • Usually leads to temporary AWS access rather than permanent credentials.
When It Is the Answer

Exam signals for federation

Existing corporate login

The company wants employees to use their current enterprise credentials.

Central identity management

The company does not want a separate IAM user lifecycle inside AWS for everyone.

Temporary access preferred

The design should avoid long-lived AWS credentials when possible.

If the question says employees should sign in with existing company credentials, federation is a very strong signal.
Security Controls

What strengthens IAM in practice?

  • MFA adds another layer to sign-in.
  • Password policy helps enforce stronger console access hygiene.
  • Credential rotation reduces risk around long-lived keys.
  • CloudTrail records actions for audit and investigation.
  • Access Analyzer helps detect broad or unintended access.
IAM is not only about granting access. It is also about controlling, reviewing, and proving that access was used correctly.
Security Thinking

How an architect answers IAM security questions

For services

Use roles, not hardcoded keys.

For humans

Use least privilege and MFA.

For auditing

Use CloudTrail to record activity.

For suspicious access review

Use analysis tools and review policies for overexposure.

Common bad pattern: embedding long-term AWS keys inside EC2 instances, code repositories, or configuration files.
Architecture Patterns

What a certified trainer wants you to recognize

Pattern 1: Application on EC2 needs S3 access

Attach an IAM role to the EC2 instance with the required permissions. This is safer than storing access keys on disk.

Pattern 2: Central operations team manages many accounts

Use cross-account roles so the central team can assume controlled access into workload accounts.

Pattern 3: Employees use enterprise login

Use federation so AWS access is based on the organization's identity provider rather than separate IAM users for every employee.

Common Mistakes

Where learners often lose marks

  • Choosing IAM users instead of roles for AWS services.
  • Forgetting that roles need both trust and permissions.
  • Missing the signal for federation when corporate identity already exists.
  • Not recognizing cross-account access as a role-based trust design.
  • Ignoring the security risk of long-term embedded credentials.
Trainer shortcut: when the question says temporary, delegated, cross-account, or AWS service access, roles should be one of your first thoughts.

A Lambda function needs to write logs to CloudWatch and read from DynamoDB. What is the recommended design?

Lambda should assume an IAM execution role with the required permissions.

Question 2

What tells AWS who is allowed to assume a role?

The trust policy defines who or what can assume the role.

Question 3

A company wants employees to access AWS using existing enterprise credentials. What is the best fit?

Federation lets AWS trust an external identity provider instead of managing separate AWS identities for everyone.

Question 4

A security account needs to inspect resources in many workload accounts. Which pattern is most appropriate?

Cross-account roles are the standard pattern for controlled multi-account access.

If roles are available, they are usually safer than storing long-term secrets on servers.
