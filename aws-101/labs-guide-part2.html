LAB 10.1Create Hosted Zone & Record Sets
$$Beginner
▼

🎯 Objective

Create a hosted zone and various DNS record types.

# Create hosted zone (you need a domain — or use a private hosted zone for practice) ZONE_ID=$(aws route53 create-hosted-zone --name lab.internal \ --vpc VPCRegion=ap-southeast-1,VPCId=$LAB_VPC \ --caller-reference $(date +%s) \ --hosted-zone-config PrivateZone=true \ --query 'HostedZone.Id' --output text) # Create A record pointing to EC2 aws route53 change-resource-record-sets --hosted-zone-id $ZONE_ID --change-batch '{ "Changes": [{ "Action": "CREATE", "ResourceRecordSet": { "Name": "web.lab.internal", "Type": "A", "TTL": 300, "ResourceRecords": [{"Value": "'$PUBLIC_IP'"}] } }] }' # Create CNAME record aws route53 change-resource-record-sets --hosted-zone-id $ZONE_ID --change-batch '{ "Changes": [{ "Action": "CREATE", "ResourceRecordSet": { "Name": "app.lab.internal", "Type": "CNAME", "TTL": 300, "ResourceRecords": [{"Value": "web.lab.internal"}] } }] }'
💡
Exam: A record = domain → IPv4. AAAA = domain → IPv6. CNAME = domain → domain (can't use at zone apex). Alias = AWS-specific, works at zone apex, free for AWS resources.
LAB 10.2Route 53 Routing Policies
$$Intermediate
▼

🎯 Objective

Configure different routing policies and understand their behavior.

Routing Policy Comparison (for reference while building):

  • Simple — One record, one or more IPs (random selection). No health checks.
  • Weighted — Split traffic by percentage (e.g., 70/30 blue-green). Each record has a weight.
  • Latency — Route to the Region with lowest latency for the user.
  • Failover — Active-Passive. Primary + Secondary with health check.
  • Geolocation — Route based on user's geographic location (country/continent).
  • Geoproximity — Route based on proximity with bias (shift traffic). Requires Traffic Flow.
  • Multi-value — Return multiple IPs with health checks (like simple + health checks).

Weighted Routing (Console)

Route 53 → Hosted Zone → Create Record → Routing: Weighted → Record 1: IP-A, Weight: 70 → Record 2: IP-B, Weight: 30 → Same record name → Use different Set IDs.

Failover Routing

Create health check for primary endpoint → Create Failover record (Primary) with health check → Create Failover record (Secondary) as standby.

🎯
Exam Patterns: "Blue-green deployment" → Weighted. "Active-passive DR" → Failover. "Serve users from nearest Region" → Latency. "Comply with local regulations" → Geolocation. "Gradually shift traffic" → Weighted or Geoproximity.

LAB 11.1CloudFront Distribution with S3 Origin + OAC
Free TierIntermediate
▼

🎯 Objective

Serve S3 content through CloudFront with Origin Access Control (block direct S3 access).

  1. Create S3 bucket with Block All Public Access ON
  2. Upload index.html to the bucket
  3. CloudFront → Create Distribution → Origin: S3 bucket → Origin Access: OAC (Origin Access Control)
  4. CloudFront will generate a bucket policy — copy and apply to S3
  5. Default root object: index.html
  6. Wait ~5 min for deployment → access via CloudFront URL dxxxxxx.cloudfront.net
  7. Direct S3 URL should return Access Denied — only CloudFront can access it!
🎯
Exam: OAC is the modern replacement for OAI (Origin Access Identity). "Restrict S3 access to only CloudFront" → OAC + bucket policy. OAC supports KMS encryption; OAI doesn't.

🧹 Cleanup

Disable distribution → Wait → Delete distribution → Delete S3 bucket

LAB 11.2CloudFront with ALB Origin (Dynamic Content)
$$Intermediate
▼

🎯 Objective

Use CloudFront to serve dynamic content from ALB + cache static assets from S3.

  1. Create CloudFront distribution with two origins: S3 (static) + ALB (dynamic)
  2. Create behaviors: /api/* → ALB origin, Default (*) → S3 origin
  3. Configure cache policies: S3 gets long TTL (1 day), ALB gets short TTL or no cache
💡
Exam Pattern: "Serve static + dynamic content with low latency globally" → CloudFront with multiple origins and path-based behaviors. S3 for assets, ALB for API.

LAB 12.1SQS — Standard & FIFO Queues
FreeBeginner
▼
# Create Standard Queue STD_URL=$(aws sqs create-queue --queue-name lab-standard-queue \ --attributes '{"VisibilityTimeout":"30","MessageRetentionPeriod":"86400"}' \ --query 'QueueUrl' --output text) # Create FIFO Queue FIFO_URL=$(aws sqs create-queue --queue-name lab-fifo-queue.fifo \ --attributes '{"FifoQueue":"true","ContentBasedDeduplication":"true"}' \ --query 'QueueUrl' --output text) # Send messages aws sqs send-message --queue-url $STD_URL --message-body "Hello from standard queue!" aws sqs send-message --queue-url $FIFO_URL --message-body "Hello from FIFO queue!" --message-group-id "group1" # Receive messages aws sqs receive-message --queue-url $STD_URL --max-number-of-messages 5 aws sqs receive-message --queue-url $FIFO_URL --max-number-of-messages 5 # Create Dead Letter Queue DLQ_URL=$(aws sqs create-queue --queue-name lab-dlq --query 'QueueUrl' --output text) DLQ_ARN=$(aws sqs get-queue-attributes --queue-url $DLQ_URL --attribute-names QueueArn --query 'Attributes.QueueArn' --output text) # Set DLQ on standard queue (after 3 failed receives) aws sqs set-queue-attributes --queue-url $STD_URL \ --attributes '{"RedrivePolicy":"{\"deadLetterTargetArn\":\"'$DLQ_ARN'\",\"maxReceiveCount\":\"3\"}"}'
🎯
Exam: Standard = unlimited throughput, at-least-once, best-effort order. FIFO = 300 msg/s (3000 with batching), exactly-once, guaranteed order. "Process orders in sequence" → FIFO. "Maximum throughput" → Standard. DLQ = capture failed messages.

🧹 Cleanup

aws sqs delete-queue --queue-url $STD_URL aws sqs delete-queue --queue-url $FIFO_URL aws sqs delete-queue --queue-url $DLQ_URL

LAB 13.3Migration Strategies — 6 R's Decision Exercise
FreeBeginner
▼

🎯 Exercise (No AWS resources needed)

For each scenario below, decide which R strategy applies:

  • Rehost (Lift & Shift) — Move as-is to EC2
  • Replatform (Lift, Tinker, Shift) — Minor optimization (e.g., move to RDS)
  • Repurchase — Switch to SaaS (e.g., CRM → Salesforce)
  • Refactor — Re-architect for cloud-native (e.g., microservices + Lambda)
  • Retire — Turn off (not needed)
  • Retain — Keep on-premises (not ready to migrate)

Scenarios:

  1. "Move legacy Java app to AWS quickly for data center exit" → Rehost
  2. "Move self-managed MySQL to managed DB" → Replatform (to RDS)
  3. "Replace on-prem email server" → Repurchase (to WorkMail/O365)
  4. "Break monolith into microservices" → Refactor
  5. "Old test server nobody uses" → Retire
  6. "Mainframe with complex dependencies" → Retain (for now)

LAB 16.1Multi-Tier Architecture (Web → App → DB)
$$Advanced
▼

🎯 Build This Architecture:

  1. VPC with 6 subnets (2 public, 2 private-app, 2 private-db across 2 AZs)
  2. ALB in public subnets → routes to EC2 web servers in private-app subnets
  3. Web servers connect to RDS MySQL Multi-AZ in private-db subnets
  4. NAT Gateway in public subnet for web server updates
  5. Security Groups: ALB (80/443) → Web (8080 from ALB SG) → DB (3306 from Web SG)
🎯
Exam Pattern: This is THE classic 3-tier architecture. Know it cold. Web tier (public) → App tier (private) → DB tier (private). Each tier has its own SG referencing the tier above.

LAB 16.4Disaster Recovery — Pilot Light
$$Advanced
▼

🎯 Concept Build:

  1. Primary Region (ap-southeast-1): Full stack — ALB, ASG, RDS Multi-AZ
  2. DR Region (ap-northeast-1): Pilot Light — RDS Read Replica only (core data running)
  3. During failover: Promote Read Replica → Launch EC2/ASG → Update Route 53 to DR Region

DR Strategy Comparison:

  • Backup & Restore — Cheapest, slowest (hours). Just backups in S3.
  • Pilot Light — Core DB running in DR, scale up on failover (minutes).
  • Warm Standby — Scaled-down version running in DR (minutes, faster).
  • Multi-Site Active-Active — Full stack in both Regions. Instant failover. Most expensive.
LAB 16.5High Availability Architecture Checklist
FreeBeginner
▼

🎯 Verify Your Architecture Has:

  • ☐ Resources deployed across at least 2 AZs
  • ☐ Auto Scaling Group with min ≥ 2 instances
  • ☐ Load Balancer distributing traffic across AZs
  • ☐ RDS Multi-AZ for database high availability
  • ☐ S3 for static assets (11 nines durability)
  • ☐ CloudFront for global content delivery
  • ☐ Route 53 health checks with failover routing
  • ☐ EBS snapshots on schedule for backup
  • ☐ Cross-Region replication for DR (S3 CRR, RDS cross-Region read replica)
  • ☐ CloudWatch alarms for monitoring and auto-recovery
  • ☐ SNS notifications for alerting
  • ☐ No single points of failure — everything redundant
