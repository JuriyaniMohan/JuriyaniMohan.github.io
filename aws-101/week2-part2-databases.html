The Database Decision Framework

🧠 The Architect's First Question

When the exam gives you a database scenario, your decision tree is: (1) Relational or NoSQL? → (2) Managed or self-managed on EC2? → (3) Read-heavy or write-heavy? → (4) Latency requirements? → (5) Scale pattern (vertical vs horizontal)?

🏗️ AWS Database Decision Tree

🐘 Amazon RDS

Managed relational DB: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server. AWS handles patching, backups, HA. You manage schema & queries.

~25% of DB questions

⚡ Amazon Aurora

AWS-built relational engine. 5x MySQL / 3x Postgres performance. Auto-scales storage, 6-way replication, up to 15 read replicas.

~20% of DB questions

⚡ DynamoDB

Serverless NoSQL. Single-digit millisecond latency at any scale. Key-value + document model. Auto-scales. Global Tables for multi-region.

~30% of DB questions

Amazon RDS — Relational Database Service

Why RDS Exists

Running a production database on EC2 means you handle: OS patching, DB engine upgrades, backups, replication, failover, monitoring, and security. RDS takes all of that off your plate. You pick the engine, instance size, and storage — AWS handles the rest. Tradeoff: you can't SSH into the DB server or customize OS-level settings.

Supported Engines

MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server, and Amazon Aurora (separate tab). Each has slight feature differences in RDS, but the core concepts (Multi-AZ, Read Replicas, backups) apply to all.

🛡️

Multi-AZ vs Read Replicas — The Critical Distinction

🎯 EXAM HOT SPOT — #1 RDS Topic

Multi-AZ ≠ Read Replica. The exam will ALWAYS test this. Multi-AZ is for availability (failover). Read Replicas are for read performance (scaling reads). They solve different problems. You can (and should) use BOTH together.

Multi-AZ Architecture

Multi-AZ Deployment

  • Purpose: High Availability (disaster recovery)
  • Replication: Synchronous to standby in another AZ
  • Standby: NOT readable — purely for failover
  • Failover: Automatic, ~60-120 seconds. DNS endpoint unchanged.
  • When it triggers: AZ outage, instance failure, storage failure, OS patching
  • Cost: 2x (you pay for both instances)

Read Replicas

  • Purpose: Read scaling & performance
  • Replication: Asynchronous from primary
  • Readable: YES — offload SELECT queries
  • Count: Up to 5 read replicas per RDS instance
  • Cross-Region: Yes — can create replicas in other regions
  • Promotion: Can be promoted to standalone DB (breaks replication)
  • Network cost: Free within same region. Cross-region has data transfer charges.
⚠️ Common Exam Traps

Trap 1: "Use Multi-AZ to scale reads" — WRONG. Multi-AZ standby is NOT readable. Use Read Replicas for read scaling.

Trap 2: "Read Replicas provide synchronous replication" — WRONG. Read Replicas use ASYNC replication. There will be slight replication lag. If you need zero data loss, that's Multi-AZ.

Trap 3: "Promote a Read Replica for zero-downtime failover" — WRONG. Promotion creates a new standalone DB. It doesn't preserve the Multi-AZ failover mechanism.

💾

RDS Storage & Backups

Storage Options

  • gp3: Default SSD. Best for most workloads. Independent IOPS/throughput.
  • gp2: Legacy SSD. IOPS scales with size (3 IOPS per GiB).
  • io1/io2: Provisioned IOPS for databases needing consistent I/O.
  • Storage Auto Scaling: Automatically increases storage when usage exceeds threshold. Set a maximum storage limit.

Backup Strategy

  • Automated Backups: Daily full backup + transaction logs every 5 minutes. Retention: 1-35 days. Point-in-time recovery to any second within retention.
  • Manual Snapshots: User-triggered. Persist until you delete them (no expiry).
  • Restore: Creates a NEW RDS instance. Cannot restore to existing instance.
  • Cross-Region: Snapshots can be copied to another region for DR.

RDS Security

  • Encryption at rest: KMS (AES-256). Must be enabled at creation time. Cannot encrypt an existing unencrypted DB directly — must snapshot → copy with encryption → restore.
  • Encryption in transit: SSL/TLS connections. Force with rds.force_ssl=1 parameter.
  • IAM Authentication: Instead of passwords, use IAM roles + auth tokens (15 min lifetime). Works with MySQL and PostgreSQL.
  • Network: Always deploy in a private subnet. Use Security Groups to control access. No public IP by default.
🏭 Production Architecture Pattern

3-Tier Web App with RDS: ALB → EC2 (private subnet) → RDS Multi-AZ (private subnet) + 2 Read Replicas for read-heavy endpoints. Automated backups with 35-day retention. Cross-region snapshot copy for DR. IAM authentication for EC2-to-RDS. This is the gold standard for the exam.

Amazon Aurora — Cloud-Native Relational

Why Aurora Exists

AWS re-engineered the relational database from scratch for the cloud. Instead of the traditional "one server, one disk" model, Aurora separates compute from storage. The storage layer auto-replicates 6 copies across 3 AZs. Result: 5x MySQL performance, 3x PostgreSQL performance, with cloud-native resilience. It's what AWS recommends when you say "I need RDS but better."

Aurora Serverless v2

  • Auto-scales compute capacity in fine-grained increments (0.5 ACU steps)
  • Scales from minimum to maximum ACU in seconds
  • Pay per ACU (Aurora Capacity Unit) per second
  • Use when: Unpredictable/intermittent workloads, dev/test environments, multi-tenant apps
  • Supports reader instances, Multi-AZ, Global Database
🎯 Exam Tip

"Variable workload, don't want to manage capacity" → Aurora Serverless. "Infrequently used application database" → Aurora Serverless with minimum ACU = 0 (pauses and costs nothing when idle).

Aurora Global Database

  • 1 primary region (read/write) + up to 5 secondary regions (read-only)
  • Cross-region replication lag: typically under 1 second
  • Secondary region can be promoted in < 1 minute for DR
  • Up to 16 read replicas per secondary region
  • Use when: Global apps needing low-latency reads worldwide, or cross-region DR with near-zero RPO
🏭 When to Choose Aurora Over RDS

Choose Aurora when: (1) You need more than 5 read replicas, (2) You need sub-30-second failover, (3) Storage needs to auto-scale beyond 64 TiB, (4) You need global database with < 1s replication, (5) You want backtrack to rewind errors without restoring from backup. If none of these apply and cost is a concern, standard RDS is fine.

Amazon DynamoDB — Serverless NoSQL

Why DynamoDB Exists

Relational databases hit scaling walls: joins get expensive, sharding is complex, and vertical scaling has limits. DynamoDB was built from the ground up for horizontal scaling. It's a fully managed, serverless key-value + document database that delivers single-digit millisecond performance at any scale. No servers to manage, no capacity planning (if using on-demand mode).

DynamoDB Core Concepts

  • Table — Collection of items (like rows). No fixed schema except the primary key.
  • Item — A single record (max 400 KB).
  • Primary Key — Two types:
    • Partition Key (PK) — Single attribute. Must be unique. DynamoDB hashes this for distribution.
    • Partition Key + Sort Key (PK + SK) — Composite. PK determines partition, SK determines ordering within partition. Together must be unique.
  • Attributes — Each item can have different attributes (schemaless). Can be scalar, set, map, or list.
📊

Capacity Modes

Provisioned Mode

  • You specify Read Capacity Units (RCU) and Write Capacity Units (WCU)
  • 1 RCU = 1 strongly consistent read/sec for up to 4 KB
  • 1 RCU = 2 eventually consistent reads/sec for up to 4 KB
  • 1 WCU = 1 write/sec for up to 1 KB
  • Can enable Auto Scaling to adjust based on demand
  • Cheaper for predictable, steady workloads
  • Reserved Capacity — commit for 1 or 3 years for significant discounts

On-Demand Mode

  • No capacity planning. Scales automatically.
  • Pay per request (read/write)
  • ~2.5x more expensive per request than provisioned
  • Best for: unpredictable workloads, new apps, spiky traffic
  • Can switch between modes once every 24 hours
🎯 Exam Tip

"Unpredictable traffic pattern" or "don't want to manage capacity" → On-Demand. "Steady, predictable workload" and "minimize cost" → Provisioned with Auto Scaling.

🔍

Indexes — Enabling Flexible Queries

Global Secondary Index (GSI)

  • Completely new primary key (different PK + optional SK)
  • Can be created at any time
  • Has its own provisioned throughput (separate RCU/WCU)
  • Supports eventual consistency only
  • Use when: You need to query by a different attribute than the table's PK

Local Secondary Index (LSI)

  • Same Partition Key, different Sort Key
  • Must be created at table creation (cannot add later!)
  • Shares the table's throughput
  • Supports strongly consistent reads
  • Use when: You need alternate sort orders on the same partition key
⚠️ GSI Throttling Trap

If a GSI runs out of WCU, the base table gets throttled too — even if the base table has plenty of WCU. This is a common exam scenario: "writes to the table are being throttled but the table has sufficient WCU" → check GSI capacity.

🚀

DynamoDB Advanced Features

DAX (DynamoDB Accelerator)

  • Fully managed, in-memory cache for DynamoDB
  • Reduces read latency from milliseconds to microseconds
  • Compatible with existing DynamoDB API calls (no code changes to queries)
  • Multi-AZ with up to 10 nodes
  • Use when: Read-heavy workloads, repeated reads on same items, need microsecond latency
  • NOT for: Write-heavy workloads, or workloads needing strongly consistent reads
🎯 DAX vs ElastiCache

DAX = caching for DynamoDB specifically (transparent). ElastiCache = general-purpose caching for any data source. "Cache DynamoDB reads" → DAX. "Cache RDS query results" → ElastiCache.

Global Tables

  • Multi-region, multi-active (read/write in ANY region)
  • DynamoDB handles bi-directional replication
  • Replication latency: typically under 1 second
  • Requires DynamoDB Streams enabled
  • Use when: Global applications needing low-latency access from multiple regions, disaster recovery
  • Last-writer-wins conflict resolution

DynamoDB Streams

  • Captures time-ordered sequence of item-level changes (insert, update, delete)
  • Retained for 24 hours
  • Can trigger Lambda functions for event-driven processing
  • Use cases: Cross-region replication (Global Tables), audit logging, real-time analytics, trigger workflows

TTL (Time to Live)

  • Automatically delete items after a specified timestamp
  • No extra cost — deletion happens in background
  • Deleted items are also removed from indexes
  • Use cases: Session data, temporary tokens, logs with expiry, regulatory data retention
🏭 DynamoDB Design Patterns for the Exam
  • "Session store" → DynamoDB with TTL
  • "Gaming leaderboard" → DynamoDB with composite key (GameID + Score as SK)
  • "IoT device data" → DynamoDB with DeviceID (PK) + Timestamp (SK)
  • "Shopping cart" → DynamoDB (session-based, auto-scaling)
  • "Need ACID transactions across tables" → DynamoDB Transactions (or RDS if complex joins needed)

Amazon ElastiCache

Why ElastiCache Exists

Databases are fast, but reading from RAM is 100x+ faster. ElastiCache gives you a managed in-memory data store that sits between your application and database. Frequently accessed data (sessions, product info, leaderboards) is served from cache → DB load drops dramatically → latency drops to sub-millisecond.

Redis vs Memcached — The Decision

🎯 Exam Hot Spot

The exam ALWAYS tests Redis vs Memcached. The shortcut: Redis has everything. Memcached has multi-threading and simplicity. If the question doesn't specifically mention "multi-threaded" or "simple key-value cache," the answer is probably Redis.

Caching Strategies

  • Lazy Loading (Cache-Aside): Read from cache first. On miss, read from DB, then write to cache. Pros: only requested data is cached. Cons: cache miss = 3 round trips, stale data possible.
  • Write-Through: Write to cache AND DB on every write. Pros: cache always current. Cons: write penalty (every write hits both), cache filled with data that may never be read.
  • TTL (Time-to-Live): Set expiry on cached items. Combines benefits of both strategies. Prevents stale data from persisting indefinitely.

Common Use Cases

  • Session Store: Store user sessions in Redis with TTL. Stateless EC2 instances.
  • Leaderboards: Redis Sorted Sets — O(log N) insert and O(1) rank lookup.
  • DB Query Cache: Cache expensive query results. Reduce DB load.
  • Rate Limiting: Redis INCR with EXPIRE — count API calls per time window.
  • Real-time Analytics: Redis Streams for event processing.
🏭 Exam Pattern Shortcuts

"Reduce database load for read-heavy workload" → ElastiCache (Redis).
"Session management for stateless web tier" → ElastiCache Redis or DynamoDB with TTL.
"Leaderboard with real-time ranking" → Redis Sorted Sets.
"Simple cache, no persistence needed, multi-threaded" → Memcached.
"Cache with high availability and failover" → Redis with Multi-AZ.

Other Database Services

These appear less frequently on the exam but knowing their purpose is critical for "which database?" questions.

Amazon Redshift

Type: Columnar data warehouse (OLAP)

  • Based on PostgreSQL but NOT for OLTP
  • Columnar storage = 10x query performance for analytics
  • Massively parallel processing (MPP)
  • Redshift Spectrum: query data directly in S3 without loading
  • Exam trigger: "Data warehouse," "analytics on petabytes," "business intelligence," "OLAP"

Amazon DocumentDB

Type: MongoDB-compatible document database

  • Managed, auto-scales storage up to 64 TB
  • Multi-AZ with up to 15 read replicas
  • Exam trigger: "MongoDB," "document database," "JSON data model in the cloud"

Amazon Neptune

Type: Graph database

  • Managed graph DB for highly connected datasets
  • Supports Gremlin and SPARQL query languages
  • Multi-AZ with up to 15 read replicas
  • Exam trigger: "Social network," "recommendation engine," "knowledge graph," "fraud detection with relationships"

Amazon Keyspaces

Type: Apache Cassandra-compatible

  • Serverless, auto-scales
  • Compatible with CQL (Cassandra Query Language)
  • Exam trigger: "Cassandra," "migrate Cassandra workloads to AWS"

Amazon QLDB

Type: Quantum Ledger Database

  • Immutable, cryptographically verifiable transaction log
  • No decentralization (unlike blockchain) — centrally owned
  • Exam trigger: "Immutable ledger," "audit trail," "system of record for financial transactions"

Amazon Timestream

Type: Time-series database

  • Serverless, auto-scales
  • Built-in time-series analytics functions
  • Automatic tiering (recent in memory, historical in magnetic)
  • Exam trigger: "IoT sensor data," "time-series data," "DevOps metrics"

Exam Prep — Database Questions

Question 1

A company's web application experiences heavy read traffic during business hours and minimal traffic overnight. The application uses an RDS MySQL database. Users report slow page loads during peak hours. The company wants to improve read performance without modifying the application code significantly. What should the Solutions Architect recommend?

✅ Answer: B
Read Replicas offload read traffic from the primary. The application directs SELECT queries to the reader endpoint. Multi-AZ (A) is for HA, not read scaling — the standby is NOT readable. DynamoDB (C) requires significant application changes (different data model). Vertical scaling (D) is temporary and expensive — doesn't solve the fundamental read bottleneck.

Question 2

A global e-commerce company needs a database solution that provides single-digit millisecond reads and writes at any scale, supports automatic scaling, and requires minimal operational overhead. The data model is key-value with flexible attributes per item. Which solution is MOST appropriate?

✅ Answer: B
The keywords "key-value," "any scale," "minimal operational overhead," and "single-digit millisecond" all point directly to DynamoDB. On-demand mode = no capacity planning. Aurora Serverless (A) is relational — overkill for key-value. RDS (C) requires capacity management and is relational. ElastiCache (D) is a cache, not a primary database.

Question 3

A company uses DynamoDB for their application. Read latency needs to be reduced from single-digit milliseconds to microseconds for frequently accessed items. The team wants to achieve this with minimal application code changes. What should they implement?

✅ Answer: A
DAX is purpose-built as a write-through cache for DynamoDB. It uses the same DynamoDB API → minimal code changes (just change the SDK client endpoint). Provides microsecond read latency. ElastiCache (B) works but requires significant code changes to implement caching logic. Global Tables (C) reduces cross-region latency, not same-region read latency. More RCU (D) doesn't reduce latency below DynamoDB's inherent millisecond floor.

Question 4

An application needs a relational database that can automatically scale storage, support up to 15 read replicas, and provide sub-30-second failover. The company also needs the ability to "rewind" the database to a specific point in time without restoring from a backup. Which service meets ALL these requirements?

✅ Answer: B
Only Aurora provides ALL of these: auto-scaling storage (10GB → 128 TiB), up to 15 read replicas, sub-30-second failover, AND Backtrack (rewind without restore). Standard RDS (A,C) maxes out at 5 read replicas and 60-120 second failover, and has no backtrack feature. DynamoDB (D) is not relational and doesn't support SQL joins.

Question 5

A company needs to implement a caching layer for their RDS PostgreSQL database. Requirements: high availability with automatic failover, data persistence (cache survives restarts), and support for complex data types (sorted sets for leaderboard feature). Which solution should the architect choose?

✅ Answer: B
Redis provides: Multi-AZ with auto-failover (HA), persistence (survives restarts), and sorted sets (leaderboard feature). Memcached (A) has no persistence, no failover, no sorted sets. DAX (C) only works with DynamoDB, not RDS. CloudFront (D) is a CDN for content delivery, not database caching.

Question 6

A company is building a social media platform that needs to store and query complex relationships between users, posts, and interests. Queries need to traverse multiple levels of connections efficiently (e.g., "friends of friends who like topic X"). Which database service is BEST suited?

✅ Answer: C
"Social network," "complex relationships," "traverse connections" — these are textbook graph database use cases. Neptune is AWS's managed graph database optimized for relationship queries. DynamoDB (A) handles key-value, not relationship traversals. RDS (B) can do JOINs but they become very expensive for multi-hop relationship queries. DocumentDB (C) is for document/JSON data, not graph queries.
