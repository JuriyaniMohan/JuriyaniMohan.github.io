Week 2 Hands-On Labs

Why Labs Matter

The exam tests conceptual understanding, but building these services yourself creates muscle memory that makes exam questions feel like recalling lived experience instead of memorized facts. Every lab below is achievable within AWS Free Tier.

Lab 1: S3 Lifecycle & Versioning

Goal: Create a bucket with versioning, lifecycle policies, and cross-region replication.

1
Create S3 Bucket with Versioning

Create a bucket in your primary region. Enable versioning. Upload a file, modify it, upload again. Observe the version history in the console. Delete the file — note the delete marker. Restore by deleting the delete marker.

2
Configure Lifecycle Policy

Create a lifecycle rule: transition objects to Standard-IA after 30 days, Glacier Flexible after 90 days, and expire (delete) after 365 days. Apply to the entire bucket. Verify the rule appears in the Lifecycle configuration tab.

3
Enable Cross-Region Replication (CRR)

Create a destination bucket in another region with versioning enabled. Set up a replication rule on the source bucket. Upload a new file to the source — verify it appears in the destination. Note: existing objects are NOT replicated automatically.

4
Test Encryption

Set default encryption to SSE-S3. Upload a file — check the properties to confirm encryption. Change default to SSE-KMS with the default aws/s3 key. Upload another file. Compare the encryption headers.

⚠️ Cleanup

Delete all objects (including versions and delete markers), then delete both buckets. Empty a versioned bucket by going to Versions view and deleting all.

Lab 2: EBS Volume Operations

Goal: Attach volumes, create snapshots, encrypt, and move across AZs.

1
Launch EC2 + Attach EBS

Launch a t2.micro in AZ-A. Create a separate gp3 volume (10 GiB) in AZ-A. Attach it to the instance. SSH in, format with mkfs.ext4, mount it, write data.

2
Create Snapshot & Restore in Different AZ

Create a snapshot of the volume. Go to another AZ (AZ-B). Create a new volume from the snapshot in AZ-B. Launch an EC2 in AZ-B, attach and mount — verify your data is there. This is how you migrate data across AZs.

3
Encrypt an Unencrypted Volume

Take the unencrypted volume → Create snapshot → Copy snapshot with encryption → Create new encrypted volume from the encrypted snapshot. This is the only way to encrypt an existing unencrypted EBS volume.

Lab 3: RDS Multi-AZ + Read Replica

Goal: Deploy a production-grade RDS setup with HA and read scaling.

1
Create RDS MySQL with Multi-AZ

Use Free Tier (db.t3.micro, 20 GiB gp2). Check "Create a standby instance" for Multi-AZ. Deploy in your VPC's private subnets. Create a DB subnet group spanning 2+ AZs. Set up a security group allowing MySQL (3306) from your app subnet only.

2
Create a Read Replica

From the RDS console, select your DB → Actions → Create Read Replica. Note: it gets its own endpoint. Connect from your EC2 and run SELECT queries against the replica endpoint. Run INSERT queries only against the primary endpoint.

3
Simulate Failover

Go to RDS → Actions → Reboot → Check "Reboot With Failover." Monitor the Events tab. Note: the DNS endpoint stays the same, but it now points to the former standby. Connection briefly drops (60-120 sec).

4
Test Automated Backup & Restore

Check automated backups are enabled (retention = 7 days). Go to Snapshots → select a recent automated backup → Restore to Point in Time. This creates a NEW RDS instance. Verify data, then delete the restored instance.

Lab 4: DynamoDB Essentials

Goal: Create a table, understand capacity modes, work with indexes and TTL.

1
Create a Table with Composite Key

Create table UserSessions with Partition Key: UserID (String) and Sort Key: SessionTimestamp (Number). Use On-Demand mode. Add items with different attributes per item (schemaless nature).

2
Create a Global Secondary Index

Add GSI with PK: DeviceType, SK: SessionTimestamp. This lets you query by device type across all users. Note: GSI has its own capacity.

3
Enable TTL

Enable TTL on attribute ExpirationTime. Add items with ExpirationTime set to a Unix timestamp a few minutes in the future. Wait and observe automatic deletion. Free cleanup!

4
Enable DynamoDB Streams

Turn on Streams (NEW_AND_OLD_IMAGES). Create/update/delete items. Go to the Streams tab and observe the change records. In production, you'd connect a Lambda function here for event-driven processing.

Lab 5: ElastiCache Redis

Goal: Deploy a Redis cluster and understand caching patterns.

1
Create Redis Cluster

Use ElastiCache console → Create cluster → Redis. Choose cache.t3.micro (free tier eligible). Deploy in your VPC private subnets. Security group: allow port 6379 from your app subnet.

2
Connect & Test

SSH into an EC2 in the same VPC. Install redis-cli. Connect: redis-cli -h <endpoint> -p 6379. Test: SET mykey "hello" → GET mykey. Try: ZADD leaderboard 100 "player1" 250 "player2" → ZREVRANGE leaderboard 0 -1 WITHSCORES.

Real-World Architecture Patterns

Why Patterns Matter

The SAA-C03 exam presents scenarios and asks you to design or identify the correct architecture. These patterns appear repeatedly. Internalize them, and 70% of scenario questions become pattern-matching exercises.

Pattern 1: Three-Tier Web Application

Pattern 1 Explained

This is the #1 most tested architecture on the SAA-C03. Key decisions the exam tests:

  • Static content: S3 + CloudFront (never serve static files from EC2)
  • Web tier: ALB across multiple AZs for HA. Auto Scaling for elasticity.
  • Caching: ElastiCache Redis between app tier and database to reduce DB load
  • Database: Aurora Multi-AZ (writer) + Read Replicas for read-heavy workloads
  • Subnets: ALB in public subnets, EC2 and DB in private subnets

Pattern 2: Serverless API with DynamoDB

When the exam says "serverless," "auto-scaling," "minimal operational overhead," or "event-driven," this is the architecture:

  • API Gateway → Lambda → DynamoDB
  • API Gateway handles REST API, throttling, auth (Cognito)
  • Lambda processes business logic (no servers to manage)
  • DynamoDB in on-demand mode (auto-scales, pay per request)
  • Add DAX for microsecond caching if read-heavy
  • Add DynamoDB Streams → Lambda for event-driven processing

Pattern 3: Data Lake on S3

When the exam mentions "analytics," "query data in place," "data lake," or "cost-effective analysis of large datasets":

  • S3 as the central data lake (all data lands here)
  • Kinesis Data Firehose for streaming data ingestion
  • Glue for ETL and schema discovery (Glue Crawlers)
  • Athena for serverless SQL queries directly on S3
  • QuickSight for BI dashboards
  • Lifecycle policies: Standard → IA → Glacier for cost optimization

Pattern 4: Disaster Recovery Strategies

StrategyRPO/RTOCostHow
Backup & Restore Hours 💰 Lowest S3 cross-region backups, RDS snapshots, AMIs. Restore when needed.
Pilot Light 10s of minutes 💰💰 Core DB running in DR region (RDS replica). Scale up compute on failure.
Warm Standby Minutes 💰💰💰 Reduced-capacity copy running in DR region. Scale up on failure.
Multi-Site Active-Active Near-zero 💰💰💰💰 Highest Full copy in both regions. Route 53 failover routing.
🎯 Exam Tip

"Minimize cost, can tolerate hours of downtime" → Backup & Restore. "Minimize RTO, budget allows" → Multi-Site. "Balance cost and recovery" → Warm Standby. The exam always provides cost constraints — use them to eliminate options.

S3 Bucket with Lifecycle & Versioning

resource "aws_s3_bucket" "app_data" { bucket = "alienops-app-data-${var.environment}" } resource "aws_s3_bucket_versioning" "app_data" { bucket = aws_s3_bucket.app_data.id versioning_configuration { status = "Enabled" } } resource "aws_s3_bucket_lifecycle_configuration" "app_data" { bucket = aws_s3_bucket.app_data.id rule { id = "archive-old-data" status = "Enabled" transition { days = 30 storage_class = "STANDARD_IA" } transition { days = 90 storage_class = "GLACIER" } expiration { days = 365 } } }

Week 2 Ultimate Cheat Sheet

🎯 Review This Before the Exam

This is your one-page rapid review for all Week 2 Storage & Database content. Read it the night before, the morning of, and during any breaks.

🔵 S3 Quick Recall

  • 11 nines durability | Object max = 5TB | Multipart > 100MB
  • Standard (frequent) → IA (30 day min) → Glacier Instant (90d) → Glacier Flexible (1-12 hr) → Deep Archive (12-48 hr, 180d min)
  • Intelligent-Tiering = auto-moves, no retrieval fees, monitoring cost
  • One Zone-IA = cheapest IA, 1 AZ only, for re-creatable data
  • Encryption: SSE-S3 (default) | SSE-KMS (audit trail) | SSE-C (you manage keys)
  • Versioning: Can't disable, only suspend. MFA Delete = root only.
  • Object Lock: Governance (special perms override) vs Compliance (NOBODY overrides)
  • Replication: CRR (cross-region) / SRR (same-region). Requires versioning. New objects only.
  • Event Notifications: Lambda, SQS, SNS, EventBridge

🟡 EBS Quick Recall

  • AZ-locked. Move = Snapshot → Restore in new AZ.
  • gp3 = default, independent IOPS/throughput, up to 16K IOPS
  • io2 = highest perf, up to 256K IOPS (Block Express), Multi-Attach
  • st1 = throughput HDD (big data). sc1 = cold HDD (cheapest).
  • HDD (st1/sc1) CANNOT be boot volumes.
  • Snapshots: Incremental, stored in S3, cross-region copy possible
  • Encrypt unencrypted: Snapshot → Copy w/ encryption → Create volume
  • Instance Store: Ephemeral. Highest perf (local NVMe). Data lost on stop/terminate.

🟢 EFS / FSx Quick Recall

  • EFS: NFS, Linux only, multi-AZ, auto-scales, pay per use
  • FSx Windows: SMB + Active Directory. Windows shared storage.
  • FSx Lustre: HPC / ML. Sub-ms latency. Integrates with S3.
  • FSx NetApp ONTAP: Multi-protocol (NFS + SMB + iSCSI).

🔵 RDS / Aurora Quick Recall

  • Multi-AZ = HA (failover). Standby NOT readable. Sync replication.
  • Read Replicas = Read scaling. Async replication. Up to 5 (RDS) / 15 (Aurora).
  • Aurora: 6 copies × 3 AZs, 128 TiB auto-scale, <30s failover, Backtrack
  • Aurora Serverless v2: Auto-scale compute. ACU-based pricing. Min ACU = 0 pauses.
  • Aurora Global: < 1s cross-region replication. < 1 min promotion for DR.
  • Restore = NEW instance. Can't restore to existing DB.
  • IAM Auth: MySQL + PostgreSQL. Token-based, 15-min lifetime.

🟡 DynamoDB Quick Recall

  • Serverless NoSQL. Key-value + document. Max item = 400 KB.
  • On-Demand: No capacity planning. 2.5x cost. For unpredictable traffic.
  • Provisioned: Set RCU/WCU. Auto Scaling available. Cheaper for steady workloads.
  • 1 RCU = 1 strong read/s (4KB) or 2 eventual reads/s (4KB)
  • 1 WCU = 1 write/s (1KB)
  • GSI: Different PK. Own throughput. Eventually consistent only. Can add anytime.
  • LSI: Same PK, different SK. Created at table creation ONLY. Shares throughput.
  • DAX: In-memory cache for DynamoDB. Microsecond latency. Minimal code change.
  • Global Tables: Multi-region active-active. Requires Streams.
  • Streams: 24hr ordered changelog. Triggers Lambda.
  • TTL: Auto-delete items by timestamp. No cost.

🔴 ElastiCache Quick Recall

  • Redis: Persistence ✅ | Multi-AZ ✅ | Replicas ✅ | Sorted Sets ✅ | Pub/Sub ✅ | Backup ✅
  • Memcached: Multi-threaded ✅ | Simple k/v ✅ | Everything else ❌
  • Default choice = Redis unless "multi-threaded simple cache" is mentioned.
  • Lazy Loading: Read cache → miss → read DB → write cache. Stale data risk.
  • Write-Through: Write to both. Always current. Extra write latency.

❄️ Snow Family & Gateway Quick Recall

  • Snowcone: 8-14 TB. Edge + small migration.
  • Snowball Edge Storage: 80 TB. Large migrations.
  • Snowball Edge Compute: 42 TB + GPU. Edge ML.
  • Snowmobile: 100 PB. Data center migration.
  • Rule: < 10 TB online → DataSync. 10 TB - 10 PB → Snowball. > 10 PB → Snowmobile.
  • Storage Gateway S3 File: NFS/SMB → S3. On-prem file access.
  • Storage Gateway Volume: iSCSI → S3 (cached or stored mode).
  • Storage Gateway Tape: Virtual tapes → S3 + Glacier. Replace physical tapes.

🧠 Week 2 Mnemonics

  • "SSD for Speed, HDD for Heap" — SSD volumes (gp/io) for IOPS-intensive. HDD (st/sc) for throughput/archival.
  • "Multi-AZ = Insurance, Read Replica = Performance" — Never confuse the two.
  • "Aurora = RDS on Steroids" — More replicas, faster failover, auto-scale storage, backtrack.
  • "DynamoDB = Scale without Tears" — Serverless, any scale, ms latency, on-demand.
  • "Redis Has Everything" — When in doubt between Redis and Memcached, pick Redis.
  • "FedEx > Internet" — For large data, physical shipping (Snow) beats uploading.
