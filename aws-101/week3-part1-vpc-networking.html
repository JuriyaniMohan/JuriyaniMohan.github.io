VPC — Your Private Cloud Within AWS

A VPC is a logically isolated section of the AWS cloud where you launch resources in a virtual network you define. Think of it as your own private data center inside AWS — you control IP ranges, subnets, route tables, and gateways.

Why VPCs Exist
Before VPC (2009-2013), all EC2 instances ran in a shared flat network called EC2-Classic. Any instance could potentially reach any other. VPC was created to give customers network isolation, security boundaries, and control over IP addressing — just like a physical data center but elastic.

VPC Key Properties

  • Region-scoped — A VPC lives in one region but spans all AZs in that region
  • CIDR block — Primary IPv4 range you assign (e.g., 10.0.0.0/16 = 65,536 IPs)
  • Secondary CIDRs — You can add up to 4 more CIDR blocks later (total 5)
  • IPv6 — Optional /56 CIDR allocated by AWS (always public and globally unique)
  • Tenancy — Default (shared hardware) or Dedicated (single-tenant, expensive)
  • DNS — enableDnsSupport and enableDnsHostnames settings
Exam Tip
The Default VPC gets CIDR 172.31.0.0/16, has one public subnet per AZ, an IGW attached, and enableDnsHostnames=true. Custom VPCs have enableDnsHostnames=false by default — you must enable it for services like RDS that need DNS resolution.

CIDR Notation — The Foundation

Classless Inter-Domain Routing defines IP address ranges. The /XX suffix tells you how many bits are the "network" portion — the rest are available for hosts.

CIDRSubnet MaskTotal IPsUsable IPsUse Case

AWS Reserves 5 IPs Per Subnet
In every subnet, AWS reserves the first 4 and last 1 IP:
• .0 — Network address
• .1 — VPC router
• .2 — DNS server
• .3 — Future use
• .255 — Broadcast (not used but reserved)
So a /24 subnet has 256 - 5 = 251 usable IPs, not 254.

Subnets — Segmenting Your VPC

Subnets are segments of a VPC's IP range, each tied to exactly one Availability Zone. A subnet cannot span AZs. This is how you build multi-AZ resilience.

Public vs Private Subnets

There is no "public subnet" checkbox in AWS. A subnet is public because of two conditions:

  1. Its route table has a route to an Internet Gateway (IGW)
  2. Instances in it have a public IP or Elastic IP

A private subnet has no route to an IGW. Resources there cannot receive inbound internet traffic. For outbound internet (e.g., downloading patches), they use a NAT Gateway.

Internet Gateway (IGW)

  • Horizontally scaled, redundant, HA — managed by AWS, no bandwidth limit
  • One IGW per VPC (1:1 relationship)
  • Performs NAT between public and private IPs for instances with public IPs
  • Only allows traffic when route table + security group + NACL all permit it

Exam Tip — NAT Gateway HA Pattern
Deploy one NAT Gateway per AZ for true HA. Each private subnet's route table should point to the NAT GW in the same AZ. This ensures that if an AZ goes down, only resources in that AZ are affected — resources in other AZs continue working.

Elastic IP (EIP)

  • Static, public IPv4 address you own until you release it
  • Free when attached to a running instance; charged when unattached or attached to stopped instance
  • Limit: 5 per region (soft limit, can request increase)
  • Can be moved between instances for failover

Route Tables — The Traffic GPS

Every subnet must be associated with exactly one route table. A route table contains rules (routes) that determine where traffic is directed.

Production Best Practice
Never modify the Main Route Table. Create explicit custom route tables for public and private subnets. The main route table is a safety net — any unassociated subnet gets it. By keeping it private (no IGW route), new subnets are private by default. This is defense-in-depth.

Route Priority

AWS uses the most specific route (longest prefix match). Example:

10.0.0.0/16    → local           (VPC internal)
172.16.0.0/12  → pcx-xxx         (Peering connection)
0.0.0.0/0      → igw-xxx         (Internet — least specific, catch-all)

A packet to 10.0.3.45 matches /16 → stays local. A packet to 8.8.8.8 matches only 0.0.0.0/0 → goes to IGW.

Defense in Depth — Security Groups & NACLs

AWS provides two layers of network security that work together. Understanding their differences is one of the most heavily tested topics on the exam.

Biggest Exam Trap — Stateful vs Stateless
Security Groups are stateful: If you allow inbound HTTP (port 80), the response traffic is automatically allowed out — you don't need an outbound rule for it.

NACLs are stateless: You must explicitly allow both inbound (port 80) AND outbound (ephemeral ports 1024-65535) for HTTP to work. Forgetting the ephemeral port range outbound is the #1 reason NACL configurations break.

Security Group Chaining — The Real Power

Instead of referencing IP addresses, you reference other Security Groups. This is how production architectures are built:

# ALB Security Group: sg-alb
Inbound: 443 from 0.0.0.0/0 (HTTPS from internet)

# App Server Security Group: sg-app
Inbound: 8080 from sg-alb       (only accept from ALB!)

# Database Security Group: sg-db
Inbound: 3306 from sg-app       (only accept from app servers!)
Exam Tip — SG Chaining
When an exam question says "only the application tier should access the database" — the answer is Security Group referencing. Create a DB SG that allows port 3306 from the App SG. This is more secure than IP-based rules because it automatically applies to any instance in that SG.

NACL Rule Numbering Strategy

Rules are evaluated lowest number first. Best practice: use increments of 100 to leave room for insertions.

Rule 100: Allow HTTP  (80)  from 0.0.0.0/0
Rule 200: Allow HTTPS (443) from 0.0.0.0/0
Rule 300: Allow SSH   (22)  from 203.0.113.0/24
Rule 350: DENY  SSH   (22)  from 203.0.113.50/32   ← WON'T WORK!
                                                     Rule 300 already matched
* (Default): Deny all
Rule Order Trap
Because NACLs evaluate in order and stop at first match, a deny rule with a higher number than an allow rule for the same traffic will never be reached. To block a specific IP within an allowed range, the deny rule must have a lower number. E.g., Rule 250 DENY SSH from 203.0.113.50/32 before Rule 300 ALLOW SSH from 203.0.113.0/24.

VPC Flow Logs

  • Captures IP traffic metadata (not payload) going to/from network interfaces
  • Can be applied at VPC level, subnet level, or ENI level
  • Published to CloudWatch Logs, S3, or Kinesis Data Firehose
  • Captures accepted traffic, rejected traffic, or both
  • Does NOT capture: DNS traffic to Route 53, DHCP, metadata (169.254.169.254), NTP, Windows licensing
Production Use Case
Flow Logs → S3 → Athena for ad-hoc SQL queries on network traffic. Common interview question: "How would you troubleshoot why an instance can't reach the internet?" Answer: Check SG, NACL, route table, IGW, and VPC Flow Logs to see if traffic is being rejected.

VPC Connectivity Options

Connecting VPCs together, connecting to on-premises, and connecting to AWS services privately — this is where networking gets complex and where the exam goes deep.

VPC Peering

A 1-to-1 private connection between two VPCs using AWS's backbone network (not the internet). Can be within same account, cross-account, or cross-region.

  • Not transitive — If VPC-A peers with VPC-B and VPC-B peers with VPC-C, A cannot reach C through B
  • CIDR blocks must not overlap
  • Must update route tables on both sides
  • Can reference peered VPC's security groups (same region only)
Exam Trap — Transitive Peering
VPC Peering is NOT transitive. If you need full mesh connectivity between many VPCs, peering doesn't scale (n×(n-1)/2 connections). With 10 VPCs, you'd need 45 peering connections. The answer for "connect many VPCs" is Transit Gateway.

VPC Endpoints — Private Access to AWS Services

Traffic to AWS services (S3, DynamoDB, etc.) normally goes through the IGW/NAT. VPC Endpoints keep traffic entirely within the AWS network — more secure, lower latency, no data transfer charges.

Gateway Endpoints

  • Supported for: S3 and DynamoDB only
  • Added as a target in your route table (not an ENI)
  • Free — no hourly or data processing charges
  • Controlled by endpoint policies (resource-based JSON policies)
  • Cannot be extended to on-premises (VPN/DX traffic cannot use them)

Interface Endpoints (AWS PrivateLink)

  • Supported for most other AWS services (CloudWatch, KMS, STS, SSM, etc.)
  • Creates an ENI with a private IP in your subnet
  • Costs: hourly charge + per GB data processed
  • Can be accessed from on-premises via VPN/Direct Connect
  • Supports Security Groups for access control
  • Can enable Private DNS to override public DNS with private IPs

Exam Tip — When to Use Which
Gateway Endpoint: Use for S3/DynamoDB from within VPC — it's free and simple.
Interface Endpoint: Use when accessing AWS services from on-premises through VPN/DX, or for any service other than S3/DynamoDB.
Trick question: "Access S3 from on-premises without internet" → Interface Endpoint (not Gateway, because Gateway can't be used from on-premises).

AWS Transit Gateway (TGW)

A regional hub-and-spoke network transit hub that connects VPCs, VPNs, Direct Connect gateways, and peered Transit Gateways through a single point.

  • Supports transitive routing — VPC-A can reach VPC-C through TGW
  • Route tables on TGW control which attachments can talk to which
  • Supports multicast (only AWS networking service that does)
  • Can peer with TGWs in other regions (inter-region peering)
  • Supports up to 5,000 VPC attachments per TGW
  • Bandwidth: up to 50 Gbps per VPC attachment

Site-to-Site VPN

  • Encrypted IPsec tunnel over the public internet
  • AWS side: Virtual Private Gateway (VGW) or Transit Gateway
  • Customer side: Customer Gateway (CGW) — your router/firewall
  • Two tunnels for HA (each in a different AZ)
  • Max throughput: 1.25 Gbps per tunnel
  • Can be set up in minutes (vs weeks for Direct Connect)
  • Supports static routing or BGP dynamic routing

AWS Direct Connect (DX)

A dedicated physical fiber connection from your data center to an AWS Direct Connect location. Not over the internet — private, consistent, low-latency.

Exam Tip — DX + VPN Combo
"Consistent, low-latency AND encrypted" → Direct Connect with VPN overlay (IPsec over DX). DX alone is not encrypted.
"Quick connection while DX is being set up" → VPN as interim, then migrate to DX.
"Maximum resilience" → Two DX connections at two DX locations + VPN backup.

DX Virtual Interfaces (VIFs)

  • Private VIF — Access VPC resources via private IPs
  • Public VIF — Access AWS public services (S3, DynamoDB) via AWS backbone (not internet)
  • Transit VIF — Access Transit Gateway via DX

Direct Connect Gateway

Connects a DX connection to multiple VPCs in different regions (but same account or via Resource Access Manager). Without it, a DX connection can only reach VPCs in the same region.

Advanced VPC Concepts

AWS PrivateLink

Expose a service in your VPC to other VPCs (or accounts) without VPC peering, VPN, or internet. The consumer creates an Interface Endpoint; the provider creates a Network Load Balancer.

PrivateLink vs Peering — When to Use Which
VPC Peering: When two VPCs need full bidirectional access to each other's resources.
PrivateLink: When you want to expose a specific service from VPC-A to VPC-B without opening full network access. More secure, more scalable, used by SaaS providers. Think of it as a one-way window.

VPC Sharing (AWS RAM)

  • Share subnets with other AWS accounts in the same Organization
  • Participants can launch resources into shared subnets
  • Owner manages VPC, subnets, route tables, gateways
  • Reduces VPC count and simplifies networking

Elastic Network Interface (ENI)

  • Virtual network card attached to an instance
  • Has: primary private IP, one or more secondary IPs, one Elastic IP per private IP, one public IP, one or more Security Groups, a MAC address
  • Can be detached and moved between instances in the same AZ
  • Use case: Management network, dual-homed instances, low-budget HA

Exam Tip — EFA
If a question mentions HPC, MPI, tightly-coupled workloads, or inter-node communication — the answer is Elastic Fabric Adapter (EFA). EFA provides OS-bypass for ultra-low latency. Only available on Linux.

IPv6 in VPC

  • All IPv6 addresses in AWS are globally unique and public
  • IPv6 CIDR is /56 per VPC, /64 per subnet
  • Cannot disable IPv4 — dual-stack is required (IPv4 + IPv6)
  • Egress-Only Internet Gateway — allows IPv6 outbound but blocks inbound (like NAT GW for IPv6)
Exam Tip — Egress-Only IGW
If a question mentions "IPv6 instances need outbound internet but no inbound" — the answer is Egress-Only Internet Gateway. NAT Gateway does NOT support IPv6. This is a guaranteed exam question.

VPC Traffic Mirroring

  • Captures and mirrors network traffic from ENIs
  • Full packet capture (not just metadata like Flow Logs)
  • Sends to NLB or another ENI for analysis
  • Use case: intrusion detection, content inspection, threat monitoring

Network Firewall

  • Managed stateful firewall for VPC
  • Supports deep packet inspection, intrusion prevention (IPS), web filtering
  • Deployed at subnet level with endpoint in each AZ
  • Integrates with Firewall Manager for multi-account policies

Exam-Style Questions — VPC & Networking

Q1: A company has an application in a private subnet that needs to download software updates from the internet. The solution must be highly available. What should the solutions architect recommend?

Answer: C
NAT Gateway is the managed, scalable solution. For HA, deploy one per AZ. NAT instances require manual HA setup. An IGW would make them public (not private). VPN adds unnecessary complexity.

Q2: A solutions architect needs to allow an EC2 instance in a private subnet to access an S3 bucket without traffic going over the internet. The traffic should stay within the AWS network. Which is the most cost-effective solution?

Answer: B
Gateway Endpoints for S3 are free and keep traffic within AWS. Interface Endpoints work but cost money ($0.01/hr + data). NAT Gateway would work but costs more and traffic goes through NAT. You cannot peer with AWS service VPCs.

Q3: An application running on EC2 in VPC-A needs to communicate with a database in VPC-B (same region, same account). The VPC CIDR blocks do not overlap. What is the simplest solution?

Answer: B
For a simple 1-to-1 connection between two VPCs, VPC Peering is the simplest and cheapest. Transit Gateway works but is overkill for two VPCs. PrivateLink is for exposing specific services. VPN between VPCs is unnecessary complexity.

Q4: A company's web application is in a VPC. Users report intermittent connectivity issues. The security team wants to analyze network traffic patterns. Which feature provides the most useful data with least operational overhead?

Answer: B
VPC Flow Logs capture accept/reject decisions for all traffic at the network interface level with minimal overhead. Traffic Mirroring provides full packet capture but is more complex and expensive. CloudTrail captures API calls, not network traffic. tcpdump is manual and doesn't scale.

Q5: A company needs to connect its on-premises data center to AWS with consistent network performance and encryption. The connection must provide at least 5 Gbps bandwidth. What should the architect recommend?

Answer: B
The requirement is consistent performance (DX) AND encryption (VPN). DX alone provides consistency but is not encrypted by default. Adding an IPsec VPN overlay on DX provides both. VPN alone can't guarantee consistent performance or 5 Gbps. Client VPN is for individual user access, not site-to-site.

Q6: A company has 15 VPCs in the same region that all need to communicate with each other and with an on-premises data center via Direct Connect. What is the most operationally efficient architecture?

Answer: B
Transit Gateway is the hub-and-spoke model designed exactly for this. 15 VPCs with peering would need 105 connections (n×(n-1)/2). TGW needs only 15 attachments + 1 DX Gateway with Transit VIF. Cloud WAN is for multi-region global networks — overkill here.

Q7: An instance in a private subnet cannot reach the internet for software updates. The route table has 0.0.0.0/0 → nat-xxx. The NAT Gateway is in a public subnet with an Elastic IP. What should the architect check FIRST?

Answer: C
The most common misconfiguration: the NAT Gateway sits in a "public" subnet that doesn't actually have a route to the IGW. The NAT GW's subnet must have 0.0.0.0/0 → igw-xxx. Security Groups allow all outbound by default (A). NACLs allow all by default (B). Private instances don't need public IPs (D).
