Amazon Route 53 — Intelligent DNS

Route 53 is AWS's managed DNS service. Named after port 53 (DNS). It provides three functions: domain registration, DNS routing, and health checking.

Why Route 53 Matters for the Exam
Route 53 is the only AWS service with a 100% SLA. Understanding its routing policies is critical — at least 3-5 exam questions will test your ability to choose the right routing policy for a scenario.

DNS Fundamentals

DNS translates human-readable domain names (alienops.online) into IP addresses (54.123.45.67). The process involves a hierarchy:

Critical — CNAME vs ALIAS
CNAME cannot be used at the zone apex (naked domain like alienops.online). It only works on subdomains (www.alienops.online).

ALIAS is Route 53's special record — works at zone apex, resolves to an AWS resource (ALB, CloudFront, S3 website, etc.), and queries are free. This is the answer whenever an exam question asks about pointing a naked domain to an AWS resource.

Hosted Zones

  • Public Hosted Zone — Routes traffic on the internet. Contains records for your public domain.
  • Private Hosted Zone — Routes traffic within VPCs. Associates with specific VPCs for internal DNS (e.g., db.internal.alienops).
  • Cost: $0.50/month per hosted zone + $0.40 per million queries (standard)

Health Checks

  • Monitor endpoint health (HTTP, HTTPS, TCP)
  • Health checkers from multiple regions worldwide
  • Threshold: configurable (default 3 consecutive failures = unhealthy)
  • Can monitor: endpoints, other health checks (calculated), CloudWatch alarms
  • Integrates with routing policies for automatic failover
Exam Tip — Health Check + Private Resources
Route 53 health checkers are on the public internet — they cannot access private endpoints directly. To health-check a private resource, create a CloudWatch Alarm monitoring the resource, then create a Route 53 health check that monitors that CloudWatch Alarm.

Weighted Routing — Traffic Splitting

Assign a weight (0-255) to each record. Traffic percentage = record weight ÷ sum of all weights.

# Example: Gradual migration from old to new
app.alienops.online → old-server   Weight: 70  (70%)
app.alienops.online → new-server   Weight: 30  (30%)

# To send NO traffic to a record, set weight = 0
# If ALL weights are 0, traffic splits equally
Exam Tip — Weighted
Questions mentioning "send 10% of traffic to a new version" or "gradually shift traffic" = Weighted routing. It's NOT the same as ALB weighted target groups — Route 53 weighted is at the DNS level.

Latency-Based vs Geolocation vs Geoproximity

These three are the most confused. Here's the difference:

PolicyDecision FactorExample
Latency-basedNetwork latency measurementUser in Singapore gets routed to ap-southeast-1 because it has lowest latency (even though India is geographically closer)
GeolocationUser's physical continent/country/stateAll users in EU get routed to eu-west-1 for GDPR compliance, regardless of latency
GeoproximityGeographic distance + adjustable biasNormally users in Texas route to us-east-1, but with +50 bias on us-west-2, some Texas traffic shifts west
Exam Trap — Geolocation Default Record
With Geolocation routing, if a user's location doesn't match any configured records, they get no answer (NXDOMAIN). You must create a "Default" record as a catch-all. Without it, users from unmapped locations cannot access your site.

Failover Routing — DR Pattern

Common Exam Pattern — S3 Static Failover
Route 53 Failover + S3 static website hosting is a classic DR pattern. Primary = dynamic app on ALB/EC2. Secondary = static "sorry" page on S3. When primary fails health check, DNS automatically resolves to S3. Cost-effective passive DR.

Routing Policy Combos

You can nest routing policies using ALIAS records:

  • Latency + Failover: Use latency to pick the closest region, then failover within each region to a secondary
  • Geolocation + Weighted: Route EU users to EU, then within EU split 80/20 for A/B testing
  • Failover + Multi-value: Primary record fails over to a multi-value set for client-side balancing

Amazon CloudFront — Global CDN

CloudFront is AWS's Content Delivery Network with 450+ edge locations worldwide. It caches content close to users, reducing latency and offloading origin servers.

Why CloudFront Exists
Without a CDN, every request travels from the user to your origin (say, us-east-1). A user in Singapore has 200-300ms round-trip. CloudFront caches content at an edge location in Singapore — subsequent requests return in 5-20ms. This isn't optional for production apps — it's expected.

Key CloudFront Concepts

Origins

  • S3 bucket — Static content (images, CSS, JS). Uses Origin Access Control (OAC) for private buckets
  • Custom origin — ALB, EC2, API Gateway, any HTTP server
  • Origin Groups — Primary + secondary origin for automatic failover (if primary returns 5xx)
  • S3 bucket as website endpoint is treated as a custom origin (different from regular S3 origin)

Origin Access Control (OAC) — Securing S3 Origin

Restricts S3 bucket access so users must go through CloudFront — they cannot bypass it by hitting the S3 URL directly.

Exam Tip — OAC vs OAI
Origin Access Control (OAC) is the modern replacement for the older Origin Access Identity (OAI). OAC supports SSE-KMS encryption, all S3 regions, and is recommended. If the exam mentions "restrict direct S3 access while serving through CloudFront" — OAC is the answer. OAI is legacy.

Cache Behaviors

  • Rules that define how CloudFront handles different URL patterns
  • Default behavior (*) plus path-based behaviors (/api/*, /images/*)
  • Each behavior can point to a different origin and have different cache settings
  • Can configure: TTL, viewer protocol policy, allowed HTTP methods, compression
# Example: Multi-origin CloudFront
/api/*     → ALB origin (no caching, all methods)
/static/*  → S3 origin (max caching, GET only)
*          → S3 origin (default, moderate caching)

Cache Invalidation

  • Force CloudFront to remove objects from edge caches before TTL expires
  • /* invalidates everything (expensive at scale)
  • /images/logo.png invalidates specific file
  • First 1,000 invalidation paths/month free, then $0.005 per path
  • Better alternative: versioned file names (e.g., style-v2.css) — no invalidation needed

Signed URLs vs Signed Cookies — Exam Trap
Signed URL: Access to a single file. When RTMP (streaming) is needed. When client doesn't support cookies.
Signed Cookie: Access to multiple files (e.g., all files in /premium/). When you don't want to change URLs.
S3 Pre-signed URL (different!): Gives direct access to S3 object, bypasses CloudFront. Issued by IAM user.

AWS Global Accelerator

Provides static Anycast IP addresses that serve as a fixed entry point to your applications, routing traffic through AWS's global network instead of the public internet.

Global Accelerator vs CloudFront — Why Both Exist
CloudFront caches content at the edge. Great for static/cacheable content.
Global Accelerator routes connections through AWS's backbone. Great for dynamic, non-cacheable, TCP/UDP traffic. No caching — every request goes to the origin, but via AWS's optimized network instead of the public internet.

Key Features

  • 2 static Anycast IPs — Never change, global entry points
  • Health checking — Automatic failover to healthy endpoints in < 30 seconds
  • Endpoint groups — One per region, with traffic dial (0-100%) for weighted routing
  • Endpoints — ALB, NLB, EC2, Elastic IP
  • Client affinity — Can route same client to same endpoint (session stickiness)
  • Supports TCP and UDP (CloudFront is HTTP/HTTPS/WebSocket only)

Exam-Style Questions — Route 53, CloudFront & Edge

Q1: A company hosts an application in us-east-1 and eu-west-1. They want users to be routed to the region that provides the best experience. Which Route 53 routing policy should be used?

Answer: C
"Best experience" = lowest latency. Latency-based routing measures actual network latency and sends users to the region with the best performance. Geolocation routes by location (not latency). Weighted splits traffic by percentages. Failover is for DR.

Q2: A company wants to serve their website at the naked domain (example.com) pointing to an Application Load Balancer. Which DNS record type should be used?

Answer: C
CNAME cannot be used at the zone apex (naked domain) — DNS specification prohibits it. ALIAS is Route 53's solution: it works at the apex, resolves to AWS resources like ALB, and queries are free. ALB doesn't have a static IP (B). MX is for mail (D).

Q3: A media company needs to restrict access to premium video content so only paying subscribers can view it. The content is served through CloudFront from an S3 origin. What is the recommended approach?

Answer: B
Signed cookies provide access to multiple files (all premium content) without changing URLs. Signed URLs would work but are per-file and would require changing all video URLs. S3 pre-signed URLs bypass CloudFront. Geo-restriction blocks by country, not by subscription status.

Q4: A gaming company has real-time multiplayer servers in 4 AWS regions. Players need consistent, low-latency connections using UDP, and the company needs static IP addresses for firewall whitelisting. What should the architect use?

Answer: C
Three signals point to Global Accelerator: UDP protocol (CloudFront doesn't support UDP), static IP addresses (Anycast IPs), and consistent low-latency (AWS backbone). Route 53 latency routing helps with DNS but doesn't improve the actual network path. NLBs per region doesn't provide a unified static IP or backbone routing.

Q5: An application serves content to users in Europe and must comply with data residency requirements. European users' requests must ONLY be processed by servers in the EU, regardless of latency. Which Route 53 routing policy should be used?

Answer: B
"Data residency", "compliance", "users in [specific region] MUST be served by [specific location]" = Geolocation routing. Latency-based might route EU users to a non-EU region if it's faster. Geoproximity is about distance with bias, not strict geographic boundaries. Remember to add a default record for geolocation.

Q6: A company wants to add URL rewrite rules at CloudFront's edge to normalize request paths (e.g., redirect /PRODUCTS to /products). The transformation must be fast and handle millions of requests per second. What should they use?

Answer: B
URL rewrites are lightweight, need sub-millisecond execution, and must handle massive scale — exactly what CloudFront Functions are designed for. Lambda@Edge works but is overkill (slower, more expensive). Origin-side logic increases latency. WAF is for security rules, not URL transformations.
