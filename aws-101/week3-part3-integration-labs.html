Amazon SQS — Decoupled Message Queuing

SQS is a fully managed message queuing service that decouples producers from consumers. Instead of Service A calling Service B directly (tight coupling), A puts a message on a queue and B reads it when ready.

Why Decoupling Matters
Without queues: if Service B goes down, Service A fails too (cascade failure). With SQS: Service A puts messages in the queue and succeeds. When B comes back, it processes the backlog. This is the foundation of resilient, scalable architectures.

Standard vs FIFO Queues

FeatureStandard QueueFIFO Queue
ThroughputUnlimited — near-infinite TPS300 TPS (3,000 with batching)
OrderingBest-effort (may be out of order)Guaranteed FIFO
DeliveryAt-least-once (possible duplicates)Exactly-once processing
Queue NameAny valid nameMust end in .fifo
Use CaseHigh-volume, order not criticalFinancial transactions, order processing

Key SQS Concepts

  • Message Size: Max 256 KB. For larger payloads, use SQS Extended Client Library (stores data in S3, sends pointer in SQS)
  • Retention: 1 minute to 14 days (default 4 days)
  • Visibility Timeout: After a consumer reads a message, it becomes invisible to other consumers for this duration (default 30 seconds, max 12 hours). If processing takes longer, use ChangeMessageVisibility API
  • Long Polling: Consumer waits up to 20 seconds for messages (reduces empty responses and cost). Set WaitTimeSeconds > 0
  • Dead Letter Queue (DLQ): Messages that fail processing after N attempts (MaxReceiveCount) are moved to a DLQ for troubleshooting
Exam Tip — Visibility Timeout
If consumers are processing the same message twice, the visibility timeout is too short. If messages sit invisible too long, it's too long. This is a classic troubleshooting question.
Exam Trap — SQS + Auto Scaling
SQS alone doesn't scale consumers. Use CloudWatch metric ApproximateNumberOfMessagesVisible to trigger Auto Scaling for EC2/ECS consumers. When queue depth increases → scale out workers. This pattern appears in every other exam.

SQS Access Control

  • IAM policies — Who can send/receive (identity-based)
  • SQS Access Policy (resource-based) — Cross-account access, allowing other services (SNS, S3) to write to queue
  • Encryption: SSE-SQS (AWS managed) or SSE-KMS (customer managed). In-transit encryption with HTTPS.

Amazon SNS — Pub/Sub Messaging

SNS is a publish/subscribe messaging service. One message published → multiple subscribers receive it simultaneously. Fan-out pattern.

SNS Subscriber Types

  • SQS queues, Lambda functions, HTTP/HTTPS endpoints, email, SMS, Kinesis Data Firehose, mobile push
  • Up to 12.5 million subscriptions per topic, 100,000 topics per account

SNS + SQS Fan-Out — The Most Important Pattern

Publish once to an SNS topic → fan out to multiple SQS queues. Each queue processes independently. This is the de-facto pattern for event-driven architectures and appears in nearly every exam.

Exam Tip — SNS + SQS Fan-Out
When a question says "one event needs to trigger multiple independent processing workflows" — the answer is SNS → multiple SQS queues. Examples: order placed → send email + update inventory + send to analytics. FIFO topics work with FIFO queues for ordered fan-out.

Message Filtering

Subscribers can set filter policies (JSON) to receive only messages matching certain attributes. Without filtering, subscribers receive ALL messages on the topic.

# Filter policy on analytics SQS subscription:
{
  "order_type": ["premium"],
  "amount": [{"numeric": [">=", 100]}]
}
# Only receives messages where order_type=premium AND amount>=100

Amazon EventBridge — Serverless Event Bus

EventBridge is the evolution of CloudWatch Events. It's a serverless event bus that connects applications using events from AWS services, SaaS apps, and custom applications.

EventBridge vs SNS — When to Use Which
SNS: Simple pub/sub, high throughput, when you need fan-out to SQS/Lambda/HTTP.
EventBridge: Complex event routing with content-based filtering (rules that match on event content), scheduled events (cron), SaaS integration (Zendesk, Datadog, Auth0), and schema discovery. EventBridge is the more sophisticated choice for event-driven architectures.

Key Concepts

  • Event Bus — Default (AWS events), custom (your events), or partner (SaaS events)
  • Rules — Match events by pattern (content-based) and route to targets
  • Targets — Lambda, SQS, SNS, Step Functions, API Gateway, Kinesis, ECS tasks, and 15+ others
  • Schema Registry — Automatically discovers and stores event schemas
  • Archive & Replay — Store events and replay them later (great for debugging)
  • Scheduler — Run events on a schedule (cron or rate expressions) — replaces CloudWatch Events scheduling
# EventBridge Rule — Match pattern
{
  "source": ["com.alienops.orders"],
  "detail-type": ["Order Created"],
  "detail": {
    "amount": [{"numeric": [">=", 500]}],
    "region": ["APAC"]
  }
}
# Only triggers for orders >= $500 from APAC region
Exam Tip — EventBridge Scheduler
For "run a Lambda function every 5 minutes" or "trigger an ECS task at 2 AM daily" — EventBridge Scheduler (or EventBridge rule with schedule expression). This replaced the older CloudWatch Events cron functionality.

AWS Step Functions — Visual Workflows

Step Functions lets you orchestrate multiple AWS services into serverless workflows using a visual state machine. Each step can be a Lambda function, ECS task, DynamoDB operation, SNS publish, or other AWS service action.

Workflow Types

FeatureStandard WorkflowExpress Workflow
DurationUp to 1 yearUp to 5 minutes
ExecutionExactly-onceAt-least-once (async) / At-most-once (sync)
PricingPer state transitionPer execution + duration + memory
Use CaseLong-running: order processing, ETL, human approvalHigh-volume: IoT data, streaming, real-time

Key States

  • Task — Do work (invoke Lambda, call API, run ECS task)
  • Choice — Branching logic (if/else)
  • Parallel — Execute branches simultaneously
  • Wait — Delay for X seconds or until a specific time
  • Map — Iterate over a collection (like forEach)
  • Succeed / Fail — Terminal states
Production Pattern — Step Functions for Order Processing
1. Validate order (Lambda) → 2. Check inventory (DynamoDB) → 3. Process payment (Lambda) → 4. If payment fails → retry 3 times with exponential backoff → 5. If still fails → send to DLQ → 6. If succeeds → Ship order (ECS task) + Send confirmation (SNS).

This orchestration with retry logic, error handling, and parallel execution is exactly what Step Functions excels at.
Exam Tip — Step Functions vs SQS
Step Functions: When you need orchestration — sequential/parallel steps, error handling, retries, human approval, visual workflow. Think "workflow coordinator."
SQS: When you need decoupling — buffer between producer/consumer, handle traffic spikes, loose coupling. Think "message buffer."
They often work together: Step Functions can push to SQS as one of its steps.

Amazon API Gateway

A fully managed service to create, publish, maintain, and secure APIs at any scale. It's the front door for your backend services.

API Types

TypeProtocolUse CaseKey Feature
REST APIHTTPFull-featured APIs with caching, throttling, API keysMost features, higher cost
HTTP APIHTTPSimple APIs, Lambda proxy, OIDC/OAuth270% cheaper, lower latency
WebSocket APIWebSocketReal-time bidirectional (chat, gaming, dashboards)Persistent connections

Key Features

  • Throttling: Default 10,000 RPS per account per region, burst 5,000. Per-method throttling available.
  • Caching: 300 MB - 237 GB cache. Reduces backend calls. TTL 0-3600s.
  • Stages: dev, staging, prod — each with independent configuration and deployment.
  • Usage Plans + API Keys: Rate limiting per customer. Not for authentication — for throttling/metering.
  • Authorization: IAM, Cognito User Pools, Lambda authorizer (custom JWT/token validation).
  • Integration Types: Lambda proxy (most common), HTTP proxy, AWS service integration, Mock.
Exam Tip — REST vs HTTP API
If the question mentions caching, API keys, usage plans, request validation, WAF integration, or private APIs → REST API.
If the question mentions lowest cost, lowest latency, simple Lambda proxy, or OAuth2/OIDC auth → HTTP API.
Default exam answer for "API in front of Lambda" is usually REST API unless cost optimization is the priority.
Exam Trap — API Gateway 29-Second Timeout
API Gateway has a hard limit of 29 seconds for integration timeout. If your backend takes longer, API Gateway returns 504. For long-running operations, use an asynchronous pattern: API Gateway → Lambda → start Step Functions → return immediately → client polls for status.

Hands-On Lab 1: Production VPC with Multi-AZ

Build the complete VPC architecture from the overview diagram.

Steps

  1. Create VPC with CIDR 10.0.0.0/16, enable DNS hostnames
  2. Create 4 subnets: 2 public (10.0.1.0/24, 10.0.2.0/24) + 2 private (10.0.3.0/24, 10.0.4.0/24) across 2 AZs
  3. Create and attach Internet Gateway
  4. Create 2 NAT Gateways (one per AZ) with Elastic IPs
  5. Create route tables: public (→ IGW) and private per AZ (→ local NAT GW)
  6. Create Security Groups with chaining: ALB-SG → App-SG → DB-SG
  7. Create custom NACL for public subnets allowing HTTP/HTTPS/SSH + ephemeral outbound
  8. Create S3 Gateway Endpoint and add to private route tables
  9. Enable VPC Flow Logs → CloudWatch Logs
Cost Warning
NAT Gateways cost ~$0.045/hr each (~$32/month each). For learning, you can use 1 NAT GW and share it. Delete when not in use. The S3 Gateway Endpoint is free.

Hands-On Lab 2: Route 53 + CloudFront + S3

  1. Create S3 bucket with static website enabled (your AlienOps landing page)
  2. Create CloudFront distribution with S3 origin + OAC
  3. Update S3 bucket policy to only allow CloudFront access
  4. Request ACM certificate in us-east-1 (required for CloudFront)
  5. Configure CloudFront to use custom domain + ACM cert
  6. Create Route 53 ALIAS record: alienops.online → CloudFront distribution
  7. Test: direct S3 URL should be blocked, CloudFront URL works, custom domain works with HTTPS
Exam Tip — ACM Region for CloudFront
ACM certificates for CloudFront must be in us-east-1 regardless of where your origin is. For ALB/API Gateway, ACM cert must be in the same region as the resource. This is a guaranteed exam question.

Hands-On Lab 3: SNS + SQS Fan-Out

  1. Create SNS topic: order-events
  2. Create 2 SQS queues: fulfillment-queue and analytics-queue
  3. Subscribe both queues to the SNS topic
  4. Add filter policy on analytics queue: only receive order_type: "premium"
  5. Create DLQ: fulfillment-dlq with maxReceiveCount = 3

Terraform — VPC Module for AlienOps

# modules/vpc/main.tf — Production VPC Module

variable "project_name" { default = "alienops" }
variable "vpc_cidr"     { default = "10.0.0.0/16" }
variable "azs"          { default = ["ap-southeast-1a", "ap-southeast-1b"] }

# VPC
resource "aws_vpc" "main" {
  cidr_block           = var.vpc_cidr
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = { Name = "${var.project_name}-vpc" }
}

# Internet Gateway
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id
  tags   = { Name = "${var.project_name}-igw" }
}

# Public Subnets (one per AZ)
resource "aws_subnet" "public" {
  count                   = length(var.azs)
  vpc_id                  = aws_vpc.main.id
  cidr_block              = cidrsubnet(var.vpc_cidr, 8, count.index + 1)
  availability_zone       = var.azs[count.index]
  map_public_ip_on_launch = true

  tags = { Name = "${var.project_name}-public-${count.index + 1}" }
}

# Private Subnets (one per AZ)
resource "aws_subnet" "private" {
  count             = length(var.azs)
  vpc_id            = aws_vpc.main.id
  cidr_block        = cidrsubnet(var.vpc_cidr, 8, count.index + 3)
  availability_zone = var.azs[count.index]

  tags = { Name = "${var.project_name}-private-${count.index + 1}" }
}

# Elastic IPs for NAT Gateways
resource "aws_eip" "nat" {
  count  = length(var.azs)
  domain = "vpc"
  tags   = { Name = "${var.project_name}-nat-eip-${count.index + 1}" }
}

# NAT Gateways (one per AZ for HA)
resource "aws_nat_gateway" "main" {
  count         = length(var.azs)
  allocation_id = aws_eip.nat[count.index].id
  subnet_id     = aws_subnet.public[count.index].id

  tags       = { Name = "${var.project_name}-nat-${count.index + 1}" }
  depends_on = [aws_internet_gateway.main]
}

# Public Route Table
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }

  tags = { Name = "${var.project_name}-public-rt" }
}

resource "aws_route_table_association" "public" {
  count          = length(var.azs)
  subnet_id      = aws_subnet.public[count.index].id
  route_table_id = aws_route_table.public.id
}

# Private Route Tables (one per AZ → local NAT GW)
resource "aws_route_table" "private" {
  count  = length(var.azs)
  vpc_id = aws_vpc.main.id

  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.main[count.index].id
  }

  tags = { Name = "${var.project_name}-private-rt-${count.index + 1}" }
}

resource "aws_route_table_association" "private" {
  count          = length(var.azs)
  subnet_id      = aws_subnet.private[count.index].id
  route_table_id = aws_route_table.private[count.index].id
}

# S3 Gateway Endpoint (FREE — saves NAT costs)
resource "aws_vpc_endpoint" "s3" {
  vpc_id       = aws_vpc.main.id
  service_name = "com.amazonaws.ap-southeast-1.s3"

  route_table_ids = aws_route_table.private[*].id

  tags = { Name = "${var.project_name}-s3-endpoint" }
}

# VPC Flow Logs
resource "aws_flow_log" "main" {
  vpc_id               = aws_vpc.main.id
  traffic_type         = "ALL"
  log_destination_type = "cloud-watch-logs"
  log_destination      = aws_cloudwatch_log_group.flow_logs.arn
  iam_role_arn         = aws_iam_role.flow_logs.arn
}

resource "aws_cloudwatch_log_group" "flow_logs" {
  name              = "/aws/vpc/flow-logs/${var.project_name}"
  retention_in_days = 14
}

# Outputs
output "vpc_id"             { value = aws_vpc.main.id }
output "public_subnet_ids"  { value = aws_subnet.public[*].id }
output "private_subnet_ids" { value = aws_subnet.private[*].id }

Exam-Style Questions — Integration Services

Q1: An e-commerce application needs to process orders asynchronously. When order volume spikes, some orders are being processed twice. Which solution prevents duplicate processing?

Answer: B
SQS FIFO queues provide exactly-once processing through message deduplication (using deduplication IDs or content-based deduplication). Standard queues provide at-least-once delivery, which means duplicates are possible. Increasing visibility timeout reduces duplicates but doesn't eliminate them.

Q2: When a new image is uploaded to S3, it must be processed by three independent services: thumbnail generation, metadata extraction, and content moderation. What architecture provides the most decoupled solution?

Answer: B
SNS + SQS fan-out is the most decoupled pattern. Each service reads from its own queue independently — if one fails, others continue. Option A is tightly coupled. Step Functions (C) adds orchestration complexity. EventBridge (D) works but SQS provides buffering and retry, which is more resilient.

Q3: A company needs to run a data processing pipeline every day at 3 AM UTC. The pipeline involves 5 sequential steps with error handling and retry logic. Which combination of services is most appropriate?

Answer: B
EventBridge Scheduler handles the cron trigger. Step Functions handles the sequential steps with built-in error handling, retry logic, and visual monitoring. Lambda chaining (A) is fragile — if one fails, the chain breaks with no coordination. SQS (C) is for decoupling, not orchestration. SNS (D) can't schedule.

Q4: An application processes messages from an SQS queue using a fleet of EC2 instances. During peak hours, the queue depth grows and processing falls behind. What should the architect implement?

Answer: C
Scale consumers based on queue depth. The ApproximateNumberOfMessagesVisible metric in CloudWatch triggers Auto Scaling to add more EC2 workers. Retention (A) just keeps messages longer, doesn't process faster. Long polling (B) reduces empty receives, doesn't help with backlog. FIFO (D) has LOWER throughput than standard.

Q5: A REST API backed by Lambda functions needs to handle up to 50,000 concurrent requests with response caching for repeated queries. Which API Gateway type should be used?

Answer: B
REST API supports response caching — HTTP API does not. The question specifically mentions caching, which is only available in REST API. While HTTP API is cheaper and lower latency, it lacks the caching feature required here.
